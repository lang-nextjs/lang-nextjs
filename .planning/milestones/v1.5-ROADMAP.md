## Phase Details

### Phase v1.3-01: Core Examples & Documentation
**Goal**: Developers can evaluate and adopt deepagents-nextjs via runnable examples and complete API references for every package
**Depends on**: Nothing (builds on shipped v1.2 packages)
**Requirements**: EX-02, EX-03, EX-04, EX-05, DOC-01, DOC-02, DOC-03, DOC-04, DOC-05, DOC-06
**Success Criteria** (what must be TRUE):
  1. A developer can clone the repo, run `pnpm install && turbo dev`, open `apps/sveltekit-example` or `apps/remix-example`, and see a working chat UI that streams messages from the mock backend
  2. A developer can open `apps/example` and use the adapter swap UI to switch between deepagentsAdapter, langGraphAdapter, and langchainAdapter without a page reload
  3. Every package README (`server`, `react`, `sveltekit`, `remix`, `test-utils`) contains a one-liner install, a two-line quick start, and a full API reference that matches the shipped package exports
  4. A developer can follow `docs/TESTING.md` and `apps/example/*.test.ts` to write a test against `createMockDeepAgentsServer()` with zero additional configuration
  5. All three example apps (`example`, `sveltekit-example`, `remix-example`) pass `turbo build` and typecheck in CI on every PR
**Plans**: 4 plans
Plans:
- [x] v1.3-01-01-PLAN.md — SvelteKit example app (apps/sveltekit-example) with handler + store + CI build gate
- [x] v1.3-01-02-PLAN.md — Remix example app (apps/remix-example) with action handler + hook + CI build gate
- [x] v1.3-01-03-PLAN.md — Extended apps/example: adapter swap UI, consumer test suite (example.test.ts), vitest config
- [x] v1.3-01-04-PLAN.md — Six package READMEs (server, react, sveltekit, remix, test-utils) + docs/TESTING.md

### Phase v1.3-02: Edge Runtime Adapter
**Goal**: Developers targeting Deno Deploy or Cloudflare Workers can wire up deepagents-nextjs with the same two-line pattern using only Web Streams API
**Depends on**: Phase v1.3-01 (documentation standards and README patterns established)
**Requirements**: EDGE-01, EDGE-02, EDGE-03, EDGE-04
**Success Criteria** (what must be TRUE):
  1. A Deno Deploy handler created with `createDenoHandler({ backendUrl, adapter })` streams AI SDK v6 SSE frames to the client using only `ReadableStream`, `TextEncoderStream`, and `TextDecoder` — no Node.js imports in the bundle
  2. A Cloudflare Workers handler created with `createCloudflareHandler({ backendUrl, adapter })` compiles and runs; the README prominently documents the SSE buffering caveat (TTFB > 10s) and recommends Deno Deploy as the primary edge target
  3. `@deepagents-nextjs/edge` passes `publint` and `attw` checks in CI; the `exports` field is ESM-only; importing the package in a Node.js project does not pull in `next` as a transitive dependency
  4. Cloudflare Workers TTFB is measured in an actual Workers preview deployment before shipping; if TTFB > 5s, `createCloudflareHandler` is marked EXPERIMENTAL in the README
**Plans**: 3 plans
Plans:
- [x] v1.3-02-01-PLAN.md — Package scaffold + SseFrameAccumulator copy + createDenoHandler (Web Streams only)
- [x] v1.3-02-02-PLAN.md — createCloudflareHandler implementation (EXPERIMENTAL, direct Response pattern)
- [x] v1.3-02-03-PLAN.md — README (TTFB caveat, Deno primary, API reference) + CI publint/attw guards

### Phase v1.3-03: Stream Reconnection
**Goal**: Users on unstable networks can reconnect to an interrupted AI stream without receiving duplicate messages or losing streamed content
**Depends on**: Phase v1.3-01; conditional gate on AI SDK bugs #6502 + #11865 being resolved
**Requirements**: STR-01
**Success Criteria** (what must be TRUE):
  1. When a network interruption is simulated via DevTools offline, the client automatically reconnects and the stream resumes from where it left off — no duplicate messages appear in the UI
  2. A developer can trigger manual retry via the `retry()` function returned from `useDeepAgentsChat`; a loading indicator is shown during reconnection
  3. If the same `resumeId` is submitted twice concurrently, the server delivers the stream exactly once — duplicate submissions are idempotent
  4. If AI SDK bugs #6502 or #11865 are unresolved at phase kickoff, stream reconnection ships behind `ENABLE_STREAM_RECONNECT=true` (default off) with a prominent README warning, or is deferred to v1.4
**Plans**: 3 plans
Plans:
- [x] v1.3-03-01-PLAN.md — Server foundation TDD: stream-registry.ts (in-memory Map singleton) + reconnect.ts (flag guard + GET handler factory)
- [x] v1.3-03-02-PLAN.md — Integration: handler.ts POST resumeId dedup + server index.ts exports + hook.ts retry() + react index.ts
- [x] v1.3-03-03-PLAN.md — README warnings: ENABLE_STREAM_RECONNECT feature flag docs + bug #6502/#11865 known limitations

### Phase v1.4-01: E2E Test Coverage
**Goal**: Companies can evaluate and adopt deepagents-nextjs with confidence — every production-critical flow is validated end-to-end in a real browser with a running server, not mocks.
**Depends on**: Nothing (builds on shipped v1.3; all adapters, frameworks, auth helpers, and reconnection are complete)
**Requirements**: E2E-01, E2E-02, E2E-03, E2E-04, E2E-05, E2E-06, E2E-07, E2E-08, E2E-09, E2E-10
**Success Criteria** (what must be TRUE):
  1. A developer can run `pnpm test:e2e` and see all 10 E2E test scenarios pass against a running Next.js dev server with a mock backend
  2. Auth flow: a cookie set in the browser is forwarded as `Authorization: Bearer` to the backend — verified by inspecting the request received server-side
  3. Backend 5xx mid-stream: the client renders an error state in the UI, not a frozen spinner — verified by simulating a 500 response
  4. Tool call rendering: a `tool-call` message emitted by the backend appears in the UI with pending then complete status transitions
  5. Multi-adapter: langGraphAdapter and langchainAdapter each produce visible text in the chat UI when their respective SSE format is returned by the mock backend
  6. Remix E2E: one full send → stream → render cycle passes in `apps/remix-example`
  7. SvelteKit E2E: one full send → stream → render cycle passes in `apps/sveltekit-example`
  8. Rapid sends: two messages sent back-to-back both appear in the UI with correct content and order — no interleaving
  9. Stream reconnection: with `ENABLE_STREAM_RECONNECT=true`, a retry() call after stream interruption resumes and appends to existing messages
  10. Large response: a 200-token response accumulates completely in the DOM — no truncation
**Plans**: 3 plans
Plans:
- [ ] v1.4-01-01-PLAN.md — Next.js E2E: auth cookie → Bearer, 5xx error state, tool call rendering, multi-adapter (E2E-01 to E2E-04)
- [ ] v1.4-01-02-PLAN.md — Framework E2E: Remix + SvelteKit full cycles; rapid-send; data-plan schema; large response (E2E-05 to E2E-08, E2E-10)
- [ ] v1.4-01-03-PLAN.md — Reconnection E2E + CI: retry() flow, resume route, ENABLE_STREAM_RECONNECT, test:e2e script, GitHub Actions matrix (E2E-09 + CI)

### Phase v1.5-01: openSweAdapter Foundation
**Goal**: Developers can stream open-swe tool events (start and end) from a LangGraph Platform run through the adapter, with heartbeat keep-alive and correct reordering for parallel tool calls
**Depends on**: Phase v1.4-01 (or can run in parallel — no adapter code dependency on E2E; depends on shipped v1.2 adapter patterns)
**Requirements**: ADAPT-01, ADAPT-02, ADAPT-03, ADAPT-04
**Success Criteria** (what must be TRUE):
  1. A developer passing `openSweAdapter` to `createDeepAgentsHandler` sees `tool-input-start` frames in the AI SDK v6 stream when the LangGraph Platform emits `on_tool_start` events
  2. A developer sees `tool-output-available` frames in the stream when the upstream emits `on_tool_end` events, with the correct `tool_call_id` linking each pair
  3. A run that produces no upstream events for 30 seconds still holds the SSE connection open — a heartbeat comment frame is received by the client and no timeout or connection reset occurs
  4. When two tool calls arrive in reversed order (simulated in a unit test), the buffered output is emitted in the correct `tool_call_id` order — no out-of-order frames reach the client
**Plans**: 3 plans

### Phase v1.5-02: Approval Gating
**Goal**: Developers can opt into tool-level approval gating — the handler emits a pause frame and holds the run until the client sends back an explicit approve or reject signal
**Depends on**: Phase v1.5-01 (openSweAdapter core must exist before gating is layered on top)
**Requirements**: ADAPT-05
**Success Criteria** (what must be TRUE):
  1. When approval gating is enabled on the handler, the client receives a `data-approval-required` frame containing the pending tool call details before the tool executes
  2. The run remains paused — no further tool or text frames are emitted — until the handler receives an explicit approval or rejection POST from the client
  3. When the client sends a rejection, the run is cancelled and a terminal frame is emitted; no further tool execution occurs
  4. When approval gating is disabled (default), the adapter behaves identically to the non-gating path — no `data-approval-required` frames are emitted
**Plans**: 3 plans
Plans:
- [ ] v1.5-02-01-PLAN.md — RED: failing tests for approval-registry, approvalGating transform, handler integration
- [ ] v1.5-02-02-PLAN.md — GREEN: implement approval-registry + approvalGating transform + wire into handler
- [ ] v1.5-02-03-PLAN.md — Approval route factory (createApprovalRoutes) + server package exports + README docs

### Phase v1.5-03: apps/open-swe Scaffold + API Routes
**Goal**: A developer can submit a new coding task and retrieve a list of all runs via REST API from a locally-running open-swe Next.js dashboard
**Depends on**: Phase v1.5-01 (openSweAdapter must exist to wire into the API routes)
**Requirements**: DASH-01, DASH-02
**Success Criteria** (what must be TRUE):
  1. A developer can run `pnpm --filter open-swe dev` from the monorepo root and reach the dashboard at `localhost:3001` (or configured port) without errors
  2. A `POST /api/open-swe/runs` request with a task description body returns a JSON response containing a `run_id` — the run is registered with the local LangGraph Platform server
  3. A `GET /api/open-swe/runs` request returns a JSON array of runs, each with `run_id`, `status` (pending/running/completed/failed), `created_at`, and `task` description
  4. Both endpoints return appropriate HTTP error responses (422 for missing body, 502 if LangGraph Platform is unreachable) rather than unhandled 500s

### Phase v1.5-04: Live Streaming + Tool Visualization
**Goal**: A user can watch a live agent run stream in the dashboard — seeing text and tool events in real time — and inspect tool call payloads, with no event leakage between concurrent open runs
**Depends on**: Phase v1.5-03 (API routes must exist); Phase v1.5-01 (openSweAdapter must produce the events being visualized); Phase v1.5-02 (approval UI depends on gating being implemented)
**Requirements**: DASH-03, DASH-04, DASH-05
**Success Criteria** (what must be TRUE):
  1. A user opening the run detail page for an active run sees agent text tokens appear progressively in the browser without a page reload, streamed via `GET /api/open-swe/runs/[runId]/stream`
  2. Tool call events appear as expandable cards in the run view — the card shows a pending state when `tool-input-start` is received and a completed state when `tool-output-available` arrives
  3. A user can expand a completed tool call card and see the full input payload and output result, not a truncated summary
  4. With two run detail pages open simultaneously in the same browser, events from run A do not appear on the page for run B — streams are fully isolated per `runId`
**Plans**: 2 plans
Plans:
- [ ] v1.5-04-01-PLAN.md — Wave 0 RED stubs + SSE proxy route (GET /api/open-swe/runs/[runId]/stream)

### Phase v1.5-05: MCP Tools
**Goal**: An LLM agent can trigger, inspect, and cancel open-swe coding runs via MCP tools without polling loops — each tool call returns immediately with the current state
**Depends on**: Phase v1.5-03 (API routes that MCP tools proxy to must exist)
**Requirements**: MCP-01, MCP-02, MCP-03, MCP-04
**Success Criteria** (what must be TRUE):
  1. An LLM agent calling `trigger_task` with a task description string receives a `run_id` in the tool response within the same MCP call — the tool does not wait for the run to complete
  2. An LLM agent calling `list_runs` receives a structured list of all runs with their statuses — the response is suitable for the agent to decide which run to query next
  3. An LLM agent calling `get_run_status` with a `run_id` receives the current status and the latest output snapshot of that run — no polling loop is required on the agent side
  4. An LLM agent calling `cancel_run` with a `run_id` for an active run receives a confirmation that the cancellation was requested; subsequent `get_run_status` calls show the run as cancelled or failed
**Plans**: 2 plans
Plans:
- [x] v1.5-05-01-PLAN.md — Wave 0: 21 RED test stubs for all 4 tools in packages/mcp/src/index.test.ts (completed 2026-05-05)
- [x] v1.5-05-02-PLAN.md — GREEN: implement trigger_task + list_runs + get_run_status + cancel_run + two new app/open-swe API routes (completed 2026-05-05)
