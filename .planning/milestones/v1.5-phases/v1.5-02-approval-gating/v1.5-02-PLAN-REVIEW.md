# v1.5-02 Approval Gating: Implementation Plan Review

**Review Date:** 2026-05-04  
**Reviewer:** Claude Code (Haiku 4.5)  
**Status:** CRITICAL GAPS IDENTIFIED

## Executive Summary

**VERDICT: BLOCK** with required fixes before execution.

The three-plan structure for Phase v1.5-02 correctly captures the work breakdown (RED tests → GREEN implementation → API exposure), and the must_haves statements accurately mirror the ROADMAP success criteria. **However, five critical gaps exist** that will cause implementation failures if not addressed in Plan 02 before GREEN execution:

1. **Task 2, Step 6f Race Condition** — Rejection path returns null without emitting terminal frame (ROADMAP #3 violated)
2. **Task 2, Step 6e Approval Drain Race** — POST handler clears approval but transform hasn't draining yet  
3. **Task 2, Non-Tool Frame Gating Gap** — Transform only gates tool-input-start, misses text-delta and other frames during approval (ROADMAP #2 partial coverage)
4. **Task 3 Missing Cleanup Edge Case** — cleanupExpiredApprovals() called in finally but registry state is shared across requests (memory leak)
5. **Plan 01 Missing Test Coverage** — No test for buffering text-delta frames when approval is pending

## Detailed Analysis

### 1. ROADMAP Criteria vs. Plan must_haves

**Finding: MATCH (but brittle)**

All four ROADMAP criteria are restated verbatim in all three plans' must_haves sections:

### 2. **CRITICAL GAP: Task 2, Step 6f — Rejection Path Doesn't Emit Terminal Frame**

**Location:** v1.5-02-02-PLAN.md, Task 2, action section, step 6f

**Current language:**
```
f. If approval.status === "rejected" → return null (discard)
```

**ROADMAP Criterion 3 requires:**
> "When the client sends a rejection, the run is cancelled and a terminal frame is emitted; no further tool execution occurs"

**Problem:**
- Returning null discards buffered frames but emits **nothing** to the client
- No terminal frame is emitted to signal cancellation
- Client sees the stream pause (data-approval-required received) but no error/closure feedback on rejection
- ROADMAP explicitly requires a "terminal frame be emitted on rejection"

**Impact:**
- Implementation will fail criterion 3 as written
- Client-side tests expecting rejection to emit `data-error` will fail
- Users experience stuck UI (approval frame without rejection confirmation)

**Example failure scenario:**
```
Client: receives data-approval-required (waiting for decision)
User: clicks "Reject"
POST /api/approval/{id} sent with decision=reject
Server: resolveApproval() sets status="rejected"
Next frame arrives (tool-output-available from backend)
Transform: sees status==="rejected", returns null
Client: receives nothing (stream continues, no error signal)
Result: User confused, stream silently consumes more frames
```

**Fix required in Plan 02, Task 2:**
Step 6f should read:
```
f. If approval.status === "rejected":
   - Clear buffered frames (discard)
   - Return { raw: `data: ${JSON.stringify({ 
       type: "data-error", 
       data: { 
         code: "tool_rejected", 
         message: "Tool execution rejected by user" 
       } 
     })}` } (emit terminal error frame)
   - pendingApprovalsByToolCallId.delete(toolCallId)
```

### 3. **CRITICAL GAP: Task 2, Step 6e — Approval Drain Race Condition**

**Location:** v1.5-02-02-PLAN.md, Task 2, action section, step 6e and also Task 3, action section (POST handler)

**Current language (Task 2, step 6e):**
```
e. If approval.status === "approved" → push frame to readyQueue (or push first to readyQueue, clear pendingMap entry); return readyQueue.shift()!
```

**Current language (Task 3, POST handler):**
```
// Resolve: update status in registry (transform reads status on next call)
resolveApproval(approvalId, decision as "approve" | "reject");
cleanupApproval(approvalId);
```

**Problem:**
1. POST handler calls `cleanupApproval(approvalId)` immediately after `resolveApproval()`
2. Task 2 step 6e expects to read `getApproval(approvalId)` on the next transform call
3. But the approval is already deleted from the registry — lookup returns undefined
4. Transform then falls through to the "approval expired" path (step 6g in current plan) OR crashes

**Race timeline:**
```
T0: Client GET /api/approval/{id} → status=waiting
T1: User clicks Approve
T2: POST /api/approval/{id} with decision=approve
T3: POST handler: resolveApproval(approvalId) → status becomes "approved"
T4: POST handler: cleanupApproval(approvalId) → DELETED from registry
T5: Next frame arrives at approvalTransform
T6: Transform: getApproval(approvalId) → undefined (already cleaned up!)
T7: Transform: handles as expired approval or crashes
Result: Buffered frames never drained, tool never executes
```

**ROADMAP Impact:**
- Criterion 1: tool-input-start never reaches client (it's buffered and lost)
- User waits forever for tool to execute

**Fix required in Plan 02, Task 3:**
POST handler should NOT call `cleanupApproval()` immediately:
```typescript
POST: async (request, context) => {
  // ... validation ...

  if (approval.status !== "waiting") {
    return NextResponse.json(
      { error: "approval already resolved", status: approval.status },
      { status: 409 }
    );
  }

  // Resolve: update status in registry
  resolveApproval(approvalId, decision as "approve" | "reject");
  
  // DO NOT cleanup immediately — let the transform drain buffered frames
  // The transform will access the approval on its next call and see status==="approved"
  // After draining, the transform can signal cleanup to the registry
  // OR: cleanup can happen in the SSE finally block via cleanupExpiredApprovals()

  return NextResponse.json({ id: approvalId, decision, accepted: true });
}
```

**Alternative:** Move cleanup to Task 2, step 6e:
```
e. If approval.status === "approved":
   - Transfer buffered frames to readyQueue
   - Clear pendingMap entry
   - cleanupApproval(approvalId) — only after draining
   - return readyQueue.shift()!
```

### 4. **CRITICAL GAP: Task 2 — Transform Only Gates tool-input-start, Not Text-Delta**

**Location:** v1.5-02-02-PLAN.md, Task 2, action section, step 6

**ROADMAP Criterion 2 requires:**
> "The run remains paused — no further **tool OR text frames** are emitted — until the handler receives an explicit approval or rejection POST from the client"

**Current language (step 6):**
```
6. Extract toolCallId from parsed (check parsed.toolCallId):
   - If toolCallId exists and pendingApprovalsByToolCallId.has(toolCallId):
```

**Problem:**
- Only frames WITH a `toolCallId` field are checked against pending approvals
- Text-delta frames (`{ type: "text-delta", delta: "Hello " }`) do NOT have a toolCallId
- These frames will pass through (return frame) even while an approval is pending
- ROADMAP explicitly requires "tool OR text frames" to be paused

**Example failure scenario:**
```
Approval pending: toolCallId=run-123--tool_1
LLM generates text: text-delta frame arrives
Transform step 6: looks for toolCallId in text-delta → not found
Step 6 logic: toolCallId not in pendingApprovalsByToolCallId → pass through
Result: Client receives text-delta even though approval is pending
Criterion 2 violated: "no further tool OR text frames" — text WAS emitted
```

**Fix required in Plan 02, Task 2:**

Step 6 logic needs to gate ALL frames during pending approval, not just tool frames:
```
6. If ANY approval is pending (pendingApprovalsByToolCallId.size > 0):
   a. Check if frame has a toolCallId and it's in pending map → buffer/reject as before
   b. ELSE: check frame type
      - If text-delta → buffer it (don't emit)
      - If tool-output-* → buffer it (don't emit)
      - If [DONE] and NO approvals pending → pass through; else buffer
      - If other → buffer or pass-through depending on type
   c. Return null (don't emit any frame during pending approval)

7. If no approvals pending, return frame (pass-through)
```

**Alternative simpler approach:**
Keep a global "is any approval pending" flag:
```typescript
const hasAnyPendingApproval = () => pendingApprovalsByToolCallId.size > 0;

return function approvalTransform(frame: SseFrame): SseFrame | null {
  // Drain readyQueue first
  if (readyQueue.length > 0) return readyQueue.shift()!;

  // ... parse frame ...

  // If any approval is pending, buffer all frames until approval resolves
  if (hasAnyPendingApproval()) {
    // This is a frame that arrived while gating is active
    // Store it for draining, but be careful:
    // - If it's the tool-input-start for the pending approval, it's already in bufferedFrames
    // - If it's a subsequent frame, add it to the same bufferedFrames list
    // - If it's an unrelated tool (different toolCallId), should it be gated?
    
    // Conservative: gate everything except [DONE] and unrelated tools
    if (frame.raw === "[DONE]") return frame;
    
    // Buffer this frame
    const approvalId = pendingApprovalsByToolCallId.values().next().value; // or track the approval being waited for
    const approval = getApproval(approvalId);
    if (approval) {
      approval.bufferedFrames.push(frame);
      return null;
    }
  }
  
  // ... rest of logic ...
}
```

**Warning sign:** Current Plan 02 has no explicit mention of text-delta handling, and step 6 only references toolCallId matching.

### 5. **CRITICAL GAP: Task 3 — Cleanup Edge Case (Memory Leak)**

**Location:** v1.5-02-02-PLAN.md, Task 3, action section

**Current language:**
```typescript
finally {
  if (resumeId && isStreamReconnectEnabled()) {
    markStreamDone(resumeId);
  }
  // Clean up any expired/abandoned approvals from this request
  if (options.approvalGating) {
    cleanupExpiredApprovals();
  }
}
```

**Problem 1: cleanupExpiredApprovals() is global, not request-scoped**
- `cleanupExpiredApprovals()` per the plan deletes "all entries where expiresAt < Date.now() AND status !== 'approved'"
- But multiple requests can be active concurrently, each with their own approvals
- One request's finally block could delete approvals from OTHER concurrent requests
- This causes race conditions in concurrent test scenarios

**Problem 2: Approved approvals are never cleaned up**
- cleanupExpiredApprovals() specifically SKIPS "status !== 'approved'" (it keeps approved ones)
- An approved approval that was already drained should be deleted
- But the current plan never explicitly deletes approved approvals after drain completes
- Over time, approved registry entries accumulate

**Impact:**
- Memory leak: approved approvals pile up in registry
- Concurrent requests: one request's cleanup deletes another's pending approval
- Test failures: concurrent test cases will see approval registry mutations from other tests

**Example:**
```
Concurrent requests A and B both have approvals pending
Request A finishes: finally block calls cleanupExpiredApprovals()
cleanupExpiredApprovals() deletes entries with expiresAt < now (not status-based)
But Request B's approval expiresAt is NOT < now yet (still waiting)
So it survives... but what if the approvals happen to share an expiresAt time?
Or if expiresAt is not checked correctly?
Actually, looking closer: "status !== 'approved'" means it KEEPS approved, deletes waiting/rejected/timeout
This is backwards — it should clean up all terminal states, only keep waiting
```

**Fix required in Plan 02, Task 2:**
Revise cleanup strategy:
```typescript
// In approval-registry.ts, update cleanupExpiredApprovals:
export function cleanupExpiredApprovals(): number {
  let cleaned = 0;
  for (const [id, approval] of registry.entries()) {
    // Delete if:
    // 1. Expired (expiresAt < now) AND (status is terminal: approved/rejected/timeout)
    // 2. OR: status is approved and bufferedFrames is empty (already drained)
    if ((approval.expiresAt < Date.now() && 
         (approval.status === "approved" || approval.status === "rejected" || approval.status === "timeout")) ||
        (approval.status === "approved" && approval.bufferedFrames.length === 0)) {
      registry.delete(id);
      cleaned++;
    }
  }
  return cleaned;
}
```

**AND in Task 2, step 6e, after draining:**
```
e. If approval.status === "approved":
   - Transfer bufferedFrames to readyQueue
   - Clear pendingMap entry
   - Clear bufferedFrames[] in approval (signal that it's been drained)
   - return readyQueue.shift()!
```

### 6. **MODERATE GAP: Plan 01 Missing Test Case**

**Location:** v1.5-02-01-PLAN.md, feature/behavior section, task 2

**Current test cases for approvalGating transform:**
- Pass-through when require: false
- Approval required → data-approval-required emitted
- Buffering: subsequent tool-output-available for same toolCallId returns null
- Buffering: frame for DIFFERENT toolCallId passes through
- Readyqueue drain: after approved, next transform call drains buffered frames
- Rejection: transform returns null for rejected toolCallId frames

**Missing test cases:**
1. **Text-delta gating during pending approval** — emit text-delta while approval pending → should return null (buffer), not pass through
2. **Concurrent tool calls (one gated, one not)** — two tools, only one requires approval; unrelated tool frames should pass through while first is pending
3. **[DONE] frame during pending approval** — Should [DONE] be buffered or pass through? Current plan doesn't specify

**Impact:**
- Plan 01 RED tests won't catch the text-delta gating issue (gap #4 above)
- When Plan 02 is executed, test coverage will be incomplete
- Integration tests in handler will fail because text-delta handling is untested

**Fix required in Plan 01, Task 2:**
Add to the list of test cases:
```
- Approval required with text frames: after approval-required, a subsequent text-delta frame returns null (buffered, not emitted)
- Buffering multiple frame types: after approval-required for tool-A, text-delta and tool-output-available arrive; both return null; after approval, all three (tool-input-start + text-delta + tool-output-available) are drained in order
- Non-gated tool during approval: while tool-A approval is pending, tool-B (different toolCallId, no approval required) frames pass through normally
- [DONE] frame during approval: if [DONE] arrives while approval pending, it's buffered (not emitted), drained after approval
```

## Questions for Clarification (for Plan Author)

1. **Seq counter scope:** Should the seq counter be incremented per approval (once per stream) or per data frame? Current research shows per-approval, but this should be explicit in Task 2.

2. **Global registry vs. request-scoped:** Approval registry is globalThis singleton (like stream-registry). Is this intentional for long-running servers with many concurrent requests? Should there be a per-handler registry instead?

3. **[DONE] frame timing:** Should [DONE] be emitted:
   - Immediately when received (pass-through)?
   - After all approvals are resolved?
   - Buffered like other frames?
   
   Current plan doesn't specify.

4. **Approval config per-tool:** getApprovalConfig is called per tool call. What if different tools have different timeoutMs? Is the timeout recalculated per tool, or is there a default? Current plan says "timeoutMs = result.timeoutMs ?? 300_000" — is 300s the right default?
