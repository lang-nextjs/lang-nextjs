# Phase v1.5-02: Approval Gating - Research

**Researched:** 2026-05-04
**Domain:** SSE handler pause/resume for human-in-the-loop tool approval, bidirectional messaging
**Confidence:** HIGH

## Summary

Phase v1.5-02 implements tool-level approval gating on top of the completed openSweAdapter foundation from v1.5-01. Developers can opt-in to pause runs before tool execution, require explicit client approval, and reject tools entirely. This requires two architectural additions: (1) a new `data-approval-required` frame type that pauses the stream emission (NOT dropped from the handler, but buffered internally), and (2) a bidirectional messaging channel where the client sends back approval/rejection decisions to an approval endpoint on the handler.

The approval gating is a **pass-through by default** — approval gating must be explicitly enabled on the handler to avoid breaking existing non-gating deployments. The implementation pattern mirrors the existing conditional stream reconnection (ENABLE_STREAM_RECONNECT feature flag) — a factory option gates the behavior at handler creation time.

**Primary recommendation:** Implement approval gating as a separate SseTransform inserted into the handler pipeline (opt-in via handler option), paired with a new /api/approval endpoint that receives approval/rejection POST requests and resumes buffered streams. Use an in-memory registry (like stream-registry) to track paused streams by approval ID.

### Buffering Strategy: Two-Stage Pipeline

Approval gating uses a **pause-and-buffer** pattern that does NOT modify the openSweTransform itself (keeps it stateless):

1. **Approval Transform** — New transform inserted after openSweAdapter.transforms:
   - On `tool-input-start` frame: check `getApprovalConfig()` 
   - If approval required: emit `data-approval-required` frame and buffer the `tool-input-start` (return null to prevent it from reaching the client)
   - Record pending approval ID in `approvalRegistry` 
   - Subsequent frames for this toolCallId are DROPPED until approval arrives
   - Return the approval frame immediately

2. **Resume Handler** — New POST /api/approval endpoint (created by handler factory):
   - Receives `{ approvalId, decision: "approve" | "reject" }` from client
   - Looks up approval in `approvalRegistry`
   - If approved: unblock buffered `tool-input-start` + subsequent frames; emit them to the stored controller
   - If rejected: emit cancellation frame, discard buffered frames, mark stream as terminated
   - Clean up registry entry

### Approval Transform Closure State

```typescript
// Source: createApprovalGatingTransform (new)
export function createApprovalGatingTransform(
  getApprovalConfig?: (toolCall: { ... }) => { require: boolean; ... } | undefined
): SseTransform {
  const pendingApprovalsByToolCallId = new Map<string, string>(); // toolCallId → approvalId
  
  return function approvalTransform(frame: SseFrame): SseFrame | null {
    // ... frame parsing ...
    
    // On tool-input-start:
    if (frame.type === "tool-input-start") {
      const { toolCallId, toolName, input } = parsed;
      
      if (getApprovalConfig?.({ toolCallId, toolName, input })?.require) {
        // Emit approval frame, buffer the tool-input-start
        const approvalId = crypto.randomUUID();
        registerApproval({
          approvalId,
          toolCallId,
          toolName,
          input,
          bufferedFrames: [frame], // buffer the start
          status: "waiting"
        });
        pendingApprovalsByToolCallId.set(toolCallId, approvalId);
        
        // Return the approval frame (not the tool-input-start)
        return {
          raw: `data: ${JSON.stringify({
            type: "data-approval-required",
            data: { ... }
          })}`
        };
      }
      // Approval not required → pass through normally
      return frame;
    }
    
    // On subsequent frames:
    if (pendingApprovalsByToolCallId.has(frame.toolCallId)) {
      // This frame is for a pending approval → buffer it
      const approval = getApproval(pendingApprovalsByToolCallId.get(frame.toolCallId)!);
      approval?.bufferedFrames.push(frame);
      return null; // Don't emit yet
    }
    
    // Not affected by approval gating → pass through
    return frame;
  };
}
```

**Key design choice:** The approval transform wraps the incoming frames, NOT the output stream. It sits in the SseTransform pipeline after openSweAdapter. This avoids modifying the openSweAdapter itself (keeping it stateless per v1.5-01 decisions).

### Cancellation and Rejection Flow

When client sends `POST /api/approval/{approvalId}` with `{ decision: "reject" }`:

1. Look up approval in registry → find buffered frames
2. Discard buffered frames
3. Emit a `data-error` frame with code="tool-rejected", message="Tool execution rejected by user"
4. Mark stream as terminal (controller.close() after error frame)
5. Remove from registry

When client sends `{ decision: "approve" }`:

1. Look up approval → retrieve buffered frames
2. Emit buffered `tool-input-start` frame
3. Emit any subsequent buffered frames (tool-input-delta, tool-output-available)
4. Mark approval as "approved" in registry
5. Unblock transform so future frames for this toolCallId pass through normally

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Approval state tracking (waiting → approved/rejected/timeout) | Custom state machine, if/else chains | Zod + schema validation + registry | Edge cases: concurrent requests, cleanup, timeout tracking; registry pattern proven in stream-registry.ts |
| Bidirectional messaging (emit frame + wait for response) | Custom promise/callback pattern | ReadableStreamController + registry coupling | Race conditions: what if approval resolves before transform sees the tool-input-start? Registry decouples concerns. |
| Frame buffering and ordering | Array of frames in transform state | Approval registry (same as stream-registry) | Memory leaks if approval never resolves; TTL eviction needed; registry pattern handles cleanup. |
| HTTP endpoints for approval decisions | Manual routes + state passing | Handler factory returning route creators | Testability: route handlers need registry context; factory pattern enables DI. |

**Key insight:** Approval gating looks simple (pause/resume) but has subtle concurrency issues: the transform may emit `tool-input-start`, the client receives it, the user decides, and before the POST request completes, the next transform call already happened. Registry + controller coupling solves this by buffering in one place and having the POST handler explicitly unblock via controller.enqueue().

## Common Pitfalls

### Pitfall 1: Unblocking Buffered Frames Without Respecting SseTransform Contract

**What goes wrong:** After approval resolves, code tries to emit multiple buffered frames immediately. But `SseTransform` returns `SseFrame | null` (single frame per call). If you emit all buffered frames in one `controller.enqueue()` call, subsequent transform calls skip them because you already consumed the buffer.

**Why it happens:** Confusing the transform's "return a frame" contract with the controller's "enqueue raw bytes" capability. The transform pipeline is called per-frame by the accumulator; it doesn't automatically drain your buffer.

**How to avoid:** Use the same pattern as openSweTransform's `readyQueue` — when approval unblocks N frames:
1. Return the first frame from the transform call
2. Push the rest into a `readyQueue`
3. On the next transform call, drain readyQueue before processing new input
Alternatively: don't call transform again — directly enqueue buffered frames to the controller from the approval POST handler (simpler, but breaks pipeline abstraction).

**Warning signs:** 
- Client receives `data-approval-required` but no subsequent `tool-input-start` after approval
- Second tool call after approval works, but frames from approved tool are missing
- Test shows buffering works but integration test shows frames lost

### Pitfall 2: Registering Approval But No Cleanup on Stream Close

**What goes wrong:** Approval is registered but the stream closes (client disconnects, request times out) before approval resolves. The registry entry is never cleaned up, leaking memory on long-running servers with many requests.

**Why it happens:** Approval registration is in the transform (request-scoped), but cleanup was never wired to the stream completion (controller.close() in finally block). Easy to miss if you only test the happy path.

**How to avoid:** In the streaming loop's finally block, clean up any pending approvals for this stream:
```typescript
finally {
  for (const [approvalId, approval] of approvalRegistry.entries()) {
    if (approval.streamId === currentStreamId) {  // need to track which stream each approval belongs to
      approvalRegistry.delete(approvalId);
      approval.status = "timeout"; // mark as expired
    }
  }
}
```

**Warning signs:**
- Server memory grows over time, especially under load
- Old approval registry entries never disappear
- Manual restart needed to free memory

### Pitfall 3: Concurrent Approvals for the Same toolCallId

**What goes wrong:** Two clients submit approval decisions for the same toolCallId at the same time. First one unblocks the buffer, second one tries to resolve a non-existent approval and fails silently (or crashes).

**Why it happens:** No idempotency check or lock on the approval resolution. Easy to cause in tests or on high-concurrency servers.

**How to avoid:**
1. Use atomic compare-and-swap when resolving: `if (approval.status === "waiting") { approval.status = decision; ... }` 
2. Return 409 Conflict if already resolved instead of 200
3. Test concurrent POST /api/approval calls (use Promise.all in test suite)

**Warning signs:**
- Tests pass in isolation but fail under concurrency
- One approval resolves but the stream doesn't unblock
- POST /api/approval returns 500 or hangs

### Pitfall 4: Approval Timeout Fires But Stream Still Tries to Use Expired Approval

**What goes wrong:** Approval expires (via lazy TTL check in getApproval). Later, a transform call tries to buffer another frame for that toolCallId and does `getApproval(approvalId)` → returns undefined. Code crashes or silently drops the frame.

**Why it happens:** TTL is lazy (no background timer), so the approval can look expired at random times. If the same toolCallId is reused or a delayed frame arrives, the approval lookup fails without a clear error.

**How to avoid:**
1. When an approval expires, update its status to "timeout" instead of deleting immediately
2. On timeout, emit a `data-error` frame with code="approval_timeout" so client knows the tool was rejected
3. Stop buffering new frames for that toolCallId (add a check: `if (approval.status !== "waiting")` before buffering)

**Warning signs:**
- Client sees `data-approval-required` but stream closes with no error
- Frames arrive after a long delay (>timeout) and are silently dropped
- Error logs show undefined errors when trying to access timed-out approval

### Pitfall 5: Emitting Approval Frame Without Seq Number

**What goes wrong:** `data-approval-required` frame is emitted without a `seq` field. Client-side schema parsing fails because `ApprovalSchema` expects seq to be a nonnegative integer.

**Why it happens:** ApprovalSchema was designed for structured data frames (plan, task, file, approval) that need unique seq per stream. Easy to forget when constructing the frame in the transform.

**How to avoid:** 
- Increment a per-request seq counter in the handler (or approval registry)
- Pass the current seq to the approval transform factory: `createApprovalGatingTransform(getApprovalConfig, seqCounter)`
- When constructing the approval frame, use `seqCounter.next()` and include in the data payload

**Warning signs:**
- Client-side parsing of data-approval-required returns `{ ok: false, error: ... }`
- Type narrowing to `DataApproval` fails on seq field
- Integration tests show frame is sent but React hook doesn't recognize it

### Approval Transform Factory

```typescript
// Source: packages/server/src/adapters/approvalGating.ts (new)
import type { SseFrame, SseTransform } from "../accumulator";
import { getApproval, registerApproval } from "../approval-registry";
import { crypto } from "node:crypto";

export interface ApprovalGatingConfig {
  getApprovalConfig?: (toolCall: {
    toolCallId: string;
    toolName: string;
    input: Record<string, unknown>;
  }) => { require: boolean; timeoutMs?: number } | undefined;
  seqCounter?: { next: () => number };
}

/**
 * Factory: create an SSE transform that gates tools behind explicit approval.
 * 
 * When a tool-input-start frame arrives:
 *   1. Check getApprovalConfig() to see if approval is required
 *   2. If yes: generate approval ID, register in approval-registry, emit data-approval-required, buffer the tool-input-start
 *   3. If no: pass through normally
 * 
 * When buffering is active (pending approval):
 *   - All subsequent frames for that toolCallId are buffered
 *   - Return null (don't emit to client)
 * 
 * When approval resolves (via POST /api/approval):
 *   - Approval registry calls approveApproval() or rejectApproval()
 *   - Transform's readyQueue drains buffered frames on next call
 */
export function createApprovalGatingTransform(
  config: ApprovalGatingConfig
): SseTransform {
  const pendingApprovalsByToolCallId = new Map<string, string>(); // toolCallId → approvalId
  const readyQueue: SseFrame[] = [];
  
  return function approvalTransform(frame: SseFrame): SseFrame | null {
    // Drain readyQueue first (approval unblock at previous step)
    if (readyQueue.length > 0) {
      return readyQueue.shift()!;
    }
    
    const line = frame.raw;
    if (!line.startsWith("data: ")) return frame;
    
    const raw = line.slice(6);
    if (raw === "[DONE]") return frame;
    
    let parsed: Record<string, unknown>;
    try {
      parsed = JSON.parse(raw) as Record<string, unknown>;
    } catch {
      return frame; // Non-JSON — pass through
    }
    
    // tool-input-start: check if approval required
    if (parsed.type === "tool-input-start") {
      const toolCallId = parsed.toolCallId as string;
      const toolName = parsed.toolName as string;
      const input = (parsed.input ?? {}) as Record<string, unknown>;
      
      const approvalConfig = config.getApprovalConfig?.({
        toolCallId,
        toolName,
        input,
      });
      
      if (!approvalConfig?.require) {
        // Approval not required — pass through
        return frame;
      }
      
      // Approval required: generate ID, register, emit data-approval-required
      const approvalId = crypto.randomUUID();
      const seq = config.seqCounter?.next() ?? 0;
      const createdAt = new Date().toISOString();
      const timeoutMs = approvalConfig.timeoutMs ?? 300000; // 5 min default
      const expiresAt = new Date(Date.now() + timeoutMs).toISOString();
      
      registerApproval({
        approvalId,
        toolCallId,
        toolName,
        input,
        description: `Approval required for ${toolName}`,
        createdAt: Date.now(),
        expiresAt: Date.now() + timeoutMs,
        bufferedFrames: [frame], // buffer the tool-input-start
        status: "waiting",
      });
      
      pendingApprovalsByToolCallId.set(toolCallId, approvalId);
      
      // Emit approval frame
      return {
        raw: `data: ${JSON.stringify({
          type: "data-approval-required",
          data: {
            id: approvalId,
            seq,
            actionName: toolName,
            description: `Approval required for ${toolName}`,
            arguments: input,
            status: "waiting",
            createdAt,
            expiresAt,
          },
        })}`,
      };
    }
    
    // For any frame with a toolCallId, check if it's pending approval
    const toolCallId = (parsed.toolCallId ?? parsed.toolId) as string | undefined;
    if (toolCallId && pendingApprovalsByToolCallId.has(toolCallId)) {
      // This frame belongs to a pending approval — buffer it
      const approval = getApproval(pendingApprovalsByToolCallId.get(toolCallId)!);
      if (approval && approval.status === "waiting") {
        approval.bufferedFrames.push(frame);
        return null; // Don't emit yet
      } else if (approval && approval.status === "rejected") {
        return null; // Discard — approval was rejected
      } else if (!approval) {
        // Approval expired — emit error
        return {
          raw: `data: ${JSON.stringify({
            type: "data-error",
            data: {
              code: "approval_timeout",
              message: "Tool approval expired",
            },
          })}`,
        };
      }
      // approval.status === "approved" — pass through normally
    }
    
    return frame;
  };
}

// Export for handler integration
export function approveApprovalAndDrain(
  approvalId: string,
  readyQueue: SseFrame[]
): void {
  const approval = getApproval(approvalId);
  if (!approval || approval.status !== "waiting") {
    throw new Error(
      `Approval ${approvalId} not found or already resolved`
    );
  }
  
  approval.status = "approved";
  // Queue buffered frames for emission on next transform call
  for (const bufferedFrame of approval.bufferedFrames) {
    readyQueue.push(bufferedFrame);
  }
}

export function rejectApprovalAndError(approvalId: string): SseFrame | null {
  const approval = getApproval(approvalId);
  if (!approval || approval.status !== "waiting") {
    return null; // Already resolved
  }
  
  approval.status = "rejected";
  approval.bufferedFrames = []; // Discard buffered frames
  
  // Return error frame to emit to client
  return {
    raw: `data: ${JSON.stringify({
      type: "data-error",
      data: {
        code: "tool_rejected",
        message: "Tool execution rejected by user",
      },
    })}`,
  };
}
```

### Approval Registry

```typescript
// Source: packages/server/src/approval-registry.ts (new)
import type { SseFrame } from "./accumulator";

export interface PendingApproval {
  approvalId: string;
  toolCallId: string;
  toolName: string;
  input: Record<string, unknown>;
  description: string;
  createdAt: number; // Date.now()
  expiresAt: number; // Date.now() + timeoutMs
  bufferedFrames: SseFrame[];
  status: "waiting" | "approved" | "rejected" | "timeout";
}

const registry = new Map<string, PendingApproval>();

export function registerApproval(approval: PendingApproval): void {
  registry.set(approval.approvalId, approval);
}

export function getApproval(
  approvalId: string
): PendingApproval | undefined {
  const approval = registry.get(approvalId);
  
  // Lazy TTL check: if expired, mark as timed out but don't delete yet
  // (allow subsequent calls to see the timeout status)
  if (approval && approval.expiresAt < Date.now()) {
    if (approval.status === "waiting") {
      approval.status = "timeout";
    }
  }
  
  return approval;
}

export function resolveApproval(
  approvalId: string,
  decision: "approve" | "reject"
): void {
  const approval = getApproval(approvalId);
  if (!approval) return;
  
  if (decision === "approve") {
    approval.status = "approved";
  } else {
    approval.status = "rejected";
  }
}

export function cleanupApproval(approvalId: string): void {
  registry.delete(approvalId);
}

/**
 * Cleanup all expired approvals (call periodically or in stream finally block).
 * Returns count of cleaned entries.
 */
export function cleanupExpiredApprovals(): number {
  const now = Date.now();
  let cleaned = 0;
  
  for (const [id, approval] of registry) {
    if (approval.expiresAt < now && approval.status !== "approved") {
      registry.delete(id);
      cleaned++;
    }
  }
  
  return cleaned;
}
```

## Open Questions

1. **Approval endpoint routing:**
   - Should the handler factory return route creators (e.g. `createApprovalRoutes()`) or should consumers manually wire /api/approval routes?
   - Simpler: return route factory functions; consumers handle routing (follows separation of concerns)
   - More integrated: handler auto-registers routes (requires Next.js middleware or route context passing)
   - **Recommendation:** Return route factory functions; let consumers call them in their app/api/approval/[approvalId]/route.ts

2. **Seq numbering for approval frames:**
   - Should seq be a global handler counter or per-approval counter?
   - Global: incremented for every frame (text-delta, tool-input-start, data-approval-required, etc.)
   - Per-approval: separate seq per approval (client can track multiple approvals)
   - **Recommendation:** Global counter; matches existing pattern for other data-* frames (data-plan, data-task). Simpler to implement and test.

3. **Multiple pending approvals for the same run:**
   - If tool A requires approval and tool B starts before A is approved, should B also be paused?
   - Design A: Approvals are independent (B proceeds, A stays paused)
   - Design B: Stream pauses completely until all pending approvals resolve
   - **Recommendation:** Design A (independent per-tool); matches LLM agent workflow where parallel tools can run concurrently after separate approvals.

4. **Approval timeout behavior:**
   - Should timeout emit an error frame and close the stream, or silently reject?
   - Error frame: client knows what happened (better UX)
   - Silent reject: simpler implementation, less noise
   - **Recommendation:** Emit data-error with code="approval_timeout"; allows client UI to show reason for rejection.

5. **Backwards compatibility:**
   - Phase v1.5-01 shipped openSweAdapter without approval gating. Should v1.5-02 default to approval gating on all tools, or opt-in per handler?
   - **Locked decision from REQUIREMENTS.md:** "When approval gating is disabled (default), the adapter behaves identically to the non-gating path." → Approval gating is opt-in, off by default (no breaking change).
