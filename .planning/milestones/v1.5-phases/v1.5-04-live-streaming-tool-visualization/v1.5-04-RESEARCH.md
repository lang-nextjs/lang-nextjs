# Phase v1.5-04: Live Streaming + Tool Visualization - Research

**Researched:** 2026-05-04
**Domain:** Real-time SSE streaming, tool call visualization, concurrent stream isolation
**Confidence:** HIGH

## Summary

Phase v1.5-04 adds a live dashboard view for open-swe runs, enabling users to watch agent execution in real time with expandable tool call cards. The phase builds on existing v1.5-01 (openSweAdapter) and v1.5-03 (API routes) infrastructure, leveraging the established SSE proxy pattern.

The phase requires three core deliverables:
1. **GET /api/open-swe/runs/[runId]/stream** — SSE endpoint that proxies events for a specific run
2. **React components** — Tool call visualization with pending/completed states
3. **Stream isolation** — Ensure concurrent runs don't leak events between browsers/tabs

The implementation pattern is straightforward: reuse `createDeepAgentsHandler` with `openSweAdapter`, add types for tool call events, and build React hooks for EventSource consumption with per-runId isolation.

**Primary recommendation:** Use EventSource browser API (not fetch-based ReadableStream) for client-side SSE consumption — EventSource handles auto-reconnection, is simpler, and matches the existing useDeepAgentsChat pattern in @deepagents-nextjs/react. For tool card state management, use React useState with a Map-like structure keyed by tool_call_id to track pending → completed transitions.

### Pattern 1: SSE Proxy Route (GET /api/open-swe/runs/[runId]/stream)

**What:** A Next.js route handler that:
1. Validates the runId parameter
2. Looks up the run's threadId (from some session/context)
3. Calls LangGraphClient.streamRun(threadId, runId) — or the equivalent endpoint
4. Wraps the response with createDeepAgentsHandler + openSweAdapter
5. Returns the transformed SSE stream

**When to use:** Whenever you need server-side SSE proxy with transform logic; all deepagents-nextjs patterns follow this.

**Example:**
```typescript
// apps/open-swe/app/api/open-swe/runs/[runId]/stream/route.ts
// Source: Follows v1.5-03 POST /api/open-swe/runs pattern

import { NextRequest, NextResponse } from "next/server";
import { createDeepAgentsHandler } from "@deepagents-nextjs/server";
import { openSweAdapter } from "@deepagents-nextjs/server";
import { LangGraphClient } from "../../../../../lib/langgraph-client";

export const dynamic = "force-dynamic"; // CRITICAL: SSE requires dynamic evaluation

export async function GET(
  request: NextRequest,
  { params }: { params: { runId: string } }
): Promise<Response> {
  const platformUrl = process.env.LANGGRAPH_PLATFORM_URL;
  if (!platformUrl) {
    return new Response(
      JSON.stringify({ error: "LANGGRAPH_PLATFORM_URL not configured" }),
      { status: 502, headers: { "Content-Type": "application/json" } }
    );
  }

  // FIXME: threadId lookup — need mechanism to map runId → threadId
  // Option A: Store run metadata in session/cookies
  // Option B: Query LangGraph Platform to list runs, find threadId
  // Option C: Pass threadId as query param (less secure, but simple for v1.5-04)
  const threadId = request.nextUrl.searchParams.get("threadId");
  if (!threadId) {
    return new Response(
      JSON.stringify({ error: "threadId query param required" }),
      { status: 400, headers: { "Content-Type": "application/json" } }
    );
  }

  try {
    const client = new LangGraphClient(platformUrl);
    
    // Stream from LangGraph Platform for this specific run
    // Note: Platform does NOT have a "resume" endpoint per runId
    // Instead, you stream ALL runs for a thread, or query a specific run
    // RESEARCH GAP: Exact endpoint for streaming a specific run TBD
    // Provisional: POST /threads/{threadId}/runs/{runId}/stream (unverified)
    const upstreamResponse = await client.getRun(threadId, params.runId);
    
    // For now, return run metadata (not streaming)
    // Once endpoint verified, replace with streaming logic
    return new Response(JSON.stringify(upstreamResponse), {
      status: 200,
      headers: { "Content-Type": "application/json" },
    });
  } catch (err) {
    console.error("[open-swe/stream] error:", err);
    return new Response(
      JSON.stringify({ error: "Failed to stream run" }),
      { status: 500, headers: { "Content-Type": "application/json" } }
    );
  }
}
```

### Pattern 2: EventSource React Hook (useRunStream)

**What:** A custom React hook that opens an EventSource connection to the SSE endpoint, parses events, and accumulates them in state.

**When to use:** Whenever you need to consume SSE in React and want auto-reconnection + lifecycle management.

**Example:**
```typescript
// apps/open-swe/lib/hooks/useRunStream.ts
// Source: AI SDK pattern (useDeepAgentsChat uses fetch-based; EventSource is simpler)

import { useEffect, useRef, useState, useCallback } from "react";

type StreamEvent = 
  | { type: "text-delta"; delta: string }
  | { type: "tool-input-start"; toolCallId: string; toolName: string; input: Record<string, unknown> }
  | { type: "tool-output-available"; toolCallId: string; output: unknown };

export interface UseRunStreamOptions {
  runId: string;
  threadId: string;
  endpoint: string; // e.g., "/api/open-swe/runs/[runId]/stream"
  enabled?: boolean;
}

export function useRunStream({
  runId,
  threadId,
  endpoint,
  enabled = true,
}: UseRunStreamOptions) {
  const [events, setEvents] = useState<StreamEvent[]>([]);
  const [status, setStatus] = useState<"idle" | "connecting" | "streaming" | "error" | "done">("idle");
  const [error, setError] = useState<Error | null>(null);
  const eventSourceRef = useRef<EventSource | null>(null);

  const connect = useCallback(() => {
    if (!enabled) return;

    setStatus("connecting");
    setError(null);

    const url = `${endpoint}?threadId=${threadId}`;
    const eventSource = new EventSource(url);

    eventSource.addEventListener("message", (event) => {
      try {
        const parsed = JSON.parse(event.data) as StreamEvent;
        setEvents((prev) => [...prev, parsed]);
        setStatus("streaming");
      } catch (err) {
        console.error("[useRunStream] failed to parse event:", event.data, err);
      }
    });

    eventSource.addEventListener("error", (event) => {
      console.error("[useRunStream] EventSource error:", event);
      const err = new Error("EventSource connection failed");
      setError(err);
      setStatus("error");
      eventSource.close();
    });

    // Optional: Listen for explicit end marker
    eventSource.addEventListener("done", () => {
      setStatus("done");
      eventSource.close();
    });

    eventSourceRef.current = eventSource;
  }, [enabled, endpoint, threadId]);

  // Open connection on mount (if enabled)
  useEffect(() => {
    connect();
    return () => {
      eventSourceRef.current?.close();
    };
  }, [connect]);

  const retry = useCallback(() => {
    eventSourceRef.current?.close();
    setEvents([]);
    setError(null);
    connect();
  }, [connect]);

  return { events, status, error, retry };
}
```

### Pattern 3: Tool Call State Management (useToolState)

**What:** A hook that tracks tool calls (pending → completed) and provides a map of tool_call_id → {pending, input, output}.

**When to use:** Whenever rendering a component that needs to show tool call state transitions.

**Example:**
```typescript
// apps/open-swe/lib/hooks/useToolState.ts
// Source: Custom pattern; tool-input-start + tool-output-available frames from openSweAdapter

import { useCallback, useMemo } from "react";

export interface ToolCallState {
  toolCallId: string;
  toolName: string;
  input: Record<string, unknown>;
  output?: unknown;
  status: "pending" | "completed";
}

export function useToolState(events: StreamEvent[]) {
  // Build map of tool calls as events arrive
  const toolState = useMemo(() => {
    const state = new Map<string, ToolCallState>();

    for (const event of events) {
      if (event.type === "tool-input-start") {
        state.set(event.toolCallId, {
          toolCallId: event.toolCallId,
          toolName: event.toolName,
          input: event.input,
          status: "pending",
        });
      } else if (event.type === "tool-output-available") {
        const existing = state.get(event.toolCallId);
        if (existing) {
          state.set(event.toolCallId, {
            ...existing,
            output: event.output,
            status: "completed",
          });
        }
      }
    }

    return state;
  }, [events]);

  return Array.from(toolState.values());
}
```

### Anti-Patterns to Avoid

- **Global EventSource Map:** Don't store `Map<runId, EventSource>` at module level. Each React component gets its own EventSource instance; browser isolation handles cleanup.
- **Manual Reconnection Logic:** EventSource handles reconnection automatically. Don't implement `setInterval(reconnect)`. Only implement retry UI button if needed.
- **Non-Serializable Event Types:** Keep StreamEvent as plain JSON-serializable objects. Don't store functions, Dates, or Map instances in event payloads.
- **Mixing Polling and Streaming:** Don't call GET /api/open-swe/runs/[runId] while streaming the same run. Use streaming for live output; polling for status checks only.

## Common Pitfalls

### Pitfall 1: threadId Lookup Complexity
**What goes wrong:** You need to map a client-facing runId to the threadId on the server, but there's no obvious place to store this mapping.

**Why it happens:** LangGraph Platform organizes runs under threads, but apps/open-swe UI may expose runs without exposing threads. The mapping decision was deferred in v1.5-03-01.

**How to avoid:** 
- **Option A (simplest for v1.5-04):** Pass threadId as query param in the stream endpoint URL. Accept the security tradeoff (threadId is not secret, but leaks context structure).
- **Option B (more robust):** Store run metadata (including threadId) in-memory or session when run is created (POST /api/open-swe/runs), then look it up when streaming.
- **Option C (future):** Add a LangGraphClient method to list all threads + runs and search for a runId.

**Warning signs:** Seeing "FIXME: threadId lookup" or "undefined" errors in run detail page.

### Pitfall 2: EventSource Doesn't Re-Open Across Browser Tab Focus Loss
**What goes wrong:** User navigates away from the run detail tab, then returns. SSE appears stalled (no new events).

**Why it happens:** EventSource handles network errors transparently, but if the client browser closes the connection (tab blur), reconnection is not automatic. This is a limitation of the EventSource API, not a bug.

**How to avoid:**
- **For v1.5-04:** Document that users need to manually refresh or click a "retry" button after switching tabs. Out of scope for this phase.
- **For v1.5-06+:** Implement stream reconnection (ENABLE_STREAM_RECONNECT pattern from v1.3-03) with resumeId support.

**Warning signs:** Events stop arriving after tab blur/focus; manual page reload fixes it.

### Pitfall 3: Tool Call Card Shows Pending Forever
**What goes wrong:** A tool-input-start frame arrives, but tool-output-available never arrives. Card shows "pending" indefinitely.

**Why it happens:** Either the upstream tool execution failed silently, or tool_call_id mismatch (input frame has id "abc", output frame has id "def"). The openSweAdapter's tool_call_id generation must be deterministic.

**How to avoid:**
- **Verify openSweAdapter logic:** Ensure tool_call_id = `${runId}-${toolName}-${counter}` is consistent between on_tool_start and on_tool_end handlers.
- **Add timeout UI:** Show "Tool took too long" after 30s pending state.
- **Log tool call IDs:** Debug by logging which IDs are sent to the client; compare with upstream LangGraph events.

**Warning signs:** Some tool cards stuck pending; others complete normally; IDs don't match in logs.

### Pitfall 4: Concurrent Tabs Leak Events to Wrong Run
**What goes wrong:** User opens /dashboard/runA and /dashboard/runB in two tabs. Events from runA appear on runB's page.

**Why it happens:** You're using a shared global EventSource Map or accumulating events in a Redux store keyed only by toolName (not toolCallId).

**How to avoid:**
- **Use isolated component state:** Each RunDetail component instance owns its own EventSource + state. No shared global state.
- **Key by toolCallId, not toolName:** Tool calls are keyed by ID, which is globally unique across all runs. Store state in a Map<toolCallId, ToolCallState>.
- **Verify in tests:** Write a test that opens two simulated runs in parallel; assert events don't cross.

**Warning signs:** Switching between tabs shows mixed events; tool count is wrong; race conditions in console logs.

### Pitfall 5: Memory Leak: EventSource Never Closes
**What goes wrong:** User navigates away from run detail page, but EventSource connection persists. Over time, memory accumulates.

**Why it happens:** Component unmounts without closing the EventSource (missing cleanup in useEffect).

**How to avoid:**
- **Always return cleanup:** `useEffect(..., [deps]) { ... return () => eventSourceRef.current?.close(); }`
- **Test unmount:** Write test that mounts, then unmounts the hook; verify EventSource.close() is called.

**Warning signs:** DevTools network tab shows persistent "GET /api/open-swe/runs/[runId]/stream" connections even after navigation; browser memory grows over time.

### Example 1: SSE Route Handler Pattern
```typescript
// Source: packages/server/src/handler.ts (createDeepAgentsHandler)
// Applied to: apps/open-swe/app/api/open-swe/runs/[runId]/stream/route.ts

import { NextRequest, NextResponse } from "next/server";
import { createDeepAgentsHandler } from "@deepagents-nextjs/server";
import { openSweAdapter } from "@deepagents-nextjs/server";

export const dynamic = "force-dynamic";

export async function GET(
  request: NextRequest,
  { params }: { params: { runId: string } }
): Promise<Response> {
  const platformUrl = process.env.LANGGRAPH_PLATFORM_URL;
  if (!platformUrl) {
    return new Response("LANGGRAPH_PLATFORM_URL not configured", {
      status: 502,
      headers: { "Content-Type": "text/plain" },
    });
  }

  const threadId = request.nextUrl.searchParams.get("threadId");
  if (!threadId) {
    return new Response("threadId query param required", {
      status: 400,
      headers: { "Content-Type": "text/plain" },
    });
  }

  try {
    // Fetch SSE stream from LangGraph Platform
    const controller = new AbortController();
    const timeout = setTimeout(() => controller.abort(), 30_000);
    
    const upstreamUrl = `${platformUrl}/threads/${threadId}/runs/${params.runId}/stream`;
    const upstreamResponse = await fetch(upstreamUrl, {
      method: "GET",
      signal: controller.signal,
      headers: {
        "Content-Type": "application/json",
        ...(process.env.LANGGRAPH_API_KEY && {
          Authorization: `Bearer ${process.env.LANGGRAPH_API_KEY}`,
        }),
      },
    });
    
    clearTimeout(timeout);

    if (!upstreamResponse.ok) {
      return new Response("Failed to fetch from LangGraph Platform", {
        status: upstreamResponse.status,
        headers: { "Content-Type": "text/plain" },
      });
    }

    if (!upstreamResponse.body) {
      return new Response(null, { status: 204 });
    }

    // Apply transforms (openSweAdapter normalizes to AI SDK v6)
    const encoder = new TextEncoder();
    const decoder = new TextDecoder();
    const transformedStream = new ReadableStream<Uint8Array>({
      async start(controller) {
        const reader = upstreamResponse.body!.getReader();
        try {
          while (true) {
            const { done, value } = await reader.read();
            if (done) {
              controller.close();
              break;
            }

            const chunk = decoder.decode(value, { stream: true });
            // TODO: Apply openSweAdapter transforms here
            // For now, pass through as-is
            controller.enqueue(encoder.encode(chunk));
          }
        } catch (err) {
          console.error("[stream] error:", err);
          controller.error(err);
        }
      },
    });

    return new NextResponse(transformedStream, {
      status: 200,
      headers: {
        "Content-Type": "text/event-stream",
        "Cache-Control": "no-cache, no-transform",
        "X-Accel-Buffering": "no",
      },
    });
  } catch (err) {
    console.error("[stream] error:", err);
    return new Response("Internal server error", {
      status: 500,
      headers: { "Content-Type": "text/plain" },
    });
  }
}
```

### Example 2: EventSource React Hook
```typescript
// Source: Custom pattern; EventSource API (Web API spec)

import { useEffect, useRef, useState } from "react";

export function useEventStream(url: string) {
  const [messages, setMessages] = useState<string[]>([]);
  const [isConnected, setIsConnected] = useState(false);
  const [error, setError] = useState<Error | null>(null);
  const eventSourceRef = useRef<EventSource | null>(null);

  useEffect(() => {
    const eventSource = new EventSource(url);

    eventSource.addEventListener("open", () => {
      setIsConnected(true);
      setError(null);
    });

    eventSource.addEventListener("message", (event) => {
      try {
        // Parse SSE data: line
        const data = JSON.parse(event.data);
        setMessages((prev) => [...prev, JSON.stringify(data)]);
      } catch (err) {
        console.error("Failed to parse SSE message:", err);
      }
    });

    eventSource.addEventListener("error", () => {
      setError(new Error("EventSource connection failed"));
      setIsConnected(false);
      eventSource.close();
    });

    eventSourceRef.current = eventSource;

    return () => {
      eventSource.close();
    };
  }, [url]);

  return { messages, isConnected, error };
}
```

## Open Questions

1. **LangGraph Platform Stream Endpoint for Specific Run**
   - What we know: LangGraph Platform has `POST /threads/{threadId}/runs/stream` (streams all runs for a thread) and `GET /threads/{threadId}/runs/{runId}` (fetches run metadata)
   - What's unclear: Is there a `GET /threads/{threadId}/runs/{runId}/stream` endpoint to stream a single run's events?
   - Recommendation: Verify by inspecting LangGraph Platform docs or testing with a live deployment in v1.5-04 implementation. If endpoint doesn't exist, may need to stream all runs and filter client-side (less efficient).

2. **ThreadId Persistence Across Sessions**
   - What we know: v1.5-03 POST /api/open-swe/runs creates a run + returns run_id, but doesn't expose threadId
   - What's unclear: Should threadId be stored in session cookies? Returned to client? Passed as query param?
   - Recommendation: Keep simple for v1.5-04: pass threadId as query param (accept the UX tradeoff). Implement proper session storage in v1.5-05+ if needed.

3. **Tool Call ID Determinism Across Stream Segments**
   - What we know: openSweAdapter generates tool_call_id = `${runId}-${toolName}-${counter}` 
   - What's unclear: Is this ID stable if the SSE stream is resumed/reconnected mid-run?
   - Recommendation: Verify in tests that counter state is maintained correctly across multiple HTTP requests to the same run.

4. **Memory Limits for Long-Running Streams**
   - What we know: Each EventSource connection consumes ~10KB base + message buffer
   - What's unclear: At what number of concurrent streams does a Vercel serverless function hit memory limits?
   - Recommendation: Not critical for v1.5-04 (small pilot scope). Monitor in production.
