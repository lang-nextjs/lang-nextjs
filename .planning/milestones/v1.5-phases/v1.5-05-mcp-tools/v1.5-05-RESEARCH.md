# Phase v1.5-05: MCP Tools - Research

**Researched:** 2026-05-05
**Domain:** Model Context Protocol (MCP) tool integration with LangGraph Platform proxy
**Confidence:** HIGH

## Summary

Phase v1.5-05 extends the existing `@deepagents-nextjs/mcp` server to add four new tools that enable LLM agents to programmatically trigger, inspect, and manage open-swe coding runs. The tools proxy to the REST API endpoints defined in `apps/open-swe`, which in turn call the LangGraph Platform. Each tool follows the MCP v1.12.0 SDK pattern established in the existing codebase: immediate response without polling, JSON-RPC 2.0 message semantics, and stateless tool handlers that make direct HTTP requests to the backend.

The implementation is straightforward because:
1. The APIs already exist (`POST /api/open-swe/runs`, `GET /api/open-swe/runs`, and future endpoints for get-run-status and cancel-run)
2. The MCP SDK pattern is proven in the existing five tools (chat, list_api_keys, generate_api_key, revoke_api_key, health)
3. Tool handlers are stateless functions that forward HTTP requests — no state management or async orchestration required
4. Zod is already available for input schema definition
5. The open-swe `Run` and `CreateRunRequest` types are already defined in `apps/open-swe/lib/types.ts`

**Primary recommendation:** Add four tools to `packages/mcp/src/index.ts` following the existing tool pattern: validate/coerce inputs with Zod, make a single HTTP request to the corresponding app API endpoint, return the response as JSON-stringified text content in the tool result.

### Pattern 1: Immediate Response (No Polling)

**What:** MCP tool handlers return immediately with current state; they do NOT wait for the LangGraph Platform to process the request asynchronously.

**When to use:** All four open-swe tools follow this pattern. The agent's next decision (which run to inspect, whether to trigger a new task) depends on a snapshot of the current state, not the completion of a background job.

**Example:**
```typescript
// Source: phase v1.5-05 specification + existing index.ts pattern
server.tool(
  "trigger_task",
  "Trigger a new open-swe coding task and receive the run_id immediately",
  { task: z.string().describe("The coding task description") },
  async ({ task }) => {
    const res = await backendRequest(
      `${apiUrl}/api/open-swe/runs`,
      {
        method: "POST",
        body: JSON.stringify({ task }),
      }
    );
    const run = (await res.json()) as { run_id: string; status: string; created_at: string; task: string };
    return {
      content: [
        {
          type: "text" as const,
          text: JSON.stringify(run, null, 2),
        },
      ],
    };
  }
);
```

### Pattern 2: JSON Result Formatting

**What:** All tool results are returned as single text content items containing pretty-printed JSON. This matches the existing chat tool pattern and makes results readable to the LLM.

**When to use:** For all structured results (runs, status objects, lists). Unstructured error messages use plain text.

**Example:**
```typescript
// Correct: structured result as JSON string
return {
  content: [
    {
      type: "text" as const,
      text: JSON.stringify(run, null, 2),  // Pretty-printed
    },
  ],
};

// Not used: raw object or `structuredContent` field (not in existing pattern)
```

### Pattern 3: Error Handling with isError Flag

**What:** Tool execution errors (validation, API failure) return `isError: true` in the result. Protocol errors (malformed requests) throw and propagate as JSON-RPC errors.

**When to use:** 
- Input validation error → return `{ content: [...], isError: true }`
- Network failure or 500 from platform → throw with descriptive message
- 4xx validation from platform → return `{ content: [...], isError: true }` or throw depending on semantics

**Example:**
```typescript
// Validation error — return, don't throw (agent can retry with different input)
if (!runId?.trim()) {
  return {
    content: [{ type: "text" as const, text: "runId is required" }],
    isError: true,
  };
}

// Platform error (5xx or network) — throw (out of agent's control)
if (!res.ok) {
  const body = await res.text().catch(() => "");
  throw new Error(`open-swe API ${res.status}: ${body}`);
}
```

### Pattern 4: Stateless Handler Closure

**What:** Tool handlers are closures over `apiUrl` and `apiKey` from `createDeepAgentsMcpServer` options. No module-level state or caching.

**When to use:** All four tools follow this pattern for security and testability.

**Example:**
```typescript
export function createDeepAgentsMcpServer(options: DeepAgentsMcpOptions) {
  const { apiUrl, apiKey } = options;
  const normalizedApiUrl = apiUrl.replace(/\/+$/, "");

  // Each tool handler closes over normalizedApiUrl and apiKey
  server.tool(
    "trigger_task",
    "...",
    { task: z.string() },
    async ({ task }) => {
      // Handler only uses captured variables, no module-level state
      const res = await backendRequest(`${normalizedApiUrl}/api/open-swe/runs`, {
        method: "POST",
        body: JSON.stringify({ task }),
      });
      // ...
    }
  );
}
```

### Anti-Patterns to Avoid

- **Polling inside tool handler:** Do NOT have trigger_task wait for the run to complete before returning. The LLM should use list_runs and get_run_status if it needs to wait.
- **Module-level caches:** Do NOT store run state in a map at module level. Each tool invocation fetches fresh state from the API.
- **Throwing on 4xx platform errors:** Do NOT throw when the platform returns 422 or 400 — these are actionable feedback for the agent. Return isError:true instead.
- **Unstructured error text:** Do NOT return error messages as plain text without indicating isError:true. The agent needs the flag to know recovery is possible.
- **Custom HTTP retry logic:** Do NOT add retry loops in tool handlers. Failures should propagate immediately; agents can call list_runs to see the current state.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| MCP tool registry and dispatch | Custom JSON-RPC router | @modelcontextprotocol/sdk McpServer class | SDK handles all JSON-RPC plumbing, capability negotiation, tool list caching, error codes — rolling custom loses compliance and complexity |
| Input validation and schema inference | Manual type guards + validation | Zod with `.describe()` for schema generation | Zod produces JSON Schema automatically; project already uses Zod for all 5 existing tools; zero-cost abstraction |
| HTTP request to backend | Raw fetch with manual headers/retry | backendRequest helper (existing in index.ts) | Centralized auth header injection, error classification, timeout handling — don't duplicate across new tools |
| Tool result formatting | Custom content object construction | Existing content/isError pattern (proven in 5 tools) | Format is standardized in MCP spec; existing pattern is idiomatic and tested |
| Run type definitions | TypeScript interfaces in MCP package | Import Run from apps/open-swe/lib/types.ts | Types are already defined, will change with open-swe implementation — importing prevents duplication |

**Key insight:** The MCP SDK and Zod layers remove almost all complexity from tool development. Each tool is a 15–30 line handler that validates input, makes one HTTP request, and returns formatted JSON. Custom logic only adds bugs.

## Common Pitfalls

### Pitfall 1: Tool Blocking on Async Operations

**What goes wrong:** `trigger_task` is implemented to wait for the run to reach "completed" or "failed" status before returning. The tool handler becomes a slow polling loop (30–300 seconds), blocking the LLM while the tool executes.

**Why it happens:** Developers conflate "trigger a task" (synchronous, immediate) with "wait for task completion" (asynchronous, long-lived). The agent should trigger and then poll via list_runs/get_run_status if it needs the result.

**How to avoid:** Tool handlers return immediately after the API response. Never add `while (run.status !== "completed")` loops. Test with a mock backend that returns a run with status "pending" to catch this early.

**Warning signs:**
- Tool handlers have `setTimeout` or `setInterval` calls
- Any tool takes > 5 seconds to execute
- Tests mock a delayed response or use `.delay()` on fetch mock

### Pitfall 2: Throwing on 4xx Validation Errors

**What goes wrong:** When trigger_task is called with an empty task string, the API returns 422. The tool handler throws, causing the MCP JSON-RPC error to propagate to the LLM. The LLM sees "error" and cannot retry with different input.

**Why it happens:** Developers assume all API errors should propagate. But 4xx errors are input validation feedback that the agent can act on (try again with valid input).

**How to avoid:** Classify errors: 4xx → return isError:true, 5xx/network → throw. Return actionable feedback in the text content so the agent knows what went wrong.

**Warning signs:**
- Tool result has `isError: true` but content is empty or generic
- Any 4xx response throws instead of returning a result
- Tests don't cover 422, 400, or other client errors separately

### Pitfall 3: Sharing Module-Level State Between Invocations

**What goes wrong:** A cache map `const runCache = new Map()` is added to store recently-fetched runs. Two concurrent tool invocations overwrite the cache, causing the second caller to see stale or corrupted data.

**Why it happens:** Developers assume tool handlers are bound to a single request lifecycle, but MCP servers are long-lived and handle many concurrent requests.

**How to avoid:** Tool handlers are pure functions of their inputs and environment variables (apiUrl, apiKey). No module-level state except constants. Each invocation fetches from the API.

**Warning signs:**
- Variables declared at module level inside createDeepAgentsMcpServer (outside the closure)
- Any use of `.get()` or `.set()` on a persistent map or cache
- Tests that mock a handler and expect subsequent handlers to see updated state

### Pitfall 4: Missing runId Validation Before URL Construction

**What goes wrong:** `get_run_status` is called with `runId: ""`. The handler constructs `GET /api/open-swe/runs/` (trailing slash, empty segment). The backend treats this as "list runs" instead of "get run", returning a list instead of a single run. The LLM tries to parse a list as a single run and fails silently.

**Why it happens:** Developers skip input guards, assuming Zod validation is enough. But Zod can only validate the type (string exists), not the format (non-empty, valid ID).

**How to avoid:** Add guards after Zod validation: `if (!runId?.trim())` before constructing the URL. Return isError:true with a message.

**Warning signs:**
- Input validation is ONLY Zod; no additional guards in handler
- URL construction uses template literals without checks
- Tests don't cover empty string or whitespace-only inputs

### Pitfall 5: Forgetting to Normalize apiUrl in New Tools

**What goes wrong:** `trigger_task` constructs URL as `${apiUrl}/api/open-swe/runs` but `apiUrl` has a trailing slash: `http://localhost:3000/`. Result: `http://localhost:3000//api/open-swe/runs` (double slash).

**Why it happens:** New tools don't reference the normalization that happens once at the top of createDeepAgentsMcpServer. Copy-paste URL construction across tools without using the normalized version.

**How to avoid:** Always use `normalizedApiUrl` (computed once at the start of the factory) in all tool handlers. Add a comment at the top of each handler: `// Using normalizedApiUrl which strips trailing slashes`.

**Warning signs:**
- Multiple tools construct URLs differently
- apiUrl normalization only in one tool, not all
- Tests pass with `http://localhost:3000` but fail with `http://localhost:3000/`

## Code Examples

Verified patterns from official sources and existing codebase:

### trigger_task Tool

```typescript
// Source: MCP SDK v1.12.0 spec + existing 5-tool pattern + apps/open-swe API
server.tool(
  "trigger_task",
  "Trigger a new open-swe coding task. Returns immediately with the run_id — does not wait for the run to complete.",
  {
    task: z.string().describe("The coding task description (e.g., 'Fix the login button width on mobile')"),
  },
  async ({ task }) => {
    const url = `${normalizedApiUrl}/api/open-swe/runs`;
    
    if (!task?.trim()) {
      return {
        content: [{ type: "text" as const, text: "Task is required and cannot be empty or whitespace" }],
        isError: true,
      };
    }

    try {
      const res = await backendRequest(url, {
        method: "POST",
        body: JSON.stringify({ task: task.trim() }),
      });

      const run = (await res.json()) as {
        run_id: string;
        status: string;
        created_at: string;
        task: string;
      };

      return {
        content: [
          {
            type: "text" as const,
            text: JSON.stringify(run, null, 2),
          },
        ],
      };
    } catch (err) {
      if (err instanceof Error && err.name === "AbortError") {
        return {
          content: [{ type: "text" as const, text: "Request timed out" }],
          isError: true,
        };
      }
      throw err;
    }
  }
);
```

### Test Categories for Each Tool

Each tool requires tests for:

1. **Success path:** Happy case with valid input, 200 response from API, correct JSON output
2. **Input validation:** Empty/whitespace-only inputs → isError:true, no fetch call
3. **Network error:** fetch rejects with AbortError → isError:true with timeout message
4. **Platform error:** API returns 502 → throw (propagates as JSON-RPC error)
5. **Response parsing:** API returns valid JSON → correctly parsed and stringified

Example test structure (already established in index.test.ts for existing tools):

```typescript
describe("trigger_task tool", () => {
  beforeEach(() => {
    vi.restoreAllMocks();
  });

  it("returns run_id immediately after POST to /api/open-swe/runs", async () => {
    vi.spyOn(globalThis, "fetch").mockResolvedValue(
      makeOkResponse({ run_id: "run-123", status: "pending", created_at: "...", task: "..." })
    );
    const server = createDeepAgentsMcpServer({ apiUrl: BASE_URL, apiKey: API_KEY });
    const result = await getTools(server).trigger_task.handler({ task: "Fix login button" });
    
    const parsed = JSON.parse(result.content[0].text);
    expect(parsed.run_id).toBe("run-123");
    expect(result.isError).toBeFalsy();

    vi.spyOn(globalThis, "fetch").mockResolvedValue(

    );

    await expect(
      getTools(server).trigger_task.handler({ task: "test" })
    ).rejects.toThrow("502");
  });

  // ... 3 more tests
```

## State of the Art

| Old Approach | Current Approach | When Changed | Impact |
|--------------|------------------|--------------|--------|
| MCP tool handlers use separate HTTP clients with retries and caching | Stateless handlers with single centralized `backendRequest` helper | v1.0 (MCP package init) | Reduced code duplication, improved testability, consistent auth/timeout |
| Tool input validation via manual type guards | Zod + JSON Schema inference via `z.describe()` | v1.0 (React package generics) | Automatic schema generation, compile-time type safety, zero runtime cost |
| Tool results return raw objects or custom content shapes | Standardized `{ content: [{type:"text", text: JSON.stringify(...)}], isError?: boolean }` | v1.0 (existing 5 tools) | MCP spec compliant, readable to LLMs, debuggable errors |
| Each tool independently validates and normalizes apiUrl | Single `normalizedApiUrl` computed at factory level | v1.0 (index.ts existing pattern) | DRY, prevents double-slash bugs, easier testing |

**Deprecated/outdated:**
- None. MCP v1.12.0 is current (released 2025) and patterns are stable.

## Open Questions

1. **GET /api/open-swe/runs/{runId} endpoint existence**
   - What we know: apps/open-swe/route.ts defines `POST /api/open-swe/runs` and `GET /api/open-swe/runs` (list all)
   - What's unclear: Does `GET /api/open-swe/runs/[runId]` exist? If not, is it being added in this phase or later?
   - Recommendation: Phase plan must clarify. If endpoint does not exist, get_run_status tool should stub with `throw Error('not implemented')` until Phase v1.5-06 or later adds it.

2. **POST /api/open-swe/runs/{runId}/cancel endpoint existence**
   - What we know: REQUIREMENTS.md specifies MCP-04 requirement but no corresponding API documented
   - What's unclear: Is the cancel endpoint being added to apps/open-swe in this phase? Or does cancel_run proxy directly to LangGraph Platform?
   - Recommendation: Phase plan must clarify. If endpoint does not exist, cancel_run tool should stub with `throw Error('not implemented')` until implemented.

3. **Error response format from LangGraph Platform**
   - What we know: apps/open-swe/langgraph-client.ts catches errors and throws PlatformError, but exact error body format is unknown
   - What's unclear: What does the platform return in error body? Is it JSON with an error message, or plain text?
   - Recommendation: Phase plan should verify with curl against the local LangGraph Platform server; tests should mock both JSON and text error responses.

4. **Timeout value for tool requests**
   - What we know: platformFetch in langgraph-client.ts uses 10_000ms; backendRequest in MCP package has no explicit timeout (relies on fetch abort)
   - What's unclear: Should MCP tools use the same 10s timeout, or a different value? Should it be configurable via DeepAgentsMcpOptions?
   - Recommendation: Use 10s to match the platform client. If configurable timeout is needed, defer to v1.5-06 or later.
