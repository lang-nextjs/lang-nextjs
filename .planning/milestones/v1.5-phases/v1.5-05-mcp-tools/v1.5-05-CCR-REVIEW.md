## PLAN EVALUATION

### Plan v1.5-05-01: Wave 0 RED Test Stubs (21 tests)

**Verdict: APPROVE** ✅

#### Strengths
1. **Correct test count and distribution**: 6 tests for trigger_task, 3 for list_runs, 6 for get_run_status, 6 for cancel_run = 21 tests. Distribution matches existing tool complexity patterns.

2. **Proper test structure**: All four describe blocks use the established pattern:
   - `beforeEach(() => { vi.restoreAllMocks(); })` — correct
   - Uses existing helpers: `getTools()`, `makeOkResponse()`, `makeErrorResponse()`, `BASE_URL`, `API_KEY`
   - Tests mock `globalThis.fetch` directly (proven pattern from existing tools)

3. **Comprehensive coverage of critical paths**:
   - **trigger_task**: Success (run_id return), empty string validation, whitespace validation, 502 error, trailing slash normalization, AbortError timeout
   - **list_runs**: Success (returns array), empty array edge case, 502 error
   - **get_run_status**: Success (returns run object), empty runId validation, whitespace validation, **URL encoding (prevents path injection)**, 502 error, AbortError timeout
   - **cancel_run**: Success (returns cancelled run), empty runId validation, whitespace validation, **endpoint verification (POST to /cancel)**, 502 error, AbortError timeout

4. **Security consideration**: Tests explicitly verify URL encoding (`expect(fetchCall).toContain("run%2Fevil")`) for get_run_status — prevents path traversal attacks.

5. **Error handling patterns align with existing tools**:
   - Empty/whitespace inputs → `isError: true` (no fetch call)
   - Network AbortError → `isError: true` with "timeout" message
   - 502 Platform errors → throw (propagates as MCP JSON-RPC error)
   - This matches the health tool pattern from existing index.ts

6. **TDD compliance**: Tests define the contract before implementation — each test references a tool that doesn't exist in index.ts yet (verified by the pre-flight check `grep trigger_task packages/mcp/src/index.ts` should return 0).

#### Issues
**None critical.** The tests are RED by design (tools don't exist). Plan correctly notes that tests reference `getTools(server).trigger_task.handler({})`, which will fail with "cannot read properties of undefined" until the tools are registered in Wave 1.

#### Edge Cases Properly Covered
- ✅ Empty string + whitespace-only for string parameters
- ✅ AbortError (timeout) vs. other errors (throw vs. isError)
- ✅ URL encoding for path parameters (get_run_status, cancel_run)
- ✅ 502 backend errors propagate as throws
- ✅ Successful JSON responses are parsed and re-stringified for MCP content

#### Minor Observations
- Test uses `async ({ task }) => { ... }` — correct Zod destructuring
- Tests check `expect(result.isError).toBeFalsy()` for success, `expect(result.isError).toBe(true)` for error cases — consistent pattern
- List_runs has no parameters (`{}`) — correct, aligns with list_api_keys tool

### Plan v1.5-05-02: GREEN Implementation (4 MCP tools + 2 API routes)

**Verdict: APPROVE with minor clarifications needed (non-blocking)** ✅

#### Strengths

1. **Task 1: trigger_task + list_runs MCP tools**
   - ✅ Correct tool registration pattern using `server.tool()`
   - ✅ Zod schema matches test expectations: `{ task: z.string().describe(...) }` for trigger_task, `{}` for list_runs
   - ✅ Uses `backendRequest("/api/open-swe/runs", { method: "POST" })` for trigger_task, `method: "GET"` for list_runs
   - ✅ Input validation: `if (!task?.trim()) { return { content: [...], isError: true } }` — matches Wave 0 test expectations
   - ✅ AbortError handling: `if (err instanceof Error && err.name === "AbortError") { return { content: [...], isError: true } }` — correct
   - ✅ 502 errors naturally throw via `backendRequest` (already throws on non-ok), so tests that expect `rejects.toThrow("502")` will pass
   - ✅ Returns JSON-stringified run object: `JSON.stringify(run, null, 2)` — matches test expectation
   - ✅ Does NOT wait for run to complete — returns immediately from POST response ✅ (MCP-01 satisfied)

2. **Task 2: get_run_status + cancel_run MCP tools + API routes**
   
   **GET /api/open-swe/runs/[runId] route (NEW):**
   - ✅ Correct path: `apps/open-swe/app/api/open-swe/runs/[runId]/route.ts` (directory exists per `ls` output)
   - ✅ Correct pattern: `async function GET(_request, { params })` with `const { runId } = await params`
   - ✅ Environment check: `if (!platformUrl) { return 502 }` — matches POST /api/open-swe/runs pattern
   - ✅ Calls `getRun(runId, platformUrl)` helper (NEW, needs to be added to langgraph-client.ts)
   - ✅ Error handling mirrors POST route: PlatformError with status >= 500 → 502, AbortError → 502, other errors → 500
   - ✅ Returns single run object as JSON — correct

   **POST /api/open-swe/runs/[runId]/cancel route (NEW):**
   - ✅ Correct path: `apps/open-swe/app/api/open-swe/runs/[runId]/cancel/route.ts` (new directory)
   - ✅ Correct pattern: `async function POST(_request, { params })` with params destructuring
   - ✅ Calls `cancelRun(runId, platformUrl)` helper (NEW, needs to be added to langgraph-client.ts)
   - ✅ Same error handling as GET route — consistent
   - ✅ Returns updated run object (with status = "failed" or "cancelled") — correct

   **langgraph-client.ts additions (implied):**
   - Plan correctly notes that `getRun` and `cancelRun` functions must be added
   - Should follow existing pattern: use `platformFetch`, make headers with apiKey, check `response.ok`, throw `PlatformError` on non-ok
   - Plan notes: "LangGraph Platform cancel endpoint is typically `POST /runs/{runId}/cancel`" — correct assumption

   **MCP tools in packages/mcp/src/index.ts (get_run_status + cancel_run):**
   - ✅ Correct tool registration: `server.tool("get_run_status", ...)`
   - ✅ Schema validation: `{ runId: z.string().describe(...) }` — matches tests
   - ✅ Input validation: `if (!runId?.trim()) { return { content: [...], isError: true } }` — matches tests
   - ✅ URL encoding: `encodeURIComponent(runId.trim())` — matches test expectation `expect(fetchCall).toContain("run%2Fevil")`
   - ✅ Endpoint: `/api/open-swe/runs/${encodeURIComponent(runId.trim())}` — correct
   - ✅ AbortError handling: same as trigger_task — correct
   - ✅ cancel_run identical structure but POSTs to `/api/open-swe/runs/${encodeURIComponent(runId.trim())}/cancel` — correct
   - ✅ Neither tool waits for run to reach terminal state — return immediately (MCP-03, MCP-04 satisfied)

3. **Correctness Against Existing Pattern**
   - All four tools follow the backendRequest pattern established in the existing 5 tools (chat, list_api_keys, generate_api_key, revoke_api_key, health)

   - All return `{ content: [{ type: "text" as const, text: JSON.stringify(...) }], isError?: boolean }` ✅
   - All validate input with Zod and return `isError: true` for invalid inputs ✅
