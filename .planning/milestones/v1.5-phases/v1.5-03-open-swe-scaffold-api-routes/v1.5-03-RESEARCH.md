# Phase v1.5-03: apps/open-swe Scaffold + API Routes - Research

**Researched:** 2026-05-04
**Domain:** Next.js App Router API routes, LangGraph Platform client integration, REST API design
**Confidence:** MEDIUM-HIGH

## Summary

Phase v1.5-03 scaffolds a new Next.js application (`apps/open-swe`) with two REST API endpoints that interface with a locally-running LangGraph Platform server. The dashboard allows developers to submit coding tasks and retrieve run status summaries without requiring real-time streaming (streaming support ships in v1.5-04).

The critical design constraint is that **the dashboard is NOT a LangGraph Platform deployment itself** — it is a separate Next.js application that acts as a client to a locally-running LangGraph Platform server. This follows the architecture established in v1.1-01 (reference backends) where the Next.js app proxies to an external backend via REST.

**Primary recommendation:** Scaffold `apps/open-swe` as a Next.js 15 App Router app with two stateless API routes (`POST /api/open-swe/runs` and `GET /api/open-swe/runs`) that proxy HTTP calls to the local LangGraph Platform server. Use the same error-handling pattern (fail-open, explicit status codes) as `apps/example/app/api/chat/stream/route.ts`. Do NOT initialize a LangGraph graph in this app — all agent execution happens in the LangGraph Platform server process.

### Pattern 1: LangGraph Platform HTTP Client
**What:** Thin wrapper around native `fetch()` that abstracts LangGraph Platform HTTP endpoints and handles error responses with explicit status codes.
**When to use:** All outbound requests to the Platform must go through this client for consistency, error handling, and future testability.
**Example:**
```typescript
// lib/langgraph-client.ts
interface RunRequest {
  assistant_id: string; // or graph_id, depends on Platform version
  input: { task: string };
}

interface RunResponse {
  run_id: string;
  status: "pending" | "running" | "completed" | "failed";
  created_at: string;
}

export async function createRun(
  req: RunRequest,
  platformUrl: string
): Promise<RunResponse> {
  const url = new URL("/api/threads", platformUrl);
  // OR: /api/assistants/{id}/runs depending on Platform API version
  
  const response = await fetch(url.toString(), {
    method: "POST",
    headers: {
      "Content-Type": "application/json",
      "X-Api-Key": process.env.LANGGRAPH_API_KEY || "",
    },
    body: JSON.stringify(req),
  });

  if (!response.ok) {
    throw new PlatformError(response.status, await response.text());
  }

  return response.json();
}

export async function listRuns(platformUrl: string): Promise<RunResponse[]> {
  const url = new URL("/api/runs", platformUrl);
  // Endpoint depends on Platform version
  
  const response = await fetch(url.toString(), {
    headers: {
      "X-Api-Key": process.env.LANGGRAPH_API_KEY || "",
    },
  });

  if (!response.ok) {
    throw new PlatformError(response.status, await response.text());
  }

  return response.json();
}
```

### Pattern 2: Error Handling — Explicit Status Codes
**What:** API routes catch exceptions and return explicit HTTP status codes rather than 500s. Mirrors `apps/example/app/api/chat/stream/route.ts` pattern.
**When to use:** Every POST and GET endpoint.
**Example:**
```typescript
// app/api/open-swe/runs/route.ts
export async function POST(request: NextRequest): Promise<Response> {
  try {
    const body = await request.json().catch(() => ({}));
    const { task } = body as { task?: string };

    if (!task || typeof task !== "string") {
      return new Response(
        JSON.stringify({ error: "Missing or invalid 'task' field" }),
        { status: 422, headers: { "Content-Type": "application/json" } }
      );
    }

    const platformUrl = process.env.LANGGRAPH_PLATFORM_URL;
    if (!platformUrl) {
      return new Response(
        JSON.stringify({
          error: "LANGGRAPH_PLATFORM_URL is not configured",
        }),
        { status: 502, headers: { "Content-Type": "application/json" } }
      );
    }

    const result = await createRun(
      { task, assistant_id: process.env.OPEN_SWE_ASSISTANT_ID! },
      platformUrl
    );
    return new Response(JSON.stringify(result), {
      status: 201,
      headers: { "Content-Type": "application/json" },
    });
  } catch (err) {
    if (err instanceof PlatformError && err.status >= 500) {
      return new Response(
        JSON.stringify({ error: "LangGraph Platform unreachable" }),
        { status: 502, headers: { "Content-Type": "application/json" } }
      );
    }
    // Log but don't leak internal error details
    console.error("POST /api/open-swe/runs error:", err);
    return new Response(
      JSON.stringify({ error: "Internal server error" }),
      { status: 500, headers: { "Content-Type": "application/json" } }
    );
  }
}

export async function GET(request: NextRequest): Promise<Response> {
  try {
    const platformUrl = process.env.LANGGRAPH_PLATFORM_URL;
    if (!platformUrl) {
      return new Response(
        JSON.stringify({
          error: "LANGGRAPH_PLATFORM_URL is not configured",
        }),
        { status: 502, headers: { "Content-Type": "application/json" } }
      );
    }

    const runs = await listRuns(platformUrl);
    return new Response(JSON.stringify(runs), {
      status: 200,
      headers: { "Content-Type": "application/json" },
    });
  } catch (err) {
    if (err instanceof PlatformError && err.status >= 500) {
      return new Response(
        JSON.stringify({ error: "LangGraph Platform unreachable" }),
        { status: 502, headers: { "Content-Type": "application/json" } }
      );
    }
    console.error("GET /api/open-swe/runs error:", err);
    return new Response(
      JSON.stringify({ error: "Internal server error" }),
      { status: 500, headers: { "Content-Type": "application/json" } }
    );
  }
}
```

### Anti-Patterns to Avoid
- **Storing graph state in the Next.js app:** The LangGraph Platform server owns state persistence. This app is stateless.
- **Calling LangGraph SDK classes directly:** SDK initialization adds overhead and couples this app to Python runtime. HTTP client is leaner and testable.
- **Using try/catch without status code mapping:** Unhandled errors become generic 500s. Be explicit: 422 for bad input, 502 for unreachable backend.
- **Hardcoding API paths:** Parameterize `LANGGRAPH_PLATFORM_URL` and `OPEN_SWE_ASSISTANT_ID` via environment variables for local dev and CI flexibility.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| HTTP client for LangGraph Platform | Custom fetch wrapper with retry logic | Native `fetch()` with explicit try/catch per route; retry policy is optional and belongs in a separate handler factory (like v1.0-02) | Retry adds complexity; start with simple fetch; v1.5-05+ can add MCP retry if needed |
| Request/response validation | Hand-rolled JSON schema checks | zod (if strict validation desired) or simple `typeof` checks (MVP) | Zod is overkill for two fields (task, run_id); start simple; add schema later if expanding API surface |
| Pagination for run list | Offset/limit from scratch | Rely on LangGraph Platform pagination (if available) or fetch all runs; paginate client-side if needed | Pagination is a phase v1.5-04 concern when UI needs it; not a v1.5-03 requirement |
| Rate limiting | Roll custom rate limiter | Rely on LangGraph Platform rate limits or add later; not required for local dev | Rate limiting is infra-level concern; local LangGraph Platform has no rate limit |

**Key insight:** This phase is about wiring two routes to an external Platform server. The Platform owns persistence, state, and retries. Keep this app thin.

## Common Pitfalls

### Pitfall 1: Confusing "apps/open-swe" with "open-swe agent"
**What goes wrong:** Developer assumes this app is the open-swe agent itself — tries to import LangGraph graph code, wire approval handlers, etc.
**Why it happens:** The phase name includes "open-swe" but the actual open-swe coding agent runs in a separate LangGraph Platform deployment (locally via docker compose or remotely).
**How to avoid:** This app is a CLIENT dashboard, not the agent. All agent code is in the LangGraph Platform server. This app only makes HTTP calls to POST /api/threads or equivalent.
**Warning signs:** If you find yourself importing files from langchain, langgraph, or agent/, stop — those belong in the Platform server, not here.

### Pitfall 2: Missing environment configuration
**What goes wrong:** Developer runs `pnpm dev` and gets "LANGGRAPH_PLATFORM_URL is undefined" — or the route proxies to `localhost:8000` but the Platform server isn't running.
**Why it happens:** Environment variables (`LANGGRAPH_PLATFORM_URL`, `LANGGRAPH_API_KEY`, `OPEN_SWE_ASSISTANT_ID`) are not documented or provided by a `.env.local` template.
**How to avoid:** 
  1. Create `.env.local.example` in `apps/open-swe` with required vars
  2. Document in README: "Set LANGGRAPH_PLATFORM_URL=http://localhost:8000"
  3. Return explicit 502 error if vars are missing (already in Pattern 2)
**Warning signs:** Route returns 502 silently; developer doesn't know what to configure.

### Pitfall 3: Treating LangGraph Platform stateless runs differently than thread-based runs
**What goes wrong:** Developer submits a task, gets a `run_id`, but then discovers the run_id doesn't persist and can't be queried later.
**Why it happens:** LangGraph Platform's stateless runs API differs from thread-based runs. The success criteria mention "run_id" and "status" fields, implying persistence, but stateless runs may not support this pattern the same way.
**How to avoid:**
  1. Verify with LangGraph Platform docs whether the target version supports persistent run metadata for stateless runs
  2. If stateless runs don't provide run_id + status persistently, fall back to thread-based API (create a thread, then create a run in that thread)
  3. Write a test that submits a task, gets a run_id, then queries GET /api/open-swe/runs and asserts the run_id appears with status
**Warning signs:** Test passes but follow-up GET request returns empty list; run_id is not queryable.

### Pitfall 4: Not handling the "Platform not running" case explicitly
**What goes wrong:** fetch() to the Platform hangs for 10+ seconds, causing dev server to appear frozen.
**Why it happens:** No timeout is set on the fetch call; if the Platform server is not running, the request blocks until system timeout (minutes).
**How to avoid:**
  1. Add explicit `AbortSignal` timeout to fetch calls (5–10 second timeout is reasonable for local dev)
  2. Catch timeout errors and return 502 (same as other Platform failures)
  3. Document this in the README
**Warning signs:** `pnpm dev` starts; make a POST request; dev server appears to freeze; kill the request after 30 seconds.

### Pitfall 5: Hardcoding port numbers
**What goes wrong:** Routes assume LangGraph Platform is on `localhost:8000`, but in Docker Compose it's `http://langgraph-platform:8000` or on a different port.
**Why it happens:** Hardcoded URLs are faster to iterate locally but break in containerized or different local setups.
**How to avoid:** Always parameterize via `LANGGRAPH_PLATFORM_URL` environment variable. Provide `.env.local.example` and document it clearly.
**Warning signs:** Test suite fails in CI but passes locally because CI uses different port.

### HTTP Proxy Client
```typescript
// Simple fetch wrapper
export class PlatformError extends Error {
  constructor(public status: number, message: string) {
    super(message);
    this.name = "PlatformError";
  }
}

export async function platformFetch(
  url: string,
  options: RequestInit = {}
): Promise<Response> {
  const controller = new AbortController();
  const timeoutId = setTimeout(() => controller.abort(), 10_000);

  try {
    const response = await fetch(url, {
      ...options,
      signal: controller.signal,
    });
    return response;
  } finally {
    clearTimeout(timeoutId);
  }
}
```

## Open Questions

1. **LangGraph Platform API endpoint structure**
   - What we know: Platform provides REST API for creating and listing runs; responses include run_id, status, created_at
   - What's unclear: Exact POST path (is it `/api/threads`, `/api/runs`, or `/api/assistants/{id}/runs`?); whether run_id is auto-generated or must be user-provided
   - Recommendation: Verify with a test fetch to a locally-running Platform server before finalizing the langgraph-client.ts implementation. Document the endpoint in README.

2. **Task input schema for open-swe agent**
   - What we know: Success criteria show "task description" as input
   - What's unclear: Does the Platform expect `{ input: { task: string } }` or a different schema? Does it expect assistant_id or graph_id?
   - Recommendation: Inspect the open-swe LangGraph agent graph definition to see what input schema it expects; mirror that in the POST body.

3. **Run status enumeration**
   - What we know: Success criteria mention "pending/running/completed/failed"
   - What's unclear: Are these the exact Platform status values, or abbreviations?
   - Recommendation: Test GET /api/open-swe/runs after creating a run to confirm the status field values match the enum.

4. **Environment variable for local Platform**
   - What we know: Need to configure Platform URL and API key
   - What's unclear: Should OPEN_SWE_ASSISTANT_ID be hardcoded per app or configurable?
   - Recommendation: Make it configurable (env var) so CI and local dev can point to different deployments; document defaults in .env.local.example.
