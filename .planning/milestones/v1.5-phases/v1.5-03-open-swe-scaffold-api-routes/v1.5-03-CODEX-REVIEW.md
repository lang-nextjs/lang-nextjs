- Tests fail with import-time errors? NO — stubs export functions that throw
- Tests fail with meaningful assertion errors? YES — test mocks are set up; stubs throw at call time
- TypeScript compilation succeeds? YES — stub modules exist and export correct types

✅ **PRECONDITION COMPLETENESS:**
- types.ts defines Run, CreateRunRequest, PlatformError
- langgraph-client.ts exports createRun, listRuns (as stubs)
- route.ts exports POST, GET (as stubs)

❌ **GAP IN WAVE 0 PLAN 01:**

The plan says:
```
After writing these files, create stub placeholder files so TypeScript is happy but tests remain RED:
- `apps/open-swe/lib/langgraph-client.ts` — stub that throws
- `apps/open-swe/app/api/open-swe/runs/route.ts` — stub that throws
```


This uses **dynamic import at module level**, which will:
- **Hang or throw if the file doesn't exist at parse time** (depends on test runner behavior)

This is **NOT** the intended RED state. Tests should fail because stub implementations throw, not because imports fail.

**Verdict:** ⚠️ **APPROACH IS SOUND, BUT IMPLEMENTATION HAS A CRITICAL DEFECT**

- **Fix required:** Change Wave 0 stubs to export stub functions (not throw at import time)
- **Correct pattern:**
  ```typescript

  // Tests will fail at runtime when stubs throw
  ```
  
  ```typescript

    throw new Error("not implemented");
  }
  ```

### Observation #3: Route.test.ts mocking strategy assumes fetch is global

**Issue:** Route.test.ts uses `vi.stubGlobal("fetch", vi.fn())` to mock fetch, but this only works if route.ts imports fetch as global.

**Verification:** Plan 02 route.ts imports from `@/lib/langgraph-client`, which calls `fetch` internally. The mock in route.test.ts mocks the global `fetch`, so it should work — **BUT this is fragile if langgraph-client.ts later switches to a different HTTP library**.

**Better approach:** Mock the langgraph-client module itself in route.test.ts:

```typescript
// route.test.ts (IMPROVED)
import { describe, it, expect, vi } from "vitest";
import { NextRequest } from "next/server";

vi.mock("@/lib/langgraph-client", () => ({
  createRun: vi.fn(),
  listRuns: vi.fn(),
}));

import { POST, GET } from "./route";
import { createRun, listRuns } from "@/lib/langgraph-client";

describe("POST /api/open-swe/runs", () => {
  it("returns 201 with run_id when task is valid", async () => {
    vi.mocked(createRun).mockResolvedValueOnce({
      run_id: "run-abc",
      status: "pending",
      created_at: "2026-05-04T00:00:00Z",
      task: "echo hello",
    });

    const req = new NextRequest("http://localhost:3001/api/open-swe/runs", {
      method: "POST",
      body: JSON.stringify({ task: "echo hello" }),
      headers: { "Content-Type": "application/json" },
    });

    const res = await POST(req);
    expect(res.status).toBe(201);
    const body = await res.json();
    expect(body.run_id).toBe("run-abc");
  });
});
```

**Impact:** Current approach works but is less maintainable. Recommendation: **Update Plan 02 route.test.ts to use module mocking** instead of global fetch mocking.

### Observation #4: typo in route.test.ts — BeforeEach/AfterEach lifecycle

**Issue:** Plan 02's route.test.ts has duplicate `beforeEach` and `afterEach` in GET describe block:

```typescript
describe("GET /api/open-swe/runs", () => {
  const PLATFORM_URL = "http://localhost:8000";

  beforeEach(() => {
    vi.stubEnv("LANGGRAPH_PLATFORM_URL", PLATFORM_URL);
    vi.stubGlobal("fetch", vi.fn());
  });

  afterEach(() => {
    vi.unstubAllEnvs();
    vi.unstubAllGlobals();
  });
```

This is correct, but the preceding POST describe block has DIFFERENT behavior:
```typescript
describe("POST /api/open-swe/runs", () => {
  const PLATFORM_URL = "http://localhost:8000";

  beforeEach(() => {
    vi.stubEnv("LANGGRAPH_PLATFORM_URL", PLATFORM_URL);
    vi.stubEnv("OPEN_SWE_ASSISTANT_ID", "open-swe");  // Extra stub!
    vi.stubGlobal("fetch", vi.fn());
  });
```

**Issue:** POST stubs `OPEN_SWE_ASSISTANT_ID` but GET does not. This is correct (POST needs assistant_id, GET does not), but the inconsistency may cause confusion.

**Fix:** Add comment to clarify:

```typescript
describe("GET /api/open-swe/runs", () => {
  const PLATFORM_URL = "http://localhost:8000";

  beforeEach(() => {
    // Note: We don't stub OPEN_SWE_ASSISTANT_ID because GET doesn't need it
    vi.stubEnv("LANGGRAPH_PLATFORM_URL", PLATFORM_URL);
    vi.stubGlobal("fetch", vi.fn());
  });
```

**Impact:** Minor — this is a code style/clarity issue, not a functional bug.

### Observation #5: Plan 02 lacks explicit task about handling Platform response shape mismatches

**Issue:** If the real LangGraph Platform response doesn't match the Run interface (e.g., missing `task` field, status is `"running"` not `"running"`), the GET endpoint will return malformed JSON.

**Example scenario:**
- LangGraph Platform returns: `{ run_id: "...", status: "...", created_at: "..." }` (no `task` field)
- Route.ts: `return new Response(JSON.stringify(runs), ...)`
- Client receives: `[{ run_id: "...", status: "...", created_at: "..." }]` (missing `task`)
- Client expects: `[{ run_id: "...", status: "...", created_at: "...", task: "..." }]`
- Mismatch causes client-side issues

**Fix:** Add a validation/mapping task to Plan 02:

Add to Plan 02 after Task 2:
```
Task 3: Validate and map Platform response shape (optional but recommended)

If LangGraph Platform response differs from Run interface:
- Document the actual Platform response shape in comments
- Add a mapping function in langgraph-client.ts to normalize response
- Example:
  
  export async function listRuns(platformUrl: string): Promise<Run[]> {
    const response = await platformFetch(...);
    const runs = await response.json();
    // Map Platform response to Run interface
    return runs.map(r => ({
      run_id: r.run_id,
      status: r.status,
      created_at: r.created_at,
      task: r.input?.task || r.task || "unknown",  // Handle missing task field
    }));
  }
```

**Impact:** Prevents silent data loss if Platform schema doesn't match expectations.
