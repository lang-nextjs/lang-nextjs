### Pattern 1: Multi-App E2E Suite via Playwright Projects

**What:** Each test app (Next.js example, Remix example, SvelteKit example, open-swe dashboard) has a corresponding Playwright project that sets a custom baseURL and testMatch pattern. Tests for that app only run in its project.

**When to use:** When E2E tests span multiple applications in a monorepo, and you want separate CI status for each app (or consolidated reporting).

**Example:**
```typescript
// Source: playwright.config.ts (established pattern from v1.4-01)
export default defineConfig({
  testDir: './e2e',
  projects: [
    {
      name: 'chromium',  // Core app on port 3000
      use: { baseURL: 'http://localhost:3000' },
      // testMatch defaults to all .spec.ts — includes nextjs, nextjs-extra, open-swe, reconnect
    },
    {
      name: 'remix',
      use: { baseURL: 'http://localhost:5173' },
      testMatch: /remix\.spec\.ts/,
    },
    {
      name: 'sveltekit',
      use: { baseURL: 'http://localhost:5174' },
      testMatch: /sveltekit\.spec\.ts/,
    },
    {
      name: 'open-swe',        // NEW project for open-swe dashboard
      use: { baseURL: 'http://localhost:3001' },
      testMatch: /open-swe\.spec\.ts/,
    },
  ],
});
```

### Pattern 2: Parallel Dev Server Startup in CI

**What:** GitHub Actions starts all required dev servers in the background (using `&` or `pnpm --filter ... dev &`), then waits for all ports to be responsive before running tests.

**When to use:** Multi-app E2E suites where tests depend on multiple running servers; prevents flaky test hangs waiting for slow startup.

**Example:**
```yaml
# Source: .github/workflows/e2e.yml (established pattern)
- name: Start Next.js dev server (port 3000)
  run: pnpm --filter example dev &

- name: Start Remix dev server (port 5173)
  run: pnpm --filter remix-example dev &

- name: Start SvelteKit dev server (port 5174)
  run: pnpm --filter sveltekit-example dev &

- name: Start open-swe dev server (port 3001)  # NEW
  run: pnpm --filter open-swe dev &

- name: Wait for dev servers
  run: |
    for port in 3000 3001 5173 5174; do
      timeout 60 bash -c "until curl -sf http://localhost:$port > /dev/null 2>&1; do sleep 2; done"
      echo "Server ready on :$port"
    done
```

### Anti-Patterns to Avoid

- **Running tests before all servers are ready:** `curl -sf` health check loop must include ALL ports; tests will fail mysteriously if a server is still starting
- **Using different baseURL per test file instead of projects:** testMatch + baseURL per project is cleaner and more maintainable than per-test setup
- **Omitting `ENABLE_STREAM_RECONNECT=true` in CI:** E2E-09 validation requires this flag; without it, the reconnect test will fail or be skipped
- **Running entire E2E suite for only one app:** Playwright projects prevent test leakage — remix.spec.ts should NOT run in the chromium project against port 3000

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Health-checking multiple servers in CI | Custom retry loop with `sleep` polling | `curl -sf` loop with timeout: reliable, standard, handles connection reset gracefully |
| Playwright baseURL override per test | Test-level `goto(baseURL + path)` manually | Playwright projects with baseURL: single source of truth, cleaner test code |
| Multi-app test isolation | Single E2E spec with conditional baseURL branches | testMatch + project configuration: prevents accidental cross-app test execution |
| Stream reconnection simulation | Custom SSE mock responder | Playwright `page.route()`: standard browser-layer request interception, no custom server required |

**Key insight:** Playwright's project system, baseURL, and testMatch are designed exactly for this use case (multi-app monorepo E2E). Using them saves >50 lines of boilerplate per app and eliminates a class of bugs (tests accidentally running against wrong server).

## Common Pitfalls

### Pitfall 1: CI Workflow Timing — Servers Not Ready Before Tests Start

**What goes wrong:** CI starts dev servers in background, immediately runs tests, tests fail with "connection refused" because Next.js/SvelteKit/Remix are still warming up (takes 3–8 seconds).

**Why it happens:** Async server startup is not awaited; tests assume servers are responsive immediately.

**How to avoid:**
1. Start each server with `&` (background) not `&&` (blocking)
2. Immediately after all `&` commands, add a wait loop that polls each port with `curl -sf`
3. Use `timeout 60` to prevent infinite hangs if a server fails to start
4. Test locally with `pnpm test:e2e` before pushing to CI

**Warning signs:**
- CI job succeeds locally but fails in GitHub Actions
- Flaky test failures: "connection refused" on first run, pass on retry
- All tests in a project fail but not others (suggests server-specific startup issue)

**Current state in v1.5-05:** The `.github/workflows/e2e.yml` (e2e-mocked job) already has the correct pattern:
```yaml
- name: Wait for dev servers
  run: |
    for port in 3000 5173 5174; do
      timeout 60 bash -c "until curl -sf http://localhost:$port > /dev/null 2>&1; do sleep 2; done"
      echo "Server ready on :$port"
    done
```
Extension: Add port 3001 to the list.

### Pitfall 2: Stream Reconnection Test Flakiness — Timing Sensitivity

**What goes wrong:** E2E-09 test passes locally but fails in CI; retry button click doesn't trigger second request; test hangs waiting for 'continued' text.

**Why it happens:** 
1. `abortFirst` flag is local to the test function — Playwright page.route handler sees stale closure value
2. Race condition: test clicks retry before route handler is fully installed
3. SSE parsing: test looks for exact text match that might not arrive in expected format

**How to avoid:**
1. Use `let` scoping (not const) for route handler state; let handler mutate state directly
2. Install route handler via `await page.route()` BEFORE navigation or interaction
3. Use text fragment assertions (`toBeVisible()`) with explicit timeouts, not exact string matches
4. Test locally with `ENABLE_STREAM_RECONNECT=true pnpm test:e2e` before CI

**Warning signs:**
- Test passes 9/10 times in CI
- Different failures on different runs (suggests race condition, not deterministic error)
- `text=continued` assertion times out despite SSE body containing "continued"

**Current state:** `e2e/reconnect.spec.ts` uses `abortFirst` as a local let variable in test closure — this is correct. The test already awaits `page.route()` before navigation. The assertions use `toBeVisible()` with timeouts. This pattern is established and reliable.

### Pitfall 3: open-swe Tests Running Against Wrong Port

**What goes wrong:** `e2e/open-swe.spec.ts` tests run against port 3000 (example app) instead of port 3001 (open-swe), causing test failures ("component not found", "route not found").

**Why it happens:** 
1. Playwright's chromium project has `baseURL: 'http://localhost:3000'` by default
2. If no testMatch is specified, ALL .spec.ts files run in ALL projects
3. open-swe tests try to navigate to `/runs` or `/api/open-swe/runs` on the wrong app

**How to avoid:**
1. Add a new Playwright project specifically for open-swe with `baseURL: 'http://localhost:3001'` and `testMatch: /open-swe\.spec\.ts/`
2. Configure chromium project to NOT run open-swe tests: use testMatch negation OR explicitly list the .spec files it DOES run
3. Test locally: `pnpm exec playwright test --project=open-swe --debug` navigates directly to port 3001

**Warning signs:**
- open-swe tests fail in CI but pass when run manually against `PLAYWRIGHT_BASE_URL=http://localhost:3001 pnpm test:e2e`
- Test output shows "page went to http://localhost:3000/runs" (wrong port)
- only the open-swe-related assertions fail, other tests pass

**Current state:** No open-swe project exists yet in playwright.config.ts. v1.5-06 must add it with explicit testMatch.

### Pitfall 4: CI Job Not a Required Status Check

**What goes wrong:** CI job runs and reports results, but GitHub does not block PR merge on failure — developers can merge failing tests.

**Why it happens:** Workflow is created but not added to the branch protection rules in GitHub repo settings.

**How to avoid:**
1. After creating `.github/workflows/e2e.yml`, go to repo Settings → Branches → Branch protection for `main`
2. Add the E2E job name (`e2e-mocked`) as a required check
3. Do NOT merge the RESEARCH.md without verifying branch protection is configured

**Warning signs:**
- PR shows green checkmark despite E2E failure
- No "Waiting for required checks" message in GitHub UI

**Current state:** The e2e-mocked job already exists and is configured in branch protection (visible in repo settings). v1.5-06 should verify this is still active and working.

### Example 1: Playwright Project Configuration for Multiple Apps

**Context:** `playwright.config.ts` needs to support testing 4 apps on 4 different ports.

```typescript
// Source: established pattern from v1.4-01, extended for v1.5-06
import { defineConfig, devices } from '@playwright/test'

export default defineConfig({
  testDir: './e2e',
  timeout: 60_000,
  retries: process.env.CI ? 1 : 0,
  reporter: [['list'], ['html', { open: 'never' }]],
  use: {
    baseURL: process.env.PLAYWRIGHT_BASE_URL ?? 'http://localhost:3000',
    trace: 'on-first-retry',
  },
  projects: [
    {
      name: 'chromium',
      use: { ...devices['Desktop Chrome'] },
      testMatch: [
        /nextjs\.spec\.ts/,
        /nextjs-extra\.spec\.ts/,
        /reconnect\.spec\.ts/,
        /open-swe\.spec\.ts/,
      ],
    },
    {
      name: 'remix',
      use: {
        ...devices['Desktop Chrome'],
        baseURL: process.env.PLAYWRIGHT_REMIX_URL ?? 'http://localhost:5173',
      },
      testMatch: /remix\.spec\.ts/,
    },
    {
      name: 'sveltekit',
      use: {
        ...devices['Desktop Chrome'],
        baseURL: process.env.PLAYWRIGHT_SVELTEKIT_URL ?? 'http://localhost:5174',
      },
      testMatch: /sveltekit\.spec\.ts/,
    },
    {
      name: 'open-swe',
      use: {
        ...devices['Desktop Chrome'],
        baseURL: process.env.PLAYWRIGHT_OPENSWE_URL ?? 'http://localhost:3001',
      },
      testMatch: /open-swe\.spec\.ts/,
    },
  ],
})
```

**Why this works:**
- chromium project runs core monorepo tests (nextjs example + reconnection) plus new open-swe tests
- open-swe project isolates open-swe-specific tests to port 3001
- Each project has its own baseURL, preventing cross-app pollution
- testMatch ensures remix.spec.ts doesn't run in chromium project

- Report upload only happens if test step completes (success or failure)

### Example 3: Stream Reconnection E2E Test (E2E-09)

**Context:** `e2e/reconnect.spec.ts` validates retry() flow with mid-stream interruption.

```typescript
// Source: established pattern from v1.4-01, used as-is in v1.5-06
import { test, expect } from '@playwright/test';

test.describe('DeepAgents E2E — Stream Reconnection (E2E-09)', () => {
  test('E2E-09: retry() after interruption resumes stream without duplicating messages', async ({ page }) => {
    let requestCount = 0;
    let abortFirst = true;

    await page.route('**/api/chat/stream', async (route) => {
      requestCount++;
      if (requestCount === 1 && abortFirst) {
        // First request: deliver partial response (incomplete)
        await route.fulfill({
          status: 200,
          headers: {
            'Content-Type': 'text/event-stream',
            'x-vercel-ai-ui-message-stream': 'v1',
            'Cache-Control': 'no-cache',
          },
          body: [
            'data: {"type":"text-start","id":"t1","messageId":"msg1"}',
            '',
            'data: {"type":"text-delta","id":"t1","delta":"First part"}',
            '',
            // No finish frame — simulates mid-stream interruption
          ].join('\n'),
        });
      } else {
        // Retry request: deliver complete response
        await route.fulfill({
          status: 200,
          headers: {
            'Content-Type': 'text/event-stream',
            'x-vercel-ai-ui-message-stream': 'v1',
            'Cache-Control': 'no-cache',
          },
          body: [
            'data: {"type":"text-start","id":"t1","messageId":"msg1"}',
            '',
            'data: {"type":"text-delta","id":"t1","delta":"First part"}',
            '',
            'data: {"type":"text-delta","id":"t1","delta":" continued"}',
            '',
            'data: {"type":"text-end","id":"t1"}',
            '',
            'data: {"type":"finish","finishReason":"stop"}',
            '',
            '',
          ].join('\n'),
        });
      }
    });

    await page.goto('/reconnect-test');
    await page.waitForLoadState('networkidle');

    // Send initial message (triggers first request — partial stream)
    await page.locator('[data-testid="input"]').fill('hello');
    await page.locator('[data-testid="send"]').click();

    // Wait for partial content to appear
    await expect(page.locator('text=First part')).toBeVisible({ timeout: 10_000 });

    // Simulate that the stream is stuck — click Retry
    abortFirst = false;
    await page.locator('[data-testid="retry"]').click();

    // After retry, full content appears
    await expect(page.locator('text=continued')).toBeVisible({ timeout: 10_000 });

    // Assert no duplicate: only 1 message element contains 'First part'
    const messageEls = page.locator('[data-testid="message"]');
    const count = await messageEls.count();
    let firstPartCount = 0;
    for (let i = 0; i < count; i++) {
      const text = await messageEls.nth(i).textContent();
      if (text && text.includes('First part')) firstPartCount++;
    }
    expect(firstPartCount).toBe(1);

    // Assert request count: 2 requests (original + retry)
    expect(requestCount).toBe(2);
  });
});
```

**Why this works:**
- `page.route()` intercepts at browser layer; no server modification needed
- `abortFirst` is a mutable let in closure; handler modifies it to change behavior on retry
- Assertions verify: (1) partial content arrives, (2) full content appears after retry, (3) no duplication, (4) exactly 2 requests
- Requires `/reconnect-test` page in apps/example with useDeepAgentsChat enableReconnect: true
