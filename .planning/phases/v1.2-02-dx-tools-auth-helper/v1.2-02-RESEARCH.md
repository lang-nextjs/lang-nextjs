# Phase v1.2-02: DX Tools + Auth Helper - Research

**Researched:** 2026-05-01
**Domain:** Debug logging, mock test server utilities, cookie-based authentication
**Confidence:** HIGH

## Summary

Phase v1.2-02 adds three developer experience features to the `@deepagents-nextjs` ecosystem. The phase requires extracting the existing mock SSE server from `apps/example` into a reusable test utility, implementing environment variable-based debug logging, and providing a cookie authentication helper. These are foundational DX improvements that reduce boilerplate for consumers.

The key technical decisions are: (1) debug logging via `DEBUG=deepagents:sse` environment variable using either the `debug` module or native console.error since costs are low; (2) mock server extracted from existing `streamText` + `MockLanguageModelV3` pattern from the AI SDK v6 `ai/test` exports; (3) synchronous cookie reading via `NextRequest.cookies.get()` API available since Next.js 13.

**Primary recommendation:** Create a new `@deepagents-nextjs/test-utils` package exporting `createMockDeepAgentsServer()` extracted from existing mock; implement lightweight debug logging via environment variable check in handler; add `getCookieToken()` as a simple wrapper around synchronous `NextRequest.cookies` API.

### Pattern 1: Debug Logging via Environment Variable
**What:** Lightweight logging that checks `DEBUG=deepagents:sse` at runtime; emits parsed frame data to stderr; zero overhead when disabled.
**When to use:** During development/debugging to diagnose SSE stream issues; enables operators to enable/disable without code changes.
**Example:**
```typescript
// Source: Phase v1.2-02 implementation
// In handler.ts - after transform pipeline, before controller.enqueue:
if (process.env.DEBUG?.includes('deepagents:sse')) {
  try {
    const parsed = JSON.parse(transformed.raw.split('\n').find(l => l.startsWith('data: '))?.slice(6) ?? '{}')
    console.error(`[deepagents:sse] frame:`, parsed)
  } catch {
    // Non-JSON or malformed data lines pass through without error
  }
}
```

### Pattern 2: Reusable Mock Server as Test Utility
**What:** Extract existing mock from example app into standalone package; export factory function that returns a Next.js Response with SSE stream.
**When to use:** In consumer test suites when you need deterministic SSE responses without a real backend.
**Example:**
```typescript
// Source: Extracted from apps/example/route.mock.ts
import { createMockDeepAgentsServer } from '@deepagents-nextjs/test-utils'

it('accepts mock responses', async () => {
  const response = await createMockDeepAgentsServer()
  const body = response.body
  // Assert on typed messages parsed from SSE stream
})
```

### Pattern 3: Cookie-Based Auth Helper
**What:** Wrapper function that returns a `getToken`-compatible async function; reads value from `NextRequest.cookies` synchronously (not global async `cookies()`).
**When to use:** API routes that need to extract session tokens from cookies and inject them into backend requests.
**Example:**
```typescript
// Source: Phase v1.2-02 implementation
import { getCookieToken } from '@deepagents-nextjs/server'

const handler = createDeepAgentsHandler({
  backendUrl: process.env.BACKEND_URL,
  getToken: getCookieToken('session_token')
})
// Now: request.cookies.get('session_token')?.value is extracted and sent as Bearer token
```

### Anti-Patterns to Avoid
- **Using async global `cookies()`:** Unavailable in Route Handlers; only works in Server Components. Always use `NextRequest.cookies` for API routes.
- **Throwing on missing cookie:** `getCookieToken()` should return null/undefined when cookie absent (per handler's fail-open policy), not throw.
- **Mock server with real fetch:** Extract mock must NOT call real backend; use AI SDK's `MockLanguageModelV3` as tested pattern.
- **Debug logging without environment check:** Always check `process.env.DEBUG` or `process.env.DEBUG?.includes()` first to avoid overhead when disabled.
- **Multiple mock servers in same test:** Each call creates new Promises; tests must manage cleanup properly or risk port conflicts.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| SSE mock backend | Custom ReadableStream implementation | `ai` package `streamText + MockLanguageModelV3` | Correctly implements AI SDK v6 wire format; handles all frame types (text-start, text-delta, text-end, finish); proven in example app |
| Cookie parsing | Custom header/cookie extraction | `NextRequest.cookies.get()` | Handles cookie spec (encoding, quotes, expires, secure flag); synchronous and type-safe; built-in to Next.js |
| Debug namespace filtering | Custom string splitting | Simple `process.env.DEBUG?.includes('deepagents:sse')` or `debug` npm module | Low overhead for simple case; avoids dependency; matches Node.js ecosystem patterns |
| Frame JSON parsing for logging | Inline try/catch only | Wrapped in debug-logging block | Prevents parse errors from crashing SSE stream; non-JSON lines (like [DONE]) expected |

**Key insight:** The handler's streaming loop is real-time and cannot afford heavy logging; debug logging must be: (1) opt-in via environment variable, (2) non-blocking if parse fails, (3) stderr-only to avoid mixing with stdout SSE response.

## Common Pitfalls

### Pitfall 1: Using Async Global `cookies()` in API Routes
**What goes wrong:** New developers import `cookies()` from `next/headers` and call it in Route Handlers (expectation: works like NextRequest.cookies), but it's only available in Server Components. Route Handler throws "cannot await cookies() outside a Server Component".
**Why it happens:** Next.js v15 made the global `cookies()` async; developers confuse it with `NextRequest.cookies` which is sync and Web API-compatible.
**How to avoid:** Always use `request.cookies.get(name)` (synchronous) in Route Handlers. Only use global `cookies()` (async) in Server Components.
**Warning signs:** Compilation error or "cookies is not awaited" in linter checks; runtime error if not caught during dev.

### Pitfall 2: Debug Logging Performance Overhead
**What goes wrong:** Logging added at SSE frame boundary without environment variable guard; handler serializes and logs every frame even when debugging is disabled, causing latency or frame buffering issues.
**Why it happens:** Developer adds logging for initial debugging, forgets to make it conditional; SSE is real-time and even 1-2ms per frame multiplies across a stream.
**How to avoid:** ALWAYS gate debug output behind `if (process.env.DEBUG?.includes('namespace'))` BEFORE expensive operations (parsing, serialization). Never call `JSON.parse()` on every frame if disabled.
**Warning signs:** Noticeable latency in streaming responses; E2E tests timeout when `DEBUG=*` is set; frame arrival gaps visible with `curl -N`.

### Pitfall 3: Mock Server Port/Resource Conflicts
**What goes wrong:** Test suite runs in parallel; multiple `createMockDeepAgentsServer()` calls create overlapping mock servers on same port or with shared resources, causing intermittent test failures.
**Why it happens:** Mock server not properly isolated or cleaned up between tests; Vitest parallel mode doesn't serialize creation.
**How to avoid:** Each `createMockDeepAgentsServer()` call returns a `Response`, not a server with a port. No listen/bind needed. Factory is pure and idempotent. If tests create it multiple times in sequence, each returns independent Response. For concurrent use, ensure beforeEach/afterEach cleanup or use test isolation.
**Warning signs:** Tests pass in sequence (`vitest run`) but fail in parallel (`vitest`); intermittent "EADDRINUSE" or "resource busy" errors.

### Pitfall 4: Forgetting to Export from Public API
**What goes wrong:** `getCookieToken` is added to server/src but not included in the exports field of packages/server/package.json or server/src/index.ts.
**Why it happens:** New functions often added to utility files, but exports are in central index.ts; developer forgets to re-export.
**How to avoid:** Add to `packages/server/src/index.ts` immediately after implementation; run `npm run validate` (publint + attw) to catch missing exports before commit.
**Warning signs:** Consumer can't import function; TypeScript error "named export not found"; ESM build succeeds but CJS bundle missing the function.

### Pitfall 5: Cookie Value Undefined vs Null Confusion
**What goes wrong:** `request.cookies.get(name)` returns undefined if cookie absent; developer assumes null and checks `if (cookie === null)`, missing the undefined case.
**Why it happens:** Different APIs use null vs undefined differently; cookies API is undefined-returning like most JS APIs.
**How to avoid:** Always use `if (cookie != null)` or `if (cookie?.value)` (handles both) in getCookieToken. Type signature should be `string | undefined`, not `string | null`.
**Warning signs:** Missing cookies silently treated as present; Bearer token sent as "Bearer undefined".

// Source: handler.ts streaming loop
// After line 242 in existing handler.ts (after applyTransforms call)

if (process.env.DEBUG?.includes('deepagents:sse')) {
  try {
    const dataLine = transformed.raw.split('\n').find(l => l.startsWith('data: '))

      const jsonStr = dataLine.slice(6) // Remove "data: " prefix

        console.error(`[deepagents:sse] frame:`, parsed)

    // Non-JSON lines (like bare event: lines) expected; silently skip
    // Do not propagate parse errors — they would corrupt streaming
  }

### DX-02: Mock Server Factory
```typescript
// Source: Extracted and adapted from apps/example/app/api/chat/stream/route.mock.ts
import { streamText, simulateReadableStream } from 'ai'
import { MockLanguageModelV3 } from 'ai/test'

export async function createMockDeepAgentsServer(opts?: {
  chunkDelayMs?: number
}): Promise<Response> {
  const result = streamText({
    model: new MockLanguageModelV3({
      doStream: (async () => ({
        stream: simulateReadableStream({
          chunkDelayInMs: opts?.chunkDelayMs ?? 50,
          chunks: [
            { type: 'text-start', id: 'text-1' },
            { type: 'text-delta', id: 'text-1', delta: 'Hello! ' },
            { type: 'text-delta', id: 'text-1', delta: 'I am the mock assistant.' },
            { type: 'text-end', id: 'text-1' },
            {
              type: 'finish',
              finishReason: 'stop',
              usage: { inputTokens: 0, outputTokens: 5 },
            },
          ],
        }),
        rawCall: { rawPrompt: null, rawSettings: {} },
      })) as any,
    }),
    prompt: 'mock — input is ignored',
  })

  return result.toUIMessageStreamResponse()
}
```

### AUTH-01: Cookie Token Helper
```typescript
// Source: to be added to packages/server/src/get-cookie-token.ts
import { type NextRequest } from 'next/server'

/**
 * Returns a getToken function that reads a cookie synchronously from NextRequest.
 *
 * Usage:
 *   const handler = createDeepAgentsHandler({
 *     backendUrl: process.env.BACKEND_URL!,
 *     getToken: getCookieToken('session_id')
 *   })
 *
 * Behavior:
 * - Cookie present: returns cookie value as Bearer token
 * - Cookie absent: returns undefined (no Authorization header, fail-open)
 * - Cookie malformed: returns value as-is (let backend decide validity)
 *
 * Per CONTEXT.md locked decision: getToken returns string | undefined (null-coalescing
 * in handler injects Bearer or skips header).
 */
export function getCookieToken(
  cookieName: string,
): (req: NextRequest) => string | undefined {
  return (req: NextRequest) => {
    const cookie = req.cookies.get(cookieName)
    return cookie?.value
  }
}
```

## State of the Art

| Old Approach | Current Approach | When Changed | Impact |
|--------------|------------------|--------------|--------|
| Debug via `console.log()` everywhere | DEBUG env var + conditional logging | Node.js best practice (20+ years) | Deployments stay clean; developers toggle at runtime without code changes |
| Mock backends as in-process servers on ports | AI SDK MockLanguageModelV3 + streamText | AI SDK v6 (2024+) | Tests don't need port management; Response objects compose naturally in handler tests |
| Manual cookie string parsing | `NextRequest.cookies.get()` API | Web API standard + Next.js 13+ | Type-safe, handles edge cases (encoding, domain, expires) |
| Global async `cookies()` | Synchronous `request.cookies` in Route Handlers | Next.js 13 (route handlers); v15 (async global) | Clear separation: async in components, sync in API routes |

**Deprecated/outdated:**
- Inline mock responses in test files: Use `createMockDeepAgentsServer()` factory to avoid duplication
- Manual `Set-Cookie` header parsing: Always use `NextRequest.cookies` API
- `DEBUG=*` wildcard logging: Use `DEBUG=deepagents:sse` to target specific namespace and avoid noise

## Open Questions

1. **Debug output format preference**
   - What we know: Requirement says `[deepagents:sse] frame: ...` format; `console.error` to stderr is correct (separates from response body on stdout)
   - What's unclear: Should frame be `JSON.stringify(parsed, null, 2)` (pretty) or compact? Requirement only shows "frame: ..."
   - Recommendation: Compact JSON on same line (`console.error(\`[deepagents:sse] frame: ${JSON.stringify(parsed)}\`)`) to avoid noise in CI logs; developers can pipe to jq for pretty-printing if needed

2. **Mock server response variations**
   - What we know: Existing route.mock.ts returns fixed "Hello I am the mock" response
   - What's unclear: Should `createMockDeepAgentsServer()` accept options to customize chunks/delays? Or always return fixed response?
   - Recommendation: Accept optional `{ chunkDelayMs?: number, chunks?: StreamChunk[] }` to enable test-specific scenarios (slow streams, error conditions) without duplicating the factory

3. **Test-utils package dependencies**
   - What we know: Needs `ai` (for streamText, MockLanguageModelV3) and `next` (for Next.js Response type)
   - What's unclear: Should test-utils list them as peerDependencies (like @deepagents-nextjs/server does) or devDependencies?
   - Recommendation: Both should be peerDependencies to force consumers to have compatible versions; avoids duplicate @ai-sdk packages

4. **Cookie name validation**
   - What we know: `getCookieToken(cookieName: string)` accepts a name and reads from `request.cookies.get(cookieName)`
   - What's unclear: Should the function validate the cookie name? (e.g., no spaces, valid chars per RFC 6265)
   - Recommendation: No validation in getCookieToken; if invalid name passed, cookies.get() returns undefined (fail-open). Validation is consumer's responsibility.
