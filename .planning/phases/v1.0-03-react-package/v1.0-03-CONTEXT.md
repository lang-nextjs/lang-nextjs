<decisions>
## Implementation Decisions

### Hook API surface (RCT-01)
- `useDeepAgentsChat({ sessionId, endpoint, getToken? })` — minimal API matching the two-line server usage goal
- Returns: `{ messages, sendMessage, status, error }`
  - `messages: Message[]` — typed discriminated union, never `any`
  - `sendMessage: (text: string) => void`
  - `status: 'idle' | 'streaming' | 'submitted' | 'error'`
  - `error: Error | null`
- `getToken?: () => Promise<string | null> | string | null` — mirrors server package semantics: absent = no Auth header, null = no Auth header, string = `Bearer {token}`
- No `sessionId` state management in the hook — caller owns session lifecycle (they pass it in)
- No `boardId`, `chatMode`, `agentType`, or `localStorage` — all stripped as app-specific
- `DefaultChatTransport` is constructed internally with `api: endpoint`, `body: () => ({ sessionId })`, and optional auth headers from `getToken`
- `useChat` from `@ai-sdk/react` is called internally; `messages` from `useChat` are converted via `partsToMessages()`

### Message union discrimination (RCT-02)
- Discriminated on `type` field (not `role`): `'user' | 'ai' | 'tool-call' | 'error'`
- Four variants only: `UserMessage`, `AIMessage`, `ToolCallMessage`, `ErrorMessage`
  - Matches ROADMAP.md success criterion 2 exactly
  - All stsfront-specific types (StatusMessage, ApprovalRequestMessage, SubAgentMessage, etc.) are stripped — they depend on app-specific data-* schemas
- `type` discriminator rationale: avoids ambiguity with AI SDK's own `role` field on `UIMessage`; `type` is more descriptive and consistent with stsfront naming
- `AIMessage.isStreaming: boolean` — retained because it drives the animated caret in any chat UI; callers need it
- `ToolCallMessage.status: 'running' | 'complete'` — binary, sufficient for generic display without app-specific knowledge
- No `TraceInfo` — stripped as debug-only, not part of the generic contract
- `generateId()` exported as a utility — uses `crypto.randomUUID()`
- `assertNever()` exported as a utility for exhaustive switch coverage

### Zod schema scope (RCT-03)
- Export four schemas matching ROADMAP success criterion 3: `PlanSchema`, `TaskSchema`, `FileSchema`, `ApprovalSchema`
  - Internal names in source: `DataPlanSchema`, `DataTaskSchema`, `DataFileSchema`, `DataApprovalSchema`
  - Public export names use shorter form: `PlanSchema` etc. (consistent with ROADMAP wording)
- Also export: `PlanSubtaskSchema`, `DataErrorSchema` — these are shared sub-schemas or directly useful
- Also export: `parseDataPart()` helper — callers can gate unknown `data-*` parts without rewriting the discriminated union logic
- Strip from source: `DataSubAgentSchema`, `DataApprovalPendingSchema`, `DataApprovalTimeoutSchema`, `DataToolApprovalSchema`, `AiSdkDataPartSchema` (discriminated union) — too app-specific or dependent on stripped types
- Zod version: v4 (matches PROJECT.md constraints); source uses v3 `z.object()` — API is identical for these schemas
- Schema passthrough policy: use default Zod behavior (strip unknown keys) — not `.passthrough()`, not `.strict()`; forward-compat unknown fields are dropped silently. Callers who need passthrough can wrap schemas themselves.

### partsToMessages() conversion design
- Exported function: `partsToMessages(aiMessages: UIMessage[], isStreaming: boolean): Message[]`
- Handles: text parts → `AIMessage`, user messages → `UserMessage`, tool parts → `ToolCallMessage`, `data-error` parts → `ErrorMessage`
- Drops silently (log + skip): all other `data-*` parts (data-plan, data-task, data-file, data-approval, data-sub-agent, etc.) — they are not in the Message union
- Single-pass over parts[] in stream order per message (preserves the stsfront ordering fix: tool flush before approval card)
- Upsert-by-id for tool calls within a message (same toolCallId can arrive as input-streaming then output-available)
- `isStreaming` flag propagated to the last assistant message's last `AIMessage` bubble (`isStreaming: true`)
- No SeqBuffer, no mergeHistoryAndInline, no applyOptimisticApproval — stripped as app-specific

### peerDependency versions
- `react: ^18.0.0 || ^19.0.0` — already set in skeleton package.json; correct
- `react-dom: ^18.0.0 || ^19.0.0` — already set; correct
- Add peer: `ai: ^4.0.0` — required for `UIMessage` type from the `ai` package
- Add peer: `@ai-sdk/react: ^1.0.0` — required for `useChat`
- Add peer: `zod: ^3.0.0 || ^4.0.0` — schemas must work with either; use `z.object()` which is identical in both
- Add devDependency: `ai`, `@ai-sdk/react`, `zod` (pinned to latest for test runner)
- Do NOT bundle React, AI SDK, or Zod — peerDeps only, zero bundled copies

<specifics>
## Specific Ideas

- "Port and generalize" is the mandate — strip stsfront-specific logic aggressively
- The two-line consumer usage bar: `import { useDeepAgentsChat } from '@deepagents-nextjs/react'` + `const { messages, sendMessage } = useDeepAgentsChat({ sessionId, endpoint: '/api/chat/stream' })`
- Schema export names follow ROADMAP: `PlanSchema`, `TaskSchema`, `FileSchema`, `ApprovalSchema` (not `DataPlanSchema` etc.)
- `'use client'` directive at the top of the hook file — required for Next.js App Router client components
- `jsdom` is already in devDeps (skeleton) — correct environment for React hook tests
- Test environment for hook tests: `@vitest-environment jsdom` (or vitest config `environment: 'jsdom'`)
- `partsToMessages` is the core unit under test — its conversion logic is where most test cases live
- The hook itself is tested as an integration: `renderHook(() => useDeepAgentsChat(...))` with mocked `useChat`

</specifics>
