<task type="auto">
  <name>Task 2: Verify and harden backpressure (RESIL-04)</name>
  <files>packages/server/src/handler.ts, packages/server/src/handler.backpressure.test.ts</files>
  <action>
The handler streams via a ReadableStream that pulls from the backend reader in a `while(true)` loop inside `start()`, enqueuing transformed frames. A pull-based ReadableStream applies backpressure naturally only if the producer respects `controller.desiredSize`. The current loop reads eagerly in start() and enqueues without checking desiredSize — under a slow consumer this can buffer. Harden it:

  - After each `controller.enqueue(...)`, if `controller.desiredSize !== null && controller.desiredSize <= 0`, pause reading until the consumer pulls. The cleanest fix without changing the stream contract: convert the eager `start()` loop to a `pull(controller)` based source, OR add a small awaitable gate. Minimal-risk approach: keep start() but await a microtask/`controller.desiredSize` check — if desiredSize <= 0, await a Promise that resolves on the next `pull` callback. Implement a `pull`-driven reader: move the read loop body into `pull(controller)` so the ReadableStream only requests the next chunk when the consumer is ready (this is the idiomatic Web Streams backpressure mechanism and bounds memory). Preserve ALL existing behavior: accumulator framing, oversized-frame skip, terminal-frame detection, in-band error on truncation, finally cleanup (abort + timer clear + registry/approval cleanup + onStreamEnd).
  - Keep the existing `SseFrameAccumulator` (already bounds a single oversized partial frame to MAX_FRAME_BYTES — see accumulator.ts lines 78–88). Backpressure here is about not OUT-pacing a slow client across many frames.
  - Edge-safe: use only Web Streams APIs (no Node streams.pipeline — keeps the same code path edge-compatible per locked constraint).

Write `packages/server/src/handler.backpressure.test.ts`:
  - SLOW CONSUMER BOUNDED: build a mock backend ReadableStream that can produce many frames; consume the handler's response stream slowly (read one chunk, then delay). Assert the backend reader does NOT race ahead unbounded — e.g. track how many backend frames have been pulled vs how many the client has read and assert the in-flight gap stays small/bounded (within a constant, not growing with total frames). This proves backpressure is applied (RESEARCH Pitfall 5).
  - CORRECTNESS PRESERVED: a normal fast consumer still receives all frames in order with the terminal frame, and a truncated stream still emits the in-band upstream_disconnect error — i.e. the pull-based refactor did not regress existing handler.test.ts behavior.
