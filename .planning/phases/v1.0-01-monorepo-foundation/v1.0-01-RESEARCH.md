## Summary

This phase bootstraps a greenfield monorepo from an empty repository. The work is entirely configuration and skeleton — no feature code ships. The deliverable is a repo where `pnpm install` resolves all workspaces, `turbo build` executes in correct dependency order with content-aware caching, and each package emits dual ESM + CJS + `.d.ts` artifacts that would pass `publint` if published today.

The stack is decisive and well-understood: pnpm workspaces with `pnpm-workspace.yaml`, Turborepo v2.9.x (`turbo` package, `tasks` key in `turbo.json` — not the deprecated `pipeline` key), tsup 8.x for dual ESM/CJS output, and a single `tsconfig.base.json` in strict mode extended by every package. The only noteworthy discovery from current research is that Vitest 3.2+ deprecated the `vitest.workspace.ts` file in favor of a `projects` array in the root `vitest.config.ts` — per-package configs are still valid but the workspace-level setup has changed syntax.

The phase is entirely scaffolding — no SSE proxy, no React hook, no feature logic. The risk is configuration correctness (wrong `exports` field order, missing `sideEffects: false`, wrong Turborepo schema key) rather than architectural unknowns. All pitfalls documented are preventable by following verified patterns from official sources.

**Primary recommendation:** Bootstrap using `pnpm-workspace.yaml` + `turbo.json` with `tasks` key, two package skeletons under `packages/`, one app skeleton under `apps/example/`, a shared `tsconfig.base.json` with `"moduleResolution": "bundler"`, and per-package `tsup.config.ts` with `format: ["esm", "cjs"]` and `dts: true`.

## Standard Stack

### Core

| Library | Version | Purpose | Why Standard |
|---------|---------|---------|--------------|
| pnpm | `^9.x` | Package manager + workspace orchestration | `pnpm-workspace.yaml` replaces npm/yarn workspace field; strictest `node_modules` isolation; fastest installs; `workspace:*` protocol for internal deps |
| turbo | `^2.9.6` | Build orchestration and content-aware caching | `turbo` package (not `turborepo`); v2 uses `tasks` key (not `pipeline`); authored by Vercel; topological build order via `dependsOn: ["^build"]` |
| tsup | `^8.5.1` | Dual ESM/CJS TypeScript bundler | Built on esbuild; emits `.js`/`.cjs`/`.d.ts`/`.d.cts` in one pass; 1M+ weekly downloads; zero-config for standard library builds |
| TypeScript | `^6.0.3` | Primary language | Current stable; strict mode; all packages ship `.d.ts`; tsup 8.x supports TS 6 |
| Vitest | `^4.1.5` | Test runner | Native TypeScript, Jest-compatible API; v3.2+ uses `projects` config (not deprecated `workspace`); per-package `vitest.config.ts` remains valid |

### Supporting

| Library | Version | Purpose | When to Use |
|---------|---------|---------|-------------|
| `publint` | latest | Validate `package.json` exports field | Run locally and in CI before every publish; catches `exports` field mistakes |
| `@arethetypeswrong/cli` | latest | Validate TypeScript type resolution | Catches `.d.ts` issues that publint misses; run as `npx attw --pack .` |
| `eslint` | `^9.x` | Linting | ESLint v9 flat config (`eslint.config.mjs`); do not use `.eslintrc.*` |
| `typescript-eslint` | `^8.x` | TypeScript lint rules | Used with ESLint v9 via `tseslint.config()` |

### Alternatives Considered

| Instead of | Could Use | Tradeoff |
|------------|-----------|----------|
| `tsup` | `tsc` only | `tsc` requires manual path management, no tree-shaking; use only if bundleless output is desired |
| `turbo` | `nx` | Nx has more features but higher config overhead; Turborepo is lower friction for greenfield |
| `vitest` per-package | Vitest `projects` root config | Root `projects` config gives unified coverage but loses per-package Turborepo cache granularity; per-package is recommended for this repo |

### Pattern 1: pnpm-workspace.yaml

**What:** Root workspace definition — points pnpm at both `packages/*` and `apps/*` globs.

**When to use:** Required; without it pnpm does not discover sub-packages.

```yaml
# Source: https://pnpm.io/pnpm-workspace_yaml
packages:
  - 'packages/*'
  - 'apps/*'
```

### Pattern 2: Root package.json (private, tooling only)

**What:** Root package must be `"private": true` and contain only dev tooling. The `packageManager` field pins pnpm version via Corepack.

```json
{
  "name": "deepagents-nextjs-monorepo",
  "private": true,
  "packageManager": "pnpm@9.0.0",
  "scripts": {
    "build": "turbo build",
    "test": "turbo test",
    "typecheck": "turbo typecheck",
    "lint": "turbo lint"
  },
  "devDependencies": {
    "turbo": "^2.9.6",
    "typescript": "^6.0.3",
    "eslint": "^9.x",
    "typescript-eslint": "^8.x"
  }
}
```

### Pattern 3: turbo.json (v2 schema — `tasks` key, NOT `pipeline`)

**What:** Defines build pipeline with topological ordering. `"dependsOn": ["^build"]` ensures packages build before their dependents.

**Critical:** Turborepo v2 replaced `"pipeline"` with `"tasks"`. Using `"pipeline"` triggers a deprecation warning and will break in a future version.

```json
{
  "$schema": "https://turborepo.dev/schema.json",
  "tasks": {
    "build": {
      "dependsOn": ["^build"],
      "outputs": ["dist/**"]
    },
    "test": {
      "dependsOn": ["build"],
      "outputs": ["coverage/**"]
    },
    "typecheck": {
      "dependsOn": ["^build"]
    },
    "lint": {
      "dependsOn": []
    },
    "dev": {
      "cache": false,
      "persistent": true
    }
  }
}
```

**Why `test.dependsOn: ["build"]` (same-package, no `^`):** Tests must run after the local build completes; they do not need upstream packages to rebuild first if no change occurred.

### Pattern 4: Shared tsconfig.base.json

**What:** Single TypeScript config extended by all packages. Sets `strict`, `moduleResolution: "bundler"`, and `module: "ESNext"`.

```json
{
  "compilerOptions": {
    "target": "ES2020",
    "lib": ["ES2020"],
    "module": "ESNext",
    "moduleResolution": "bundler",
    "declaration": true,
    "declarationMap": true,
    "strict": true,
    "esModuleInterop": true,
    "skipLibCheck": true,
    "isolatedModules": true,
    "resolveJsonModule": true
  }
}
```

**Why `moduleResolution: "bundler"`:** tsup (esbuild) handles resolution; bundler mode allows extensionless imports. Do not use `node16`/`nodenext` here — those require explicit `.js` extensions on every relative import which is incompatible with tsup's default behavior.

### Pattern 5: Per-package tsconfig.json

Each package extends the base and adds its own `include` + `outDir`:

```json
{
  "extends": "../../tsconfig.base.json",
  "compilerOptions": {
    "outDir": "./dist",
    "rootDir": "./src"
  },
  "include": ["src"]
}
```

### Pattern 6: tsup.config.ts

**Server package (pure Node, no React):**

```typescript
// Source: https://github.com/egoist/tsup + https://johnnyreilly.com/dual-publishing-esm-cjs-modules-with-tsup-and-are-the-types-wrong
import { defineConfig } from 'tsup';

export default defineConfig({
  entry: ['src/index.ts'],
  format: ['esm', 'cjs'],
  dts: true,
  sourcemap: true,
  clean: true,
  target: 'es2020',
  treeshake: true,
  external: ['ai', 'zod'],  // peerDeps — never bundle
});
```

**React package:**

```typescript
import { defineConfig } from 'tsup';

export default defineConfig({
  entry: ['src/index.ts'],
  format: ['esm', 'cjs'],
  dts: true,
  sourcemap: true,
  clean: true,
  target: 'es2020',
  treeshake: true,
  external: ['react', 'react-dom', 'ai', '@ai-sdk/react', 'zod'],
});
```

### Pattern 7: package.json exports field (per publishable package)

`types` MUST come first inside each condition block. This is the correct, `publint`-passing pattern:

```json
{
  "name": "@deepagents-nextjs/server",
  "version": "0.1.0",
  "private": false,
  "main": "./dist/index.cjs",
  "module": "./dist/index.js",
  "types": "./dist/index.d.ts",
  "sideEffects": false,
  "exports": {
    ".": {
      "import": {
        "types": "./dist/index.d.ts",
        "default": "./dist/index.js"
      },
      "require": {
        "types": "./dist/index.d.cts",
        "default": "./dist/index.cjs"
      }
    }
  },
  "files": ["dist"],
  "publishConfig": {
    "access": "public"
  }
}
```

**Note on file extensions:** tsup by default emits `.js` for ESM and `.cjs` for CJS (not `.mjs`). The `exports` field above reflects this default. Do not manually set `outExtension` unless a specific reason requires `.mjs` — the default works correctly with Node.js and all modern bundlers.

### Pattern 8: Per-package vitest.config.ts

**Vitest 3.2+ note:** The `vitest.workspace.ts` root file is deprecated in favor of a `projects` array in the root `vitest.config.ts`. However, per-package `vitest.config.ts` files remain valid and are the recommended approach when using Turborepo caching (each package is its own cache unit).

**Server package (Node environment):**

```typescript
import { defineConfig } from 'vitest/config';

export default defineConfig({
  test: {
    environment: 'node',
    include: ['src/**/*.test.ts'],
  },
});
```

**React package (jsdom environment, for later phases):**

```typescript
import { defineConfig } from 'vitest/config';

export default defineConfig({
  test: {
    environment: 'jsdom',
    include: ['src/**/*.test.ts'],
    setupFiles: ['./src/test/setup.ts'],
  },
});
```

### Pattern 9: Workspace internal dependency references

```json
// packages/react/package.json
{
  "dependencies": {
    "@deepagents-nextjs/server": "workspace:*"
  }
}
```

`workspace:*` always resolves to the local package, preventing version drift during development.

### Anti-Patterns to Avoid

- **Using `"pipeline"` key in turbo.json:** Deprecated in Turborepo v2; use `"tasks"` instead.
- **Installing `turborepo` package instead of `turbo`:** The npm package is `turbo`, not `turborepo`.
- **`"type": "module"` at repo root:** Forces all `.js` files to ESM, breaks CJS config files (e.g., `eslint.config.mjs` works but `vitest.config.js` may not). Set `"type"` per-package in `dist/` only via `exports` field routing.
- **Using `tsconfig paths` aliases for internal packages:** Path aliases break outside the monorepo and confuse bundlers. Use `workspace:*` protocol and proper package boundaries instead.
- **TypeScript project references (`"composite": true`):** Turborepo's own docs (2025) explicitly state "you might not need TypeScript project references" — the `turbo build` + `dependsOn` ordering replaces the need for them in most library monorepos.
- **`vitest.workspace.ts` root file:** Deprecated in Vitest 3.2+; use `test.projects` in root `vitest.config.ts` if a unified runner is needed, or per-package configs with Turborepo.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Build ordering across packages | Custom Makefile or shell scripts with manual dep tracking | `turbo build` with `dependsOn: ["^build"]` | Turborepo handles topological sort, parallelism, and content-aware caching automatically |
| Dual ESM/CJS output | Custom esbuild script with manual entry points | `tsup` with `format: ["esm", "cjs"]` | tsup handles `.d.ts`, `.d.cts`, sourcemaps, peer dep externals, and tree-shaking in one config |
| Package exports validation | Manual `package.json` review | `publint` + `attw` | These tools catch all known TypeScript/Node.js resolution edge cases; human review misses subtle ordering issues |
| TypeScript config inheritance | Duplicating `compilerOptions` per package | `tsconfig.base.json` with per-package `extends` | Ensures strict mode consistency; one place to update compiler options |
| Internal package linking during dev | `npm link` or relative `file:` paths | `workspace:*` protocol | `workspace:*` is stable across pnpm upgrades; `file:` creates copies instead of symlinks |

**Key insight:** This entire phase is configuration — every problem in the domain has an established tooling solution. Custom scripts in this layer add maintenance burden with zero benefit.

## Common Pitfalls

### Pitfall 1: `turbo.json` using `"pipeline"` key instead of `"tasks"`

**What goes wrong:** Turborepo v2 removed `"pipeline"` and replaced it with `"tasks"`. Using the old key generates deprecation warnings and will break in a future version.

**Why it happens:** Most tutorials and StackOverflow answers still show the v1 schema. The `create-turbo` scaffold generates the correct v2 schema but manually written configs often copy old examples.

**How to avoid:** Always use `"tasks"` in `turbo.json`. Verify by running `turbo build --dry` — it will warn if the schema is wrong.

**Warning signs:** Turborepo prints "Pipeline is deprecated" or "Unknown field `pipeline`" on any `turbo` command.

### Pitfall 2: `exports` field order — `types` not first

**What goes wrong:** TypeScript cannot find declaration files. Consumers see "Could not find a declaration file for module" errors even though `.d.ts` files exist in `dist/`.

**Why it happens:** The `exports` field is order-sensitive. TypeScript looks for the `types` key first inside each condition block. If `default` or `import` appears before `types`, TypeScript ignores it.

**How to avoid:** Always order as `types` → `default` inside each condition. Run `npx publint` after every `package.json` change.

**Warning signs:** `npx publint` reports a warning; consumer TypeScript projects show implicit `any` on package imports.

### Pitfall 3: Installing `turborepo` package instead of `turbo`

**What goes wrong:** The npm package `turborepo` is an outdated stub. The actual CLI is the `turbo` package.

**Why it happens:** The product is named "Turborepo" but the npm package is `turbo`. Easy to install the wrong one.

**How to avoid:** `pnpm add -D turbo -w`. Never `turbo@latest` via `turborepo`.

**Warning signs:** `turbo --version` fails or shows a very old version number.

### Pitfall 4: `sideEffects: false` omitted from package.json

**What goes wrong:** Consumer bundlers (Next.js webpack, Vite) cannot tree-shake the package. A consumer importing only one export pulls in the entire package.

**Why it happens:** Library authors forget to opt out of the default `sideEffects: true` assumption.

**How to avoid:** Set `"sideEffects": false` in both `packages/server/package.json` and `packages/react/package.json` during skeleton creation — not as an afterthought.

**Warning signs:** Consumer bundle analyzer shows the entire package included even for single named-export imports.

### Pitfall 5: `"type": "module"` at the repo root

**What goes wrong:** All `.js` files in the monorepo root are treated as ESM. Config files that use CommonJS `require()` syntax (older ESLint configs, some Vitest setups) break silently.

**Why it happens:** Adding `"type": "module"` to the root `package.json` feels correct for a modern TypeScript project but affects every file in the repo.

**How to avoid:** Do not set `"type"` in the root `package.json`. Use `.mjs`/`.cjs` extensions or the `exports` field to control ESM/CJS per package at publish time.

**Warning signs:** `eslint.config.js` or `vitest.config.js` fails to load at the root level with "require is not defined in ES module scope".

### Pitfall 6: Vitest workspace file deprecation

**What goes wrong:** Using `vitest.workspace.ts` (Vitest 2.x/3.1 pattern) generates deprecation warnings in Vitest 3.2+ and will be removed in a future version.

**Why it happens:** Most documentation and tutorials still show the workspace file pattern.

**How to avoid:** For this phase, use per-package `vitest.config.ts` files only — no root workspace file needed. Turborepo's per-package test caching makes the workspace file unnecessary anyway.

**Warning signs:** Vitest prints "workspace file is deprecated" during `vitest run`.

## Open Questions

1. **tsup ESM output extension: `.js` vs `.mjs`**
   - What we know: tsup default emits `.js` for ESM output; STACK.md shows `.mjs` extension in the `exports` field example
   - What's unclear: Whether the project will use `outExtension` to force `.mjs` for clarity, or accept `.js` with ESM semantics
   - Recommendation: Use tsup defaults (`.js` for ESM, `.cjs` for CJS) — the `exports` field routing makes the format unambiguous to tools; `.mjs` adds no practical benefit in this repo

2. **ESLint configuration scope in this phase**
   - What we know: ESLint v9 flat config is the standard; the phase description does not explicitly mention ESLint
   - What's unclear: Whether ESLint config should be set up in this phase or deferred to a later phase
   - Recommendation: Create a minimal root `eslint.config.mjs` in this phase as part of the monorepo skeleton; defer complex rule tuning to later phases

3. **`apps/example` Next.js version**
   - What we know: STACK.md mentions Next.js 15 as the example app framework
   - What's unclear: Whether the example app skeleton is created in this phase or Phase v1.0-04
   - Recommendation: Create an empty placeholder `apps/example/package.json` with `"private": true` in this phase so Turborepo knows the workspace exists and can include it in the build graph; defer the full Next.js scaffold to Phase v1.0-04
