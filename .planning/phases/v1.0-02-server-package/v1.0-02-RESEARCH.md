## User Constraints (from CONTEXT.md)

### Locked Decisions

#### transforms pipeline composition
- User-provided `transforms?` is **appended after** `defaultTransforms` — the messageId strip always runs unless the user explicitly bypasses it
- `defaultTransforms` is exported as a named export so power users can do full replacement: `createDeepAgentsHandler({ transforms: [...defaultTransforms, myTransform] })`
- This guarantees protocol compliance (SRV-04) out of the box for the two-line setup goal (SRV-01)
- Pipeline signature: `(frame: SseFrame) => SseFrame | null` — null drops the frame

#### getToken auth behavior (fail-open)
- `getToken` returns null/undefined → proxy without Authorization header (let backend decide)
- `getToken` throws → propagate the error (do not swallow; consumer is responsible for error handling in getToken)
- `getToken` not provided → forward all client request headers as-is (same as stsfront source)
- `getToken` returns a string → inject as `Authorization: Bearer {token}`, replacing any client-provided Authorization header
- Rationale: handler is a transport layer, not a policy engine; auth enforcement belongs in Next.js middleware

#### Header forwarding
- Forward all client request headers except hop-by-hop: `host`, `content-length`, `transfer-encoding`, `connection`
- This matches the stsfront source exactly and is the correct proxy pattern
- Response headers: always set `Content-Type: text/event-stream`, `Cache-Control: no-cache, no-transform`, `X-Accel-Buffering: no`
- Forward `x-vercel-ai-ui-message-stream` from backend response (required by AI SDK v6 client)

#### Error handling
- Backend unreachable (fetch throws) → return `new NextResponse('upstream error', { status: 502 })`
- Non-2xx backend response with no body → return `new NextResponse(null, { status: backendResponse.status })`
- Mid-stream error (ReadableStream error) → `controller.error(err)` breaks the stream; log to `console.error`
- Plain text error bodies (not JSON) — matches stsfront source and keeps the error response simple

#### SseFrameAccumulator design
- Buffer accumulates raw chunks, splits on `\n\n` (SSE frame boundary)
- Last element after split is kept as pending buffer (incomplete frame)
- On stream done: flush any remaining buffer content
- This is an extraction of the inline buffering logic already in stsfront route.ts

### Claude's Discretion
- Exact TypeScript type names for `SseFrame`, `SseTransform` — follow tsup/TypeScript conventions
- Whether `SseFrameAccumulator` is a class or a function returning closures
- How to structure the `defaultTransforms` array (single transform or multiple)
- Whether to expose a `createSseTransformStream()` helper or keep it internal

### Deferred Ideas (OUT OF SCOPE)
- Configurable retry policy on backend connection failure (exponential backoff) — V2-STR-02
- Debug logging mode for SSE frames in development — V2-DX-01
- Cookie-based token extraction helpers — V2-AUTH-01
- Stream reconnection via `experimental_resume` — V2-STR-01 (blocked on AI SDK upstream bugs)

## Summary

This phase ports a known-working SSE proxy (`stsfront/next-app/app/api/chat/stream/route.ts`) into a publish-ready package with a configurable handler factory. The source is ~135 lines of TypeScript and the port is primarily a refactoring exercise — extracting inline logic into named exports, adding a `createDeepAgentsHandler()` factory, and wiring up the `transforms[]` pipeline.

The primary risk is not implementation complexity but **correct TypeScript export structure** (tsup dual ESM/CJS, correct `.d.ts`/`.d.mts` pair) and **test coverage** that validates the SSE frame assembly invariant under split-chunk scenarios. The package skeleton from Phase v1.0-01 is already in place — `packages/server/src/index.ts` exports only a `VERSION` stub and the tsup/vitest configs are wired.

The transforms pipeline is a pure function chain over `SseFrame` objects — no state machine needed, no library dependency. All implementation fits in `src/index.ts` (or split across a small `src/` structure). The `SseFrameAccumulator` is the most testable isolated unit: it must correctly handle the split-chunk edge case that the source file's inline buffer already solves.

**Primary recommendation:** Port `route.ts` to `createDeepAgentsHandler()` + named exports in three steps: (1) types + accumulator, (2) transforms pipeline, (3) handler factory. Each step independently testable with vitest.

## Architecture Patterns

### Recommended Project Structure
```
packages/server/src/
├── index.ts          # Public API: createDeepAgentsHandler, defaultTransforms, types
├── accumulator.ts    # SseFrameAccumulator — frame boundary buffering
├── transforms.ts     # defaultTransforms array + stripMessageId transform
└── handler.ts        # createDeepAgentsHandler() factory function
```

**Alternative (acceptable):** All in `index.ts` if total lines < 200. Given source is ~135 lines, a single-file approach is also fine — Claude's discretion.

### Pattern 1: Handler Factory
**What:** `createDeepAgentsHandler(options)` returns a `POST` async function compatible with Next.js App Router route handlers.
**When to use:** Always — this is the primary public API surface.
**Example:**
```typescript
// Consumer usage (the two-line goal):
import { createDeepAgentsHandler } from '@deepagents-nextjs/server'
export const POST = createDeepAgentsHandler({ backendUrl: process.env.BACKEND_URL! })
```

### Pattern 2: Transforms Pipeline
**What:** `[...defaultTransforms, ...userTransforms]` applied per SSE frame. Each transform returns `SseFrame | null` — null drops the frame.
**When to use:** Every frame that passes through `SseFrameAccumulator` runs through the pipeline.
**Example:**
```typescript
type SseTransform = (frame: SseFrame) => SseFrame | null

const defaultTransforms: SseTransform[] = [stripMessageIdTransform]

// User-provided appended after:
const allTransforms = [...defaultTransforms, ...(options.transforms ?? [])]
```

### Pattern 3: SseFrameAccumulator (extracted from source)
**What:** Stateful buffer that splits raw decoded bytes into complete SSE frames on `\n\n` boundaries.
**Source origin:** `let buffer = ''` + `buffer.split('\n\n')` + `buffer = frames.pop() ?? ''` in `route.ts`.
**Example (class form):**
```typescript
class SseFrameAccumulator {
  private buffer = ''
  push(chunk: string): string[] {  // returns complete frames
    this.buffer += chunk
    const parts = this.buffer.split('\n\n')
    this.buffer = parts.pop() ?? ''
    return parts
  }
  flush(): string[] {  // call on stream end
    const remaining = this.buffer
    this.buffer = ''
    return remaining ? [remaining] : []
  }
}
```

### Anti-Patterns to Avoid
- **Bundling `next` as a direct dependency:** Must be `peerDependencies` — consumers provide Next.js; bundling it causes duplicate module issues.
- **Swallowing `getToken` errors:** CONTEXT.md locks this: if `getToken` throws, propagate — don't wrap in try/catch.
- **Removing the `@ts-expect-error` duplex comment:** The `duplex: 'half'` option is required for Node 18 fetch streaming bodies; the comment must be preserved as documentation.
- **Regex-replacing SSE frames on raw bytes:** The source explicitly notes this fails on chunk-split frames. Always buffer first.

## Common Pitfalls

### Pitfall 1: `next` in `dependencies` instead of `peerDependencies`
**What goes wrong:** Bundle size bloat; `npm ls next` shows duplicate in consumer apps; publint will warn.
**Why it happens:** Auto-added by `npm install next` — lands in `dependencies` by default.
**How to avoid:** Add `"next": ">=14.0.0"` to `peerDependencies` in `package.json`.
**Warning signs:** `npx publint` reports `next` as bundled dependency.

### Pitfall 2: Missing `@ts-expect-error` on `duplex: 'half'`
**What goes wrong:** TypeScript strict mode error on fetch options; CI breaks.
**Why it happens:** Node 18's `fetch` type definitions don't include `duplex`.
**How to avoid:** Keep `// @ts-expect-error — Node 18 fetch needs duplex for streaming bodies` exactly as in source.

### Pitfall 3: `TextDecoder` not using `{ stream: true }`
**What goes wrong:** Multi-byte UTF-8 characters split across chunk boundaries get corrupted.
**Why it happens:** Without `stream: true`, the decoder flushes its internal state on each call.
**How to avoid:** Always `decoder.decode(value, { stream: true })` — matches source exactly.

### Pitfall 4: Forgetting to flush accumulator on stream `done`
**What goes wrong:** Last SSE frame (often the `[DONE]` frame) is silently dropped if it arrives without a trailing `\n\n`.
**Why it happens:** Django backend may not add a trailing `\n\n` after the final event.
**How to avoid:** Always call `accumulator.flush()` in the `if (done)` branch before `controller.close()`.

### Pitfall 5: tsup `dts` generates `.d.ts` but not `.d.mts`
**What goes wrong:** `import.types` in `exports` field points to `.d.mts` which doesn't exist; TypeScript resolution fails for ESM consumers.
**Why it happens:** Default tsup `dts: true` generates a single `.d.ts`; v1.0-01 already solved this with `outExtension` — but the `dts` option needs verification.
**How to avoid:** Run `turbo build` and verify `dist/` contains both `index.d.ts` and `index.d.mts` after implementation. The v1.0-01 tsup config already handles this via `dts: true` — the DTS plugin mirrors `outExtension` automatically in tsup ≥8.

### stripMessageId transform (ported from transformSseFrame)
```typescript
// Source: stsfront/next-app/app/api/chat/stream/route.ts transformSseFrame()
function stripMessageIdTransform(frame: SseFrame): SseFrame | null {
  const transformed = frame.raw
    .split('\n')
    .map((line) => {
      if (!line.startsWith('data: ')) return line
      const raw = line.slice(6)
      if (raw === '[DONE]') return line
      try {
        const parsed: unknown = JSON.parse(raw)
        if (
          parsed !== null &&
          typeof parsed === 'object' &&
          (parsed as Record<string, unknown>).type === 'finish' &&
          'messageId' in parsed
        ) {
          const { messageId: _drop, ...rest } = parsed as Record<string, unknown>
          return `data: ${JSON.stringify(rest)}`
        }
      } catch {
        // Non-JSON data line — pass through as-is
      }
      return line
    })
    .join('\n')
  return { raw: transformed }
}
```

## Open Questions

1. **Does `next` need to be in `devDependencies` as well as `peerDependencies`?**
   - What we know: `peerDependencies` declares the contract for consumers; `devDependencies` is needed for local type resolution in the package itself
   - What's unclear: The v1.0-01 skeleton doesn't add `next` at all — we need it for `NextRequest`/`NextResponse` types
   - Recommendation: Add `"next": ">=14.0.0"` to `peerDependencies` AND `devDependencies` (standard pattern for typed peers)

2. **Should `SseFrame` wrap raw string or parsed lines?**
   - What we know: CONTEXT.md leaves this to Claude's discretion; the source works on raw frame strings
   - Recommendation: `{ raw: string }` wrapper — minimal overhead, extensible later for parsed fields without a breaking change
