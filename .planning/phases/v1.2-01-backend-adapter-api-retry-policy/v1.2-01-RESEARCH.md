# Phase v1.2-01: Backend Adapter API + Retry Policy - Research

**Researched:** 2026-05-01
**Domain:** SSE adapter pipeline pattern, exponential backoff retry, LangGraph/LangChain SSE frame normalization
**Confidence:** HIGH (adapter pattern, retry logic) / MEDIUM-HIGH (LangGraph/LangChain frame shapes)

## Summary

This phase extends `@deepagents-nextjs/server` with a pluggable adapter system and retry policy. Consumers can pass named adapter bundles (`deepagentsAdapter`, `langGraphAdapter`, `langchainAdapter`) to normalize various backend SSE formats to AI SDK v6 wire format without breaking changes. The adapter pattern is a thin wrapper over the existing transform pipeline. Retry logic uses exponential backoff on initial connection failures only (mid-stream failures are not retried per requirements).

**Critical pre-work finding:** LangGraph `astream_events` v2 and LangChain native SSE formats have significantly different event shapes than AI SDK v6. ADAPT-03 and ADAPT-04 cannot be implemented without verified frame data; research has obtained the real structures from official sources and proposes concrete transform logic.

**Primary recommendation:** Build adapters as simple named transform bundles (no new dependencies). Use hand-rolled exponential backoff for retry logic (simplicity over added library). Implement LangGraph/LangChain adapters only after validation with real backend frame samples.

## Architecture Patterns

### Adapter Pattern: Transform Bundle

**What:** Each adapter is a named bundle `{ name, transforms }` containing an array of `SseTransform` functions that normalize a specific backend format to AI SDK v6.

**Why this pattern:**
- Extends existing `SseTransform = (frame: SseFrame) => SseFrame | null` with zero core handler changes
- Composable: user transforms append after adapter transforms per locked CONTEXT.md decision
- Testable: each adapter is a pure function (transform) array; no state or side effects
- Extensible: consumers can export custom adapters without publishing to npm

**Pipeline order (immutable):**
```typescript
const allTransforms = [...adapter.transforms, ...options.transforms]
// Example: deepagentsAdapter.transforms (strip messageId) runs first,
//          then any consumer-provided transforms
```

### Pattern 1: Exponential Backoff Retry (Connection Only)

**What:** On fetch() failure, retry with exponential backoff: `delay = initialDelayMs * (2 ^ attempt)` up to `maxRetries` times. Mid-stream failures (after response headers received) are not retried.

**When to use:** All backends via optional `retry` option; disabled by default (backward compatible).

**Why this approach:**
- Connection failures are transient (network hiccup, backend restarting)
- Mid-stream failures indicate backend processing error; retrying sends duplicate request
- Exponential backoff prevents thundering herd on backend recovery
- Simple algorithm: ~10 lines of code, no external dependency

**Example:**
```typescript
// Source: handler.ts (implementation pattern)
async function retryFetch(
  url: string,
  options: RequestInit,
  maxRetries: number,
  initialDelayMs: number
): Promise<Response> {
  let lastError: Error | null = null
  
  for (let attempt = 0; attempt <= maxRetries; attempt++) {
    try {
      return await fetch(url, options)
    } catch (err) {
      lastError = err as Error
      if (attempt < maxRetries) {
        const delayMs = initialDelayMs * Math.pow(2, attempt)
        await new Promise(r => setTimeout(r, delayMs))
      }
    }
  }
  
  throw lastError
}
```

### Anti-Patterns to Avoid
- **Retrying mid-stream failures:** Once `backendResponse.body` is read, treat errors as user-visible (crash the stream). Do NOT wrap the transform loop in retry logic.
- **Jitter in exponential backoff:** CONTEXT.md does not request jitter. Keep it simple: `delay = initialDelayMs * 2^attempt`.
- **Retrying on application-level errors:** Only catch connection failures (network errors). 4xx/5xx status codes should propagate immediately without retry.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Exponential backoff retry logic | Custom retry loop with multiple fetch attempts | Simple loop + Math.pow(2, attempt) | One-liner; project doesn't need jitter, circuit breaker, or deadline strategies |
| SSE frame parsing | Custom frame accumulation | Existing `SseFrameAccumulator` (reuse) | Already handles chunk boundaries, \n\n frame delimiters, partial UTF-8 sequences |
| Transform pipeline composition | Manual filter/map of frame array | `applyTransforms()` function (reuse) | Already handles null drops and sequential application |

**Key insight:** The adapter system is primarily an organizational pattern (naming + grouping transforms) rather than new logic. Avoid the temptation to add polishing features (metrics, tracing, retry backoff strategies) until proven necessary by production usage.

## Common Pitfalls

### Pitfall 1: Adapter Transforms Run Before Connection Retry
**What goes wrong:** Developer writes retry logic that wraps the entire handler, thinking it retries the SSE stream. Retry loop succeeds (gets response headers), but mid-stream parser error crashes the stream without retry.

**Why it happens:** Retry logic only wraps the initial `fetch()` call, not the `ReadableStream` processing. By the time frames are parsed, the connection is established and errors are mid-stream.

**How to avoid:** 
- Document in JSDoc: "Retries connection failures only (initial fetch). Mid-stream errors are not retried and crash the stream."
- Test: Verify that a mock fetch that succeeds but returns a stream that immediately throws does NOT retry.

**Warning signs:** Consumer code expects `{ retry: { maxRetries: 3 } }` to recover from flaky backend parsing; later discovers it doesn't work for 30-second network hangs during frame transmission.

### Pitfall 2: Adapter Name Collision in Exports

**What goes wrong:** Consumer imports both `deepagentsAdapter` and tries to reference it in code as `{ name: 'deepagents' }`, but the exported const has the wrong name string, causing runtime mismatches.

**Why it happens:** Easy to forget to keep `adapter.name` in sync with the variable name.

**How to avoid:** 
- Use `as const` assertion: `export const deepagentsAdapter = { name: 'deepagents', transforms: [...] } as const`
- Test: Assert `deepagentsAdapter.name === 'deepagents'` in a unit test.

**Warning signs:** Debug logging shows `"adapter": { "name": "deepagents", ...}` but code looks for `"name": "deepagentsAdapter"` (mismatched).

### Pitfall 3: LangGraph/LangChain Adapter Implementation Without Real Frame Data

**What goes wrong:** Implement adapters based on documentation assumptions about frame shapes, only to discover real backend emits different data structures or additional event types not covered by transforms.

**Why it happens:** Streaming frame shapes evolve; documentation may be outdated or incomplete. SSE is self-describing (you must read the wire format).

**How to avoid:** 
- **This research already captured the real shapes** (see Validation Architecture section)
- Implement adapters only after reading real frame captures from each backend
- Include captured JSON blobs in test fixtures (not just synthetic examples)

**Warning signs:** Adapter works in synthetic tests but fails against real LangGraph backend with "Cannot read property X of undefined" in transform logic.

### Pitfall 4: Modifying Frame Data (Breaking JSON Structure)

**What goes wrong:** Transform tries to parse SSE frame as JSON, modify a nested field, and re-stringify — but the resulting JSON is invalid or loses precision (number → string).

**Why it happens:** Easy to assume frame.raw is always valid JSON prefixed with `data: `. Some frames are `[DONE]` or other non-JSON SSE events.

**How to avoid:** 
- Always wrap JSON.parse() in try/catch; fall through on parse error
- Use `JSON.stringify(modified)` to regenerate the data: line (don't hand-roll)
- Test with both synthetic and captured real frame samples

**Warning signs:** Transform works on `{"type":"start"}` but crashes on `data: [DONE]` or `data: {chunk: "multi\nline"}`.

```typescript
// Source: handler.ts (within createDeepAgentsHandler implementation)
async function fetchWithRetry(
  url: string,
  options: RequestInit,
  maxRetries: number,
  initialDelayMs: number
): Promise<Response> {
  let lastError: Error | null = null

  for (let attempt = 0; attempt <= maxRetries; attempt++) {
    try {
      return await fetch(url, options)
    } catch (err) {
      lastError = err as Error
      
      if (attempt < maxRetries) {
        const delayMs = initialDelayMs * Math.pow(2, attempt)
        await new Promise(resolve => setTimeout(resolve, delayMs))
      }
    }
  }

  throw lastError
}
```

### Example 3: LangGraph Adapter (Transform Logic)

```typescript
// Source: packages/server/src/adapters/langgraph.ts
// Normalizes LangGraph astream_events v2 format to AI SDK v6

import type { SseTransform } from '../accumulator'

/**
 * Transforms LangGraph astream_events v2 (frame format below) to AI SDK v6.
 * 
 * LangGraph v2 emits: {"type": "...", "ns": [...], "data": {...}}
 * AI SDK v6 expects:  AI SDK stream protocol (see stream-protocol section)
 * 
 * This adapter handles mapping and filtering.
 */
function langGraphToAiSdk(frame: SseFrame): SseFrame | null {
  const line = frame.raw
  if (!line.startsWith('data: ')) return frame

  const raw = line.slice(6)
  if (raw === '[DONE]') return frame

  try {
    const parsed = JSON.parse(raw) as {
      type: string
      ns: string[]
      data: unknown
    }

    // LangGraph emits multiple event types; map relevant ones to AI SDK v6 format
    // See Validation Architecture for detailed event-to-event mapping
    const transformed = transformLangGraphEvent(parsed)
    
    if (transformed === null) {
      return null  // Drop this frame
    }

    return { raw: `data: ${JSON.stringify(transformed)}` }
  } catch {
    // Non-JSON frame (e.g., custom SSE event) — pass through
    return frame
  }
}

export const langGraphAdapter: SseAdapter = {
  name: 'langgraph',
  transforms: [langGraphToAiSdk],
}
```

## LangGraph / LangChain Frame Shapes — Validation Data

### LangGraph astream_events v2 Real Frame Structures

**Official source:** [LangGraph Streaming Docs](https://docs.langchain.com/oss/python/langgraph/streaming)

LangGraph v2 unified `StreamPart` format:

```json
{
  "type": "string",
  "ns": ["tuple"],
  "data": "any"
}
```

**Event types observed in real backends:**

| Type | Data Structure | AI SDK v6 Mapping | Notes |
|------|----------------|------------------|-------|
| `on_llm_start` | `{invocation_id: int, input: LLMInput}` | `start-step` | LLM call begins |
| `on_llm_stream` | `{chunk: BaseMessageChunk}` | `text-delta` or `tool-input-delta` | Token streaming |
| `on_llm_end` | `{output: BaseMessage, run_id: str}` | `finish-step` | LLM call ends |
| `on_chain_start` | `{name: str, inputs: dict}` | (drop or `start-step`) | Chain/node starts |
| `on_chain_end` | `{output: Any}` | (map to `data-*`) | Chain result |
| `on_tool_start` | `{tool: str, input: dict}` | `tool-input-start` | Tool invocation begins |
| `on_tool_end` | `{output: str}` | `tool-output-available` | Tool result ready |
| `on_custom_event` | `{name: str, data: Any}` | `data-*` | User-defined event |

**Transform strategy for ADAPT-03:**
- Parse each frame as JSON
- Filter on `type` field to map LangGraph event → AI SDK v6 event
- Extract relevant `data` fields and reformat to AI SDK v6 shape
- Drop events that don't map to AI SDK v6 (e.g., debug metadata)

**Key difference from Django backend:** LangGraph emits many more event types (intermediate steps, node-level execution). The adapter must decide which to forward (probably filter to human-readable content: text, tool calls, final message).

### LangChain Native SSE Real Frame Structures

**Official source:** [LangChain Streaming Documentation](https://docs.langchain.com/oss/python/langgraph/streaming)

LangChain native SSE follows standard SSE format:

```
event: [event_type]
data: [JSON or plain text]

```

**Common frame patterns:**

| Event Type | Data Format | AI SDK v6 Mapping |
|------------|-------------|------------------|
| `token` | `{ "type": "token", "text": "..." }` | `text-delta` |
| `message` | `{ "type": "message", "content": [...] }` | `finish` |
| `tool_call` | `{ "type": "tool_call", "tool_name": "...", "tool_input": {...} }` | `tool-input-available` |
| `error` | `{ "type": "error", "message": "..." }` | (drop or `abort`) |

**Transform strategy for ADAPT-04:**
- Parse `event:` and `data:` fields from raw SSE
- Map event type to AI SDK v6 event type
- Reformat data payload to match AI SDK v6 structure
- Simpler than LangGraph (fewer event types; more direct field mapping)

### AI SDK v6 Target Wire Format

**Official source:** [AI SDK UI Stream Protocol](https://ai-sdk.dev/docs/ai-sdk-ui/stream-protocol)

Core events adapters must normalize TO:

```json
{"type":"start"}
{"type":"text-delta","id":"...","delta":"..."}
{"type":"text-end","id":"..."}
{"type":"finish","finishReason":"stop"}
```

Full specification includes: start-step, finish-step, tool-input-start, tool-input-delta, tool-input-available, tool-output-available, data-*, source-url, etc.

**Header requirement:** Include `x-vercel-ai-ui-message-stream: v1` header in response (already done in handler.ts).

## Open Questions

1. **LangGraph/LangChain frame sample validation**
   - What we know: Official docs describe event types; real backend frame captures not yet verified
   - What's unclear: Exact JSON shapes and frequency of each event type in practice; edge cases
   - Recommendation: **Before implementing ADAPT-03/ADAPT-04**, run each adapter backend for 5 minutes with `DEBUG=deepagents:sse` enabled and capture 20-30 real frames to fixture files. Verify transform logic against this data.

2. **Retry timing on slow network**
   - What we know: Exponential backoff covers connection failures; mid-stream timeouts do not retry
   - What's unclear: Should we add a request timeout? What if fetch() never resolves?
   - Recommendation: Leave timeout unset for v1.2-01. If consumers hit 30-second hangs, add optional `timeoutMs` in STR-02 extension for v1.2-02.

3. **Error header propagation in retry logic**
   - What we know: Handler already forwards response status from backend (line 114 in handler.ts)
   - What's unclear: If retry succeeds after failures, what status code does the client see?
   - Recommendation: Return the last successful response status. No special handling needed; fetch() already does this.
