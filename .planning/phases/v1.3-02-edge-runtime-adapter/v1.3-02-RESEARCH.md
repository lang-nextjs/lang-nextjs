# Phase v1.3-02: Edge Runtime Adapter - Research

**Researched:** 2026-05-02
**Domain:** Edge runtime handler factories (Deno Deploy, Cloudflare Workers), Web Streams API, ESM-only packaging
**Confidence:** HIGH

## Summary

Phase v1.3-02 ships `@deepagents-nextjs/edge`, a new package providing SSE proxy handlers for Deno Deploy and Cloudflare Workers using only Web Streams API (no Node.js built-ins). The package mirrors the established patterns from v1.2-04 (SvelteKit) and v1.2-05 (Remix) adapters, with critical differences: ESM-only output (ES2022 target), copied SseFrameAccumulator to avoid `next` peerDep leakage, and dual handler factories (`createDenoHandler`, `createCloudflareHandler`) optimized for their respective runtimes.

The Cloudflare Workers handler requires prominent documentation of a known SSE buffering issue causing TTFB > 10s in production; this phase marks it EXPERIMENTAL. Testing must account for Web Streams API differences between Deno Deploy (native support) and Cloudflare Workers (polyfilled/transpiled). ESM-only packaging passes publint + attw by setting `"type": "module"` and proper exports field structure; no dual CJS/ESM.

**Primary recommendation:** Ship createDenoHandler as stable, createCloudflareHandler as experimental with TTFB caveat. Use `target: "es2022"` in tsup with ESM-only format. Copy SseFrameAccumulator. Test via Node.js native Web Streams (18+) in unit suite; include wrangler preview deployment smoke test for Cloudflare TTFB validation.

### Pattern 1: Deno Deploy Handler Factory
**What:** `createDenoHandler(options)` returns a handler for Deno Deploy that proxies SSE from upstream backend. Handler uses only Web Streams (ReadableStream, TextEncoderStream, TextDecoder). Configuration via Deno.env.get().

**When to use:** Deploying DeepAgents to Deno Deploy.

**Example:**
```typescript
// Source: Deno Deploy documentation + Web Streams API standard
import { createDenoHandler } from '@deepagents-nextjs/edge';

const handler = createDenoHandler({
  backendUrl: Deno.env.get('BACKEND_URL')!,
  adapter: deepagentsAdapter,
});

// Deno Deploy: handler receives (Request) => Promise<Response>
Deno.serve({ port: 3000 }, handler);
```

Key differences from Node.js adapters:
- No `assertNodeRuntime()` needed (Deno is the only runtime)
- `Deno.env.get('VAR')` replaces `process.env.VAR`
- Handler signature: `(request: Request) => Promise<Response>` (Web API std)
- No `fetch(..., { duplex: 'half' })` annotation needed (Deno fetch infers correctly)

### Pattern 2: Cloudflare Workers Handler Factory
**What:** `createCloudflareHandler(options)` returns a handler for Cloudflare Workers that proxies SSE. Configuration via `env` parameter (Cloudflare bindings dict). Marked EXPERIMENTAL due to known SSE buffering issue (TTFB > 10s).

**When to use:** Deploying to Cloudflare Workers (with awareness of TTFB caveat and recommendation to use Deno Deploy instead for streaming workloads).

**Example:**
```typescript
// Source: Cloudflare Workers documentation + Wrangler type generation
import { createCloudflareHandler } from '@deepagents-nextjs/edge';

export default {
  async fetch(request: Request, env: Env): Promise<Response> {
    const handler = createCloudflareHandler({
      backendUrl: env.BACKEND_URL,
      adapter: deepagentsAdapter,
    });
    return handler(request);
  },
};
```

Key differences from Deno:
- Handler receives `(request: Request, env: Env)` args; env passed via options
- env binding types generated via `wrangler types` (no manual Env interface)
- Known issue: Response layers cause buffering; direct Response(ReadableStream) pattern required
- TTFB > 10s in production documented prominently in README; recommend Deno Deploy

### Pattern 3: Web Streams Transform Pipeline (Shared)
**What:** Both handlers reuse the same SSE frame accumulation and transform logic from v1.2-04/v1.2-05, ensuring consistent frame boundary handling across runtimes.

**When to use:** Inside both handler factories.

**Example:**
```typescript
// Source: Deno Deploy + Cloudflare Workers Web Streams API
const encoder = new TextEncoder();
const decoder = new TextDecoder();
const accumulator = new SseFrameAccumulator();

const transformedStream = new ReadableStream<Uint8Array>({
  async start(controller) {
    const reader = backendResponse.body!.getReader();
    try {
      while (true) {
        const { done, value } = await reader.read();
        if (done) {
          for (const frame of accumulator.flush()) {
            const transformed = applyTransforms(allTransforms, { raw: frame });
            if (transformed !== null) {
              controller.enqueue(encoder.encode(`${transformed.raw}\n\n`));
            }
          }
          controller.close();
          break;
        }
        const chunk = decoder.decode(value, { stream: true });
        for (const frame of accumulator.push(chunk)) {
          const transformed = applyTransforms(allTransforms, { raw: frame });
          if (transformed !== null) {
            controller.enqueue(encoder.encode(`${transformed.raw}\n\n`));
          }
        }
      }
    } catch (err) {
      console.error('[deepagents/edge] mid-stream error', err);
      controller.error(err);
    }
  },
});

return new Response(transformedStream, {
  status: backendResponse.status,
  headers: responseHeaders,
});
```

### Anti-Patterns to Avoid
- **Importing SseFrameAccumulator from @deepagents-nextjs/server:** Creates transitive `next` peerDep in edge consumers. MUST copy.
- **Using Node.js stream or process APIs:** Edge runtimes don't have these; causes bundle bloat and runtime errors.
- **Wrapping Response in multiple layers:** Cloudflare Workers buffering issue; return Response(ReadableStream) directly.
- **Dual format build (ESM + CJS):** ESM-only simpler for edge, sufficient per 2026 practices; Node.js can require() ESM.
- **Custom env binding types:** Use `wrangler types` auto-generation for Cloudflare; simpler than hand-writing Env interface.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| SSE frame boundary accumulation | Custom split logic or regex | SseFrameAccumulator (copied) | TCP chunk boundaries can split mid-frame; regex on raw bytes corrupts frames; accumulator handles incomplete frames correctly |
| Web Streams pipelines | Manual ReadableStream loops | ReadableStream.pipeTo() or transformer | Direct loops error-prone; built-in methods handle backpressure, error propagation, cleanup |
| TypeScript env bindings for Cloudflare | Hand-written Env interface | `wrangler types` CLI tool | Auto-generation ensures types match actual bindings; manual Env quickly falls out of sync with wrangler.toml |
| Response headers for SSE proxy | Custom header maps | Standard headers per RFC 9110 + AI SDK marker forwarding | Missed headers (e.g., x-vercel-ai-ui-message-stream) break client-side stream detection |
| Package export configuration | Custom exports field structure | publint validation | exports field has subtle requirements (types first, ./ prefixes, condition order); publint catches >90% of issues |

**Key insight:** Edge runtimes are significantly constraint-different from Node.js. Reuse proven patterns (SseFrameAccumulator, transform pipeline) but don't assume Node.js APIs exist. Web Streams API is the universal lingua franca; embrace it as constraint not limitation.

## Common Pitfalls

### Pitfall 1: Importing Instead of Copying SseFrameAccumulator
**What goes wrong:** Handler imports `SseFrameAccumulator` from `@deepagents-nextjs/server`, which has `next` as a peerDep. Edge consumers now see `next` as transitive peerDep, defeating the purpose of an edge-specific package.

**Why it happens:** Copy-paste shortcut; assumption that internal imports are "free".

**How to avoid:** Follow STATE.md locked decision: copy accumulator.ts verbatim into packages/edge/src/. CI must verify no imports of @deepagents-nextjs/server.

**Warning signs:** publint + attw check shows `next` in dist bundle or dep tree; edge consumers report unexpected `next` peerDep warnings.

### Pitfall 2: Using Node.js Built-ins (process, stream module, fs, etc.)
**What goes wrong:** Code references `process.env`, Node.js streams, or fs APIs. Deno Deploy and Cloudflare Workers don't have these. Code fails at runtime or creates bundle bloat via polyfills.

**Why it happens:** Muscle memory from Node.js package patterns; easy to miss edge-specific config APIs.

**How to avoid:** Use platform-specific getters: `Deno.env.get()` for Deno, `env` parameter for Cloudflare. Never reference `process`, `require()`, Node.js stream module, or fs. Linting: set tsconfig.lib to only ES2022 + DOM (no Node.js types).

**Warning signs:** Bundle analysis shows polyfill code; import errors on handler startup in edge runtime.

### Pitfall 3: Wrapping Response Multiple Times (Cloudflare Buffering)
**What goes wrong:** Handler wraps ReadableStream in multiple Response layers or uses a helper that does so. Cloudflare Workers buffers entire stream before sending, causing TTFB > 10s.

**Why it happens:** Mimicking Hono patterns or assuming multiple Response layers are harmless.

**How to avoid:** Return `new Response(transformedStream, { ... })` directly. Do NOT pass through middleware that re-wraps. Validate: wrangler preview should show <5s TTFB for short streams.

**Warning signs:** Cloudflare TTFB is 10+ seconds; entire stream arrives in one chunk instead of streaming; Hono stream() helper usage.

### Pitfall 4: Forgetting Web Streams Backpressure in Custom Loops
**What goes wrong:** Custom ReadableStream.start(controller) reads upstream without respecting downstream backpressure. Memory usage spikes for large streams; client receives nothing until buffer is full.

**Why it happens:** ReadableStream loops look simple; easy to miss that `await reader.read()` must respect `controller.desiredSize`.

**How to avoid:** Use the pattern: `while (true) { const { done, value } = await reader.read(); ... if (done) break; ... }`. The `getReader()` contract handles backpressure; the pattern shown in sveltekit/remix handlers is correct.

**Warning signs:** Memory usage grows unexpectedly; client receives delayed / buffered response; CPU spikes during streaming.

### Pitfall 5: Cloudflare env Binding Type Mismatches
**What goes wrong:** Handler expects `env.BACKEND_URL` to be string, but user deploys without setting it or as wrong type. Runtime errors or undefined propagation.

**Why it happens:** `wrangler types` auto-generation missed environment or user assumption that env always has keys.

**How to avoid:** Declare options.backendUrl as required in CloudflareHandlerOptions. Document that env.BACKEND_URL must be set in wrangler.toml. Test wrangler preview with mock env values.

**Warning signs:** Handler throws "Cannot read property ... of undefined"; wrangler.toml shows env: { BACKEND_URL: undefined }.

### Pitfall 6: ESM-Only Build Skipping publint Check
**What goes wrong:** tsup config has `format: ['esm']` but package.json still declares `"main"` and `"module"` fields. publint errors are ignored or skipped. publint + attw fail in CI.

**Why it happens:** Copy-paste from dual-format package.json; assumption that ESM config is optional.

**How to avoid:** Remove `"main"` and `"module"` fields; use only `"exports"` field with ESM-only structure. Run `publint` locally before commit. Ensure exports has `"types"` condition first.

**Warning signs:** publint warnings like "should use exports"; attw errors about missing or incorrect types.

## Open Questions

1. **TypeScript types for Cloudflare env parameter**
   - What we know: `wrangler types` generates Env interface from wrangler.toml; types are auto-updated
   - What's unclear: Should CloudflareHandlerOptions accept generic `env: Env` parameter (type-safe but binds to wrangler.toml) or accept `env: Record<string, unknown>` (flexible but loses typing)?
   - Recommendation: Accept generic `env: Env` (strict); document that consumer runs `wrangler types` after adding bindings. Aligns with Cloudflare best practices and Hono/Remix patterns.

2. **Deno.env.get() fallback strategy if BACKEND_URL missing**
   - What we know: Deno.env.get() returns `string | undefined`; handler needs backendUrl
   - What's unclear: Should handler throw immediately (fail-fast) or return 503 response (fail-open per v1.1 decision)?
   - Recommendation: Throw immediately at handler factory creation time (outside request handler). Deno Deploy cold start cost is minimal; fail-fast clarifies intent over silent 503s.

3. **Cloudflare Workers TTFB measurement methodology**
   - What we know: Feb 2026 issue shows TTFB ~10s when Response wrapped in middleware; direct Response pattern fixes it
   - What's unclear: Is <5s TTFB realistic for production Cloudflare, or should we accept 5-10s as acceptable?
   - Recommendation: Target <5s TTFB for short streams (1-5 frames, <1KB each) in preview; document caveat and recommend Deno Deploy for streaming workloads. Mark handler EXPERIMENTAL until real-world production metrics confirm stability.

4. **peerDependencies for edge package**
   - What we know: Edge package has zero runtime dependencies (Web Streams is built-in); adapters (deepagentsAdapter, langGraphAdapter, etc.) are optional
   - What's unclear: Should edge package declare SseTransform type as peerDep from server, or re-export it?
   - Recommendation: Re-export SseTransform and SseFrame types from accumulator.ts (local copy); avoid any cross-package imports. Keep peerDependencies empty; adapters are optional devDeps for consumer testing.

5. **Cloudflare Workers environment fallback / validation**
   - What we know: env bindings must be set in wrangler.toml; wrangler types generates corresponding Env interface
   - What's unclear: Should handler validate that required bindings exist, or let them surface as undefined at runtime?
   - Recommendation: Validate in handler factory: `if (!options.backendUrl) throw new Error(...)`. Follows fail-fast pattern; mirrors Deno approach. Document required env vars in README.
