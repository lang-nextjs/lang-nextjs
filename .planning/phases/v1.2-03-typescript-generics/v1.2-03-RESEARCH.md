# Phase v1.2-03: TypeScript Generics - Research

**Researched:** 2026-05-01  
**Domain:** TypeScript generics with React hooks, Zod schema type inference, discriminated union narrowing  
**Confidence:** HIGH

## Summary

Phase v1.2-03 requires making `useDeepAgentsChat` accept a generic type parameter `TData extends Record<string, ZodTypeAny>` to enable compile-time type narrowing for custom `data-*` message schemas. This is a pure TypeScript enhancement with no runtime cost—existing consumers using zero-generic calls get identical types to v1.1, while advanced consumers get compile-time narrowing.

The core challenge is **type extraction and union extension**: we need to accept a generic mapping of custom data-* types, extract their inferred schemas, and extend the existing discriminated `Message` union with new variants. TypeScript's generic constraints with `extends` and `z.infer<>` patterns from Zod provide the necessary tools; the implementation is straightforward once the constraint and extraction patterns are understood.

**Primary recommendation:** Use a two-parameter generic signature: `useDeepAgentsChat<TData extends Record<string, ZodTypeAny>>()` as the advanced path, with zero-generic calls falling through to the existing `Message` union. Validate the constraint at call sites via TypeScript's built-in `extends` checking—no runtime validation needed. Extend the converter to handle custom data-* types when the hook is parameterized with TData.

### Pattern 1: Generic Constraint with Zod Schemas
**What:** Accept `TData extends Record<string, ZodTypeAny>` where the values are Zod schemas defining custom data-* part schemas.

**When to use:** Any React hook that needs to accept a generic mapping of schema objects and extract their inferred types.

**Example:**
```typescript
// From TypeScript generic constraints handbook and Zod library design patterns
// Source: https://www.typescriptlang.org/docs/handbook/2/generics.html

interface UseDeepAgentsChatOptions<TData extends Record<string, ZodTypeAny> = {}> {
  sessionId: string
  endpoint: string
  getToken?: () => Promise<string | null | undefined> | string | null | undefined
}

export function useDeepAgentsChat<TData extends Record<string, ZodTypeAny> = {}>(
  options: UseDeepAgentsChatOptions<TData>,
): UseDeepAgentsChatReturn<TData> {
  // Hook body
}
```

This constraint ensures:
1. TypeScript rejects non-schema values at the call site (compile-time error if consumer passes `<{ foo: string }>`)
2. The constraint is structural—any ZodType<any, any, any> is accepted
3. Default is `{}` for zero-generic calls

### Pattern 2: Type Extraction and Union Extension
**What:** Extract inferred types from TData schema values using `z.infer<>`, then extend the Message union with custom data-* variants.

**When to use:** Building discriminated unions that accept an input schema map and produce narrowed message types.

**Example:**
```typescript
// Source: Zod type inference patterns from https://github.com/colinhacks/zod#type-inference-from-schemas

// Given TData = { 'data-plan': typeof PlanSchema }
// We need to build: Message | { type: 'data-plan', data: DataPlan }

type CustomDataParts<TData extends Record<string, ZodTypeAny>> = {
  [K in keyof TData]: {
    type: K
    data: z.infer<TData[K]>
  }
}[keyof TData]

type MessageWithCustom<TData extends Record<string, ZodTypeAny>> =
  Message | CustomDataParts<TData>
```

This leverages:
- **Mapped types** `[K in keyof TData]` to iterate schema keys
- **Conditional extraction** `z.infer<TData[K]>` to get the parsed type
- **Union of mapped values** to produce discriminated variants

### Pattern 3: Default Generic Parameter for Backward Compatibility
**What:** Use `= {}` as the default for TData to make zero-generic calls work without change.

**When to use:** Maintaining backward compatibility when introducing generics to an existing API.

**Example:**
```typescript
// When TData = {} (default):
useDeepAgentsChat({ sessionId: 'x', endpoint: '/api' })
// → return type is UseDeepAgentsChatReturn<{}>
// → messages are typed as Message[] (no custom variants)
// → Identical to v1.1 behavior

// When TData is provided:
useDeepAgentsChat<{ 'data-plan': typeof PlanSchema }>({ sessionId: 'x', endpoint: '/api' })
// → return type is UseDeepAgentsChatReturn<{ 'data-plan': typeof PlanSchema }>
// → messages are typed as (Message | { type: 'data-plan', data: DataPlan })[]
// → Custom variants are narrowed at compile time
```

### Anti-Patterns to Avoid
- **Over-constraining with specific Zod types:** Don't use `TData extends Record<string, z.ZodObject<any>>` — this rejects z.record(), z.union(), etc. Use `ZodTypeAny` for maximum flexibility.
- **Runtime validation of TData:** The constraint is compile-time only. No need to add runtime checks—TypeScript already prevents invalid schemas at the call site.
- **Mixing runtime schema maps with generic types:** Don't make TData optional and also accept a runtime `schemas` prop. One source of truth: the generic parameter.
- **Forgetting the default parameter:** If you don't use `= {}`, existing zero-generic call sites will break due to missing type parameter.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Mapping over Zod schema objects to extract types | Custom `extractSchemaTypes(obj)` function or helper | TypeScript's built-in mapped types `[K in keyof TData]` + `z.infer<TData[K]>` | Mapped types are compile-time safe and have zero runtime cost; a custom function would require runtime logic and be error-prone |
| Discriminating on custom data-* type strings | Manual string matching with if/else chains | Discriminated unions with `type: K` discriminant | TypeScript automatically narrows union types on discriminant checks; manual matching is verbose and error-prone |
| Testing generic call sites | Separate test suite for each TData variant | Existing converter test pattern extended with parameterized test cases | Reuse existing test helpers (`makeAssistantMsg`, etc.) with custom data-* parts |
| Validating TData at runtime | A custom validator function on hook entry | TypeScript's `extends` constraint (compile-time only) | Validation happens at call sites during type checking; runtime checks are redundant and add overhead |

**Key insight:** All of the complexity in this phase is **compile-time type work**. No runtime validation, no helper functions, no schema introspection. The hook body stays almost identical—the converter just needs to handle new data-* types when TData is provided.

## Common Pitfalls

### Pitfall 1: Confusing `z.infer<T>` with ZodTypeAny Constraint
**What goes wrong:** Developer adds the generic parameter but doesn't extract types correctly, leading to `{ foo: unknown }` instead of the actual inferred type.

**Why it happens:** `TData extends Record<string, ZodTypeAny>` constrains the *values* to be Zod types, but the *inferred type* comes from `z.infer<TData[K]>`, not from TData[K] directly.

**How to avoid:** Always use `z.infer<TData[K]>` when mapping, not `TData[K]`. The constraint enables type safety; inference extracts the schema's output type.

**Warning signs:** TypeScript shows `{ foo: unknown }` or `any` in hover or diagnostics instead of the actual schema shape.

### Pitfall 2: Breaking Zero-Generic Calls by Forgetting the Default
**What goes wrong:** Adding `<TData extends Record<string, ZodTypeAny>>` without `= {}` makes existing `useDeepAgentsChat({ ... })` calls invalid because TData is required.

**Why it happens:** TypeScript requires all type parameters unless a default is provided.

**How to avoid:** Always include `= {}` in the generic parameter: `<TData extends Record<string, ZodTypeAny> = {}>`. This makes TData optional and defaults to an empty record (no custom variants).

**Warning signs:** Existing test files show TypeScript errors on zero-generic calls after you add the generic parameter.

### Pitfall 3: Accepting the Wrong Zod Constraint Type
**What goes wrong:** Using `ZodSchema` or `ZodType<unknown, unknown>` instead of `ZodTypeAny`, leading to type inference failures for some schema types.

**Why it happens:** Different Zod constraint types have different implications for `z.infer<>`. In Zod v4, `z.Schema` defaults to `ZodType<unknown, unknown, unknown>`, which infers to `unknown`.

**How to avoid:** Use `ZodTypeAny` (which expands to `ZodType<any, any, any>`) as the constraint. It's the broadest and safest choice, and it's what Zod recommends for library authors.

**Warning signs:** `z.infer<TData[K]>` resolves to `unknown` even though the schema is known to have a concrete type.

### Pitfall 4: Not Testing Both Paths (Zero-Generic and Parameterized)
**What goes wrong:** Tests only verify the parameterized generic call, missing regressions in the zero-generic path.

**Why it happens:** Easy to focus on the new feature without regression testing.

**How to avoid:** Test both code paths explicitly:
  - Zero-generic: `useDeepAgentsChat({ sessionId, endpoint })` → verify message types match v1.1
  - Parameterized: `useDeepAgentsChat<{ 'data-plan': typeof PlanSchema }>({ ... })` → verify custom variants are present

**Warning signs:** Zero-generic calls type correctly in manual testing but the type tests don't cover them.

### Pitfall 5: Converter Logic Not Handling Unknown Custom Data-* Types
**What goes wrong:** Hook is parameterized with a custom data-* type, but the converter doesn't know how to parse it, so it warns and drops the data.

**Why it happens:** The converter's `SCHEMA_MAP` only includes the 5 built-in types. Custom types need to be passed to the converter somehow.

**How to avoid:** Pass the custom schema map from TData to the converter at runtime. The converter receives a second parameter (the schemas from TData) and uses it to parse custom data-* parts.

**Warning signs:** Custom data-* parts appear in SSE frames but are missing from the final messages array, with console.warn logs about unsupported types.

## Open Questions

1. **Should custom data-* types coexist with built-in types?**
   - What we know: TData is user-provided; built-in types (error, plan, task, etc.) are always available
   - What's unclear: When both a custom 'data-plan' and the built-in PlanSchema exist in the same stream, which takes precedence?
   - Recommendation: Built-in types always win (they're in the base Message union). Custom types only match if the type string is NOT one of the built-in five. This keeps the contract simple.

2. **Does the converter need runtime access to custom schema values for validation?**
   - What we know: partsToMessages is a pure converter—stateless and independently testable
   - What's unclear: Should we validate custom data-* parts against the schema map, or just assume the server sent valid data?
   - Recommendation: Validate (using `schema.safeParse()`), but silence validation errors with console.warn (same pattern as data-error). Consumers can use Zod's `.catch()` or `.default()` if they want fallback behavior.

3. **How are custom schemas passed to the converter at runtime?**
   - What we know: TData is compile-time; the converter runs at runtime
   - What's unclear: The converter needs the actual Zod schema objects to validate data. How does it get them?
   - Recommendation: Hook extracts the schema map from the generic parameter (requires a second internal parameter), then passes it to partsToMessages. Use a conditional type to build the schema map internally (not exposed to consumers).
