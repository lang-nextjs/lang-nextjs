## Summary

Remix v2 (still the dominant framework as of 2026) exposes `ActionFunctionArgs` with a standard Web Fetch `Request` object — structurally identical to SvelteKit's `RequestEvent.request`. The handler implementation can be near-verbatim from the SvelteKit package, replacing the `RequestEvent` parameter with `ActionFunctionArgs` from `@remix-run/node`.

The critical architectural difference from SvelteKit is on the **client side**. `useFetcher` from `@remix-run/react` is a request/response hook and does **not** natively expose a `ReadableStream` body. It waits for the full response before populating `fetcher.data`. For SSE streaming, the correct pattern is: use `useFetcher.submit()` only for state tracking (loading/submitting flags), and drive SSE consumption with a native `fetch()` + `ReadableStream` loop in `useEffect`. This is the established community workaround for AI streaming in Remix.

The STR-01 conditional (stream reconnection via `experimental_resume`) is **deferred to v1.3**. GitHub issues #6502 and #9707 on the Vercel AI repo are both confirmed open as of 2026-05-02 with no fix available. AI SDK v5 has renamed `experimental_resume` to `resume`/`resumeStream` but the underlying abort-signal incompatibility remains unresolved. Do not plan any STR-01 tasks for this phase.

**Primary recommendation:** Copy the SvelteKit handler pattern for `createDeepAgentsHandler`, substitute `ActionFunctionArgs` for `RequestEvent`. For `useDeepAgentsChat`, use `useState` + `useEffect` + native `fetch()` ReadableStream loop (not `useFetcher.data`) and expose an `useFetcher`-flavored submit trigger for the "useFetcher-based hook" requirement surface.

### Pattern 1: Handler — ActionFunctionArgs as Thin Wrapper Around Request

**What:** `ActionFunctionArgs.request` is a standard Web Fetch `Request`. The handler extracts `args.request`, reads `arrayBuffer()`, builds forwarded headers, and proxies to backend — identical to SvelteKit handler.

**Key difference from SvelteKit:** SvelteKit `RequestEvent` exposes `event.request` (nested). Remix `ActionFunctionArgs` also exposes `args.request` (same nesting). The extraction is identical.

```typescript
// Source: SvelteKit handler.ts pattern + @remix-run/node ActionFunctionArgs type
import type { ActionFunctionArgs } from '@remix-run/node';

export function createDeepAgentsHandler(
  options: RemixHandlerOptions
): (args: ActionFunctionArgs) => Promise<Response> {
  const allTransforms: SseTransform[] = [
    ...(options.adapter?.transforms ?? []),
    ...(options.transforms ?? []),
  ];

  return async function handler(args: ActionFunctionArgs): Promise<Response> {
    assertNodeRuntime();

    const body = await args.request.arrayBuffer();
    const forwardedHeaders = new Headers();
    // ... same header forwarding logic as SvelteKit handler ...
    // getToken receives ActionFunctionArgs (not RequestEvent)
  };
}
```

**getToken signature for Remix:**
```typescript
getToken?: (args: ActionFunctionArgs) => Promise<string | null | undefined> | string | null | undefined;
```

### Pattern 2: useDeepAgentsChat Hook — fetch() Loop, NOT useFetcher.data

**What:** `useFetcher` from `@remix-run/react` is a **request/response** hook. It does NOT expose `ReadableStream` on `fetcher.data` — it buffers the full response before resolving. For SSE streaming, native `fetch()` with `response.body.getReader()` is required.

**The "useFetcher-based" requirement interpretation:** Use `useFetcher` for its state management primitives (`fetcher.state`, `fetcher.submit`) to model the submission lifecycle. Drive the actual stream consumption via native `fetch()` in `useEffect`.

**Correct pattern:**

```typescript
// Source: Community consensus from GitHub discussions/2622, macwright.com/2024, sergiodxa.com
import { useState, useEffect, useRef } from 'react';
import { useFetcher } from '@remix-run/react';

export function useDeepAgentsChat(options: { endpoint: string; sessionId?: string }) {
  const [messages, setMessages] = useState<unknown[]>([]);
  const [status, setStatus] = useState<DeepAgentsStatus>('idle');
  const [error, setError] = useState<Error | null>(null);
  const abortRef = useRef<AbortController | null>(null);

  async function submit(body?: Record<string, unknown>) {
    abortRef.current?.abort();
    const controller = new AbortController();
    abortRef.current = controller;

    setMessages([]);
    setStatus('loading');
    setError(null);

    try {
      const response = await fetch(options.endpoint, {
        method: 'POST',
        signal: controller.signal,
        headers: { 'Content-Type': 'application/json' },
        body: JSON.stringify({ sessionId: options.sessionId, ...body }),
      });

      const reader = response.body!.getReader();
      const decoder = new TextDecoder();
      const accumulator = new SseFrameAccumulator();
      let firstFrame = true;

      while (true) {
        const { done, value } = await reader.read();
        if (done) {
          for (const raw of accumulator.flush()) {
            if (raw.startsWith('data: ')) {
              setMessages(prev => [...prev, JSON.parse(raw.slice(6))]);
              if (firstFrame) { setStatus('streaming'); firstFrame = false; }
            }
          }
          setStatus('done');
          break;
        }
        for (const raw of accumulator.push(decoder.decode(value, { stream: true }))) {
          if (raw.startsWith('data: ')) {
            const payload = JSON.parse(raw.slice(6));
            setMessages(prev => [...prev, payload]);
            if (firstFrame) { setStatus('streaming'); firstFrame = false; }
          }
        }
      }
    } catch (err) {
      if (err instanceof Error && err.name === 'AbortError') return;
      const error = err instanceof Error ? err : new Error(String(err));
      setError(error);
      setStatus('error');
    }
  }

  return { messages, status, error, submit };
}
```

**Why not use useFetcher.data for streaming:** `useFetcher` appends `.data` suffix to requests and waits for the complete response. It uses turbo-stream deserialization (React Router 6.30 + turbo-stream 2.4). This intercepts the SSE stream before it reaches `fetcher.data`. The only path to true streaming is native `fetch()`.

### Anti-Patterns to Avoid

- **Reading `fetcher.data` for stream chunks:** `useFetcher` buffers the full response; it will never yield partial SSE frames. Use native `fetch()`.
- **Using `EventSource` for the hook:** `EventSource` is GET-only. Our endpoint is a POST action.
- **Importing from `@deepagents-nextjs/react`:** The Remix hook is self-contained. Importing from the React package would pull in `@deepagents-nextjs/react`'s Next.js peerDeps via the peerDep chain. Copy the accumulator and state machine locally.
- **Importing from `@deepagents-nextjs/server`:** Would pull in `next` as a peerDep. Copy `SseFrameAccumulator` to `src/accumulator.ts`.
- **`"type": "module"` in package.json:** Monorepo standard is `"type": "commonjs"` + `outExtension` in tsup. Do not deviate.

## Common Pitfalls

### Pitfall 1: useFetcher Intercepts SSE Stream

**What goes wrong:** Developer wires `useFetcher.submit()` and reads `fetcher.data` expecting stream chunks. The hook only fires after the stream closes, returning the buffered full body (or turbo-stream deserialized object).

**Why it happens:** `useFetcher` uses the React Router internal fetch infrastructure which appends `.data` to requests and expects turbo-stream format. `text/event-stream` responses bypass this.

**How to avoid:** Use native `fetch()` for the streaming call. `useFetcher` can optionally be used for state co-location (submitting state flags) but must not be the stream reader.

**Warning signs:** `fetcher.state` jumps from `submitting` to `idle` after stream closes instead of staying `loading` during stream.

### Pitfall 2: Missing `external` in tsup Causes React Bundling

**What goes wrong:** tsup bundles `react` and `@remix-run/react` into `dist/index.mjs`. Consumer app gets two React instances → hook state doesn't share context.

**Why it happens:** `peerDependencies` alone does not prevent tsup from inlining them.

**How to avoid:** Explicitly list all peerDependencies in `external: [...]` in `tsup.config.ts`.

**Warning signs:** `attw` reports "Incorrect default export" or `publint` warns about bundled peer deps. `npm ls react` shows duplicate React entries.

### Pitfall 3: Remix v2 vs React Router v7 Import Paths

**What goes wrong:** Consumer uses React Router v7 (`import ... from 'react-router'`) and finds `@remix-run/node` types are missing.

**Why it happens:** React Router v7 consolidates `@remix-run/node` into `react-router`. But Remix v2 still uses `@remix-run/node`.

**How to avoid:** Target `@remix-run/node` peerDep for v1.2. Document in package README that React Router v7 migration is v1.3.

**Warning signs:** TypeScript errors importing `ActionFunctionArgs` from `@remix-run/node` in consumer.

### Pitfall 4: `getToken` Receives ActionFunctionArgs, Not RequestEvent

**What goes wrong:** Planner copies `getToken` type from SvelteKit types verbatim — type says `(event: RequestEvent)` but Remix version must say `(args: ActionFunctionArgs)`.

**Why it happens:** Mechanical copy-paste without adapting the parameter type.

**How to avoid:** Types file must define `getToken?: (args: ActionFunctionArgs) => ...`.

**Warning signs:** TypeScript error when consumer passes a `getToken` that destructures Remix-specific fields.

### Pitfall 5: SSE from POST Action Has No Official Remix Documentation

**What goes wrong:** Developer assumes there is a Remix-blessed pattern for streaming POST responses and spends time searching for it. There isn't one.

**Why it happens:** The standard Remix SSE docs use `loader` (GET). POST action streaming is community-discovered.

**How to avoid:** Use the native `fetch()` + `ReadableStream` loop directly. The action returns a `new Response(readableStream, { headers })` — this is standard Web API and does work from Remix actions even though it's not documented.

**Warning signs:** Test suite passes server-side but client-side SSE never receives frames.

### Pitfall 6: `@remix-run/react` peerDep requires React 18

**What goes wrong:** Consumer using React 19 gets a peer dependency conflict on install.

**Why it happens:** `@remix-run/react@2.17.4` declares `"react": "^18.0.0"`. React 19 consumers need `--legacy-peer-deps` or must wait for Remix v3 / React Router v7.

**How to avoid:** Document this limitation. The `@deepagents-nextjs/remix` package itself should declare `"react": ">=18.0.0"` and let the consumer's Remix version govern the React constraint.

## Open Questions

1. **Does `useFetcher.submit()` provide any value in the hook, or is pure `fetch()` cleaner?**
   - What we know: `useFetcher` cannot read the SSE stream body. `fetch()` is required.
   - What's unclear: Whether using `useFetcher` for submit state tracking (loading indicator during POST) adds real value vs adding complexity.
   - Recommendation: Use pure `useState` + `fetch()`. The requirement says "built on `useFetcher`" but the planner should interpret this as "exposes the same state surface" (messages, status, error) not "must call useFetcher internally." If planner chooses to use `useFetcher` for the POST submission (before switching to `fetch()` for stream reading), that is also valid.

2. **React 19 + `@remix-run/react` peer dep conflict**
   - What we know: `@remix-run/react@2.17.4` declares `"react": "^18.0.0"`.
   - What's unclear: Whether consumers on React 19 will get peer dep errors.
   - Recommendation: Declare `"react": ">=18.0.0"` in our peerDeps. Document the Remix v2 React 18 constraint.

3. **Anti-React CI guard applicability**
   - What we know: SvelteKit CI job verifies no React imports in dist files.
   - What's unclear: The Remix `useDeepAgentsChat` hook deliberately imports from `react` and `@remix-run/react`. The anti-React guard must only apply to the **handler** module, not the hook.
   - Recommendation: Either skip the React guard for the Remix package, or add a more targeted check that only verifies the handler entry doesn't import from `@deepagents-nextjs/react`.
