### Plan 02 (Handler TDD) - WAVE 2

**Type**: tdd
**Files**: 2 (handler.ts → handler.test.ts)
**Autonomous**: Yes (depends on Plan 01 scaffold)

**Objective**: Implement `createDeepAgentsHandler` with 12 tests.

**Tests Define the Surface**:
1. SSE stream returns correctly (content-type header)
2. Request body proxied to backend
3. null transform drops frames
4. getToken injects Authorization header
5. getToken null/empty suppresses header
6. assertNodeRuntime() validation
7. 502 on backend failure
8. Hop-by-hop headers filtered
9. x-vercel-ai-ui-message-stream forwarded
10. getToken rejection propagates
11. (2 additional unspecified)

**Strengths**:
- ✓ Test count (12) is specific and testable.
- ✓ All truths are narrowly scoped to handler behavior.
- ✓ TDD pattern (RED → GREEN) enforces test-first discipline.

**Gaps Identified**:

1. **Missing edge case tests**:
   - What happens if `backendUrl` is malformed or unreachable?
   - What is the behavior if the request stream is aborted mid-read?
   - What if the backend returns a non-streaming response (e.g., 200 with plain text)?
   - *Suggestion*: Add 2-3 more tests: "malformed backendUrl throws", "request abort", "non-SSE response handling".

2. **No test for parity with SvelteKit**:
   - The plan says "implementation is near-verbatim from SvelteKit handler with `RequestEvent` replaced by `ActionFunctionArgs`".
   - But there is no test verifying that the Remix handler passes the same 12 test scenarios as the SvelteKit handler did (if such tests exist).
   - *Risk*: Handler diverges from SvelteKit unpredictably.
   - *Suggestion*: Add a truth: "The Remix handler.test.ts tests are semantically equivalent to SvelteKit handler.test.ts tests."

3. **No explicit assertion on streaming semantics**:
   - Test 1 mentions "content-type: text/event-stream", but does not specify whether frames are flushed immediately or buffered.
   - *Why it matters*: SSE requires near-realtime flushing for streaming UX.
   - *Suggestion*: Add test: "Each SSE frame is flushed to the client within X ms of the backend sending it."

4. **Missing transformation clarification**:
   - Truth 4 says "null transform drops SSE frames" — but the plan does not specify what a non-null transform looks like.
   - *Context*: v1.2-02 and v1.2-03 shipped transforms (presumably to shape AI messages). Where are they tested?
   - *Suggestion*: Add a test: "Transform function is called for each frame and its output is sent to client."

### Plan 03 (Hook TDD) - WAVE 2

**Type**: tdd
**Files**: 2 (hook.ts → hook.test.ts)
**Autonomous**: Yes (depends on Plan 01 scaffold)

**Objective**: Implement `useDeepAgentsChat` React hook with 7+ tests.

**Critical Architectural Point**:
> "useFetcher CANNOT read SSE streams. The hook MUST use useState + useEffect + native fetch() + ReadableStream reader loop."

This is **correct and important**. Remix's `useFetcher` waits for the full response before returning data, which is incompatible with SSE streaming.

**Tests Define the Surface**:
1. Surface identical to Next.js hook (messages, status, error)
2. Initial state { messages: [], status: 'idle', error: null }
3. Status transitions: idle → loading → streaming → done
4. SSE frames accumulated into messages array
5. Fetch failures set error
6. AbortError silently ignored
7. start() triggers SSE; idle preserved until start()
8. 7+ tests pass
9. Uses native fetch() + ReadableStream, NOT useFetcher.data
10. No imports from @deepagents-nextjs/react or @deepagents-nextjs/server

**Strengths**:
- ✓ Architectural constraint is explicit (no useFetcher).
- ✓ Test count (7+) is open-ended, allowing for additions.
- ✓ Anti-import truth prevents accidental dependency on react/server packages.

**Gaps Identified**:

1. **"7+ tests" is vague**:
   - The plan says "Write 7+ failing tests" but lists 10 truths, only 7 of which map to tests.
   - *Risk*: Implementer may ship with exactly 7 tests and miss edge cases.
   - *Suggestion*: Break out the test list explicitly:
     - Test 1: messages surface + status surface + error surface
     - Test 2: Initial state
     - Test 3: Status transitions (idle → loading → streaming → done)
     - Test 4: SSE frame accumulation
     - Test 5: Fetch failure sets error
     - Test 6: AbortError ignored
     - Test 7: start() triggers fetch
     - Test 8+ (specify): Cleanup on unmount, multiple calls to start(), error recovery, etc.

2. **Missing "start()" semantics**:
   - Truth 7 says "Calling start() triggers the SSE fetch; idle state is preserved before start() is called".
   - But the plan does not specify the signature of `start()`:
     - Does it take a message payload? `start({ role: 'user', content: '...' })`?
     - Does it queue the message to the server?
     - Can it be called while streaming is in progress?
   - *Risk*: Handler and hook will have incompatible signatures.
   - *Suggestion*: Add to must_haves: "start() signature is `(payload: unknown) => Promise<void>`; calling while streaming throws."

3. **No test for race conditions**:
   - What happens if start() is called twice in quick succession?
   - What happens if the component unmounts while streaming?
   - What happens if the backend closes the stream but the client hasn't read all frames?
   - *Suggestion*: Add 3 tests: "Rapid start() calls queue or reject", "Unmount cancels fetch", "Backend stream close is handled cleanly".

4. **Missing "done" status definition**:
   - Truth 3 mentions "done" as a terminal status, but does not define when it is reached.
   - *Assumption*: The stream closes (no more frames)?
   - *Suggestion*: Add test: "status === 'done' when backend closes stream (no more SSE frames)."

5. **No test for message shape**:
   - Truth 4 says "SSE frames are accumulated into messages array", but does not specify the shape of a frame.
   - *Assumption*: Same as the Next.js hook (role/content)?
   - *Suggestion*: Add test: "Each SSE frame is parsed as JSON and appended as { role: 'assistant', content: ... }".

   - The plan says the guard "checks that the handler dist does NOT import @deepagents-nextjs/react or @deepagents-nextjs/server".

     - Grep-based check on dist files?

   - *Suggestion*: Add implementation detail: "CI step: `grep -r '@deepagents-nextjs/react\|@deepagents-nextjs/server' dist/index.js dist/index.mjs || true && exit 1` (fails if found)".

   - *Assumption*: tsup build creates separate entry points for handler and hook?

   - *Suggestion*: Add truth: "tsup config exports separate entry points for handler and hook; dist/handler and dist/hook are independent."

3. **Missing dual-build parity check**:
   - The plan delivers CJS (dist/index.js) and ESM (dist/index.mjs), but does not test that they are semantically equivalent.
   - *Risk*: ESM might use top-level await while CJS does not, causing runtime errors.
   - *Suggestion*: Add truth: "Both CJS and ESM builds pass the same handler and hook tests."

4. **No mention of package.json "exports" field**:
   - The plan does not clarify whether package.json lists both handler and hook exports, or just a barrel export.
   - *Context*: v1.2-04 SvelteKit package likely has separate exports for handler and hook.
   - *Suggestion*: Add artifact: "packages/remix/package.json exports field includes `./handler` and `./hook`."

5. **No specification of publint/attw failure handling**:
   - Truth 1 and 2 say "zero errors", but do not define what "error" means (vs. warning).
   - *Risk*: Implementer ships with warnings and thinks they passed.
   - *Suggestion*: Add clarification: "publint exit code 0; attw exit code 0 (warnings and errors both count as failure)."

## CRITICAL FINDINGS

### 1. SvelteKit Parity NOT Explicitly Tested

The plan says the handler is "near-verbatim from SvelteKit" and the hook uses a pattern "adapted from SvelteKit store to React hooks". But **no plan includes a test that compares the Remix and SvelteKit implementations side-by-side**.

**Risk**: 
- Handler might drop error handling from SvelteKit.
- Hook might not handle the same state transitions as the SvelteKit store.
- Frame accumulation logic might differ.

**Improvement**:
- Plan 02 or 03 should include a test like: "Remix handler behavior matches SvelteKit handler behavior on 12 common scenarios (see v1.2-04-02-PLAN.md for test list)."
- Document this as a key_link: from `packages/remix/src/handler.ts` to `packages/sveltekit/src/handler.ts`.

### 2. Hook Lifecycle Not Fully Specified

Plan 03 lists a "done" status but does not define when the stream has been fully consumed. The plan assumes a ReadableStream reader loop, but does not specify:
- How many frames make up a typical conversation turn?
- What happens if the backend sends frames out of order?
- What happens if a frame is malformed JSON?

**Risk**: The hook might buffer frames indefinitely or crash on bad input.

**Improvement**:
- Add a truth: "The hook accumulates frames until the backend closes the stream (no more data events). A frame that is not valid JSON is logged and skipped."

### 3. Handler Transform Pipeline Is Underspecified

Plan 02 says "null transform drops SSE frames" (Truth 4), but does not define what a non-null transform looks like or how it is used.

**Context**: Earlier phases (v1.2-02, v1.2-03) likely shipped transforms to shape AI responses. But the Remix plan does not reference them.

**Risk**: The handler might not apply transforms consistently with the SvelteKit handler.

**Improvement**:
- Add a test: "Transform function receives SSE frame and returns modified frame; null transform is identity function that drops frames."
- Add a context reference: `@.planning/phases/v1.2-02-langchain/v1.2-02-RESEARCH.md` (or equivalent) for transform semantics.

### 4. CI Guard Is "Grep-Based" — Fragile

The plan says the CI guard checks that remix handler dist "does NOT import @deepagents-nextjs/react or @deepagents-nextjs/server". But if the implementation is a simple grep, it will have false positives/negatives:
- False positive: A comment mentioning @deepagents-nextjs/react.
- False negative: A dynamic import like `require('@deepagents-nextjs/' + 'react')`.

**Risk**: CI guard is unreliable.

**Improvement**:
- Use a proper AST-based tool (e.g., `depcheck` with a custom config) or a bundler plugin that validates exports.
- Add a test that explicitly checks the handler entry point's import graph.

### 5. No Explicit "Success Criteria" in Plan Frontmatter

The plans lack a `success_criteria` section at the root level (only `must_haves` is present).

**Context**: Earlier phases (e.g., v1.2-04) may have had explicit success_criteria. The absence here suggests inconsistency.

**Improvement**:
- Add `success_criteria` to each plan. Example for Plan 01:
  ```yaml
  success_criteria:
    - "pnpm --filter @deepagents-nextjs/remix typecheck passes"
    - "pnpm --filter @deepagents-nextjs/remix test passes"
    - "The remix package is listed in pnpm-workspace.yaml"
  ```
