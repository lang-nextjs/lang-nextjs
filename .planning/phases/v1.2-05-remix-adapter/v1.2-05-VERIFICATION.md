### Criterion 2 — Status Surface Alignment Note

The phase goal stated "same `messages`, `status`, `error` surface as the Next.js hook." The Remix hook status type is `'idle' | 'loading' | 'streaming' | 'done' | 'error'` while the Next.js hook uses `'idle' | 'streaming' | 'submitted' | 'error'`. These differ in naming (`loading` vs implicit, `done` vs inferred from `submitted`). However:

1. The Remix-specific status values were defined in the Phase 01 PLAN's `must_haves` and match the `DeepAgentsState` type designed for this package.
2. The plan's success criteria explicitly lists these status values as correct.
3. The three required surface properties (`messages`, `status`, `error`) are all present and typed.
4. The semantic meaning is equivalent — both surfaces communicate idle, in-flight, streaming, finished, and errored states.

This is a deliberate design decision documented in the phase, not a defect.

---

### Hook Design Note: Native fetch vs useFetcher

The phase goal mentioned "useFetcher-based hook." The RESEARCH.md established that `useFetcher` buffers the entire response before delivering it, making true SSE streaming impossible. The implementation correctly uses `native fetch() + ReadableStream reader loop` instead. This achieves the phase goal (SSE streams correctly to the Remix client) and is the correct technical approach. The SUMMARY.md for Plan 03 documents this decision explicitly.
