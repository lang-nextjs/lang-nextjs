# Phase v1.2-04: SvelteKit Adapter - Research

**Researched:** 2026-05-01
**Domain:** SvelteKit RequestEvent, Svelte reactive stores, SSE proxy, monorepo package authoring
**Confidence:** HIGH (SvelteKit server route pattern, store API) / MEDIUM (Node runtime detection approach, publint/attw for pure-TS SvelteKit package)

## Summary

This phase creates a new package `@deepagents-nextjs/sveltekit` in the monorepo. It adapts the existing SSE proxy core (the same transform pipeline already in `@deepagents-nextjs/server`) to accept a SvelteKit `RequestEvent` instead of a `NextRequest`. The handler reads `event.request`, proxies via `fetch`, and returns a standard `Response` — identical to the Next.js pattern but without the Next.js dependency. The second deliverable is a Svelte reactive store (`createDeepAgentsStore`) that consumes the SSE stream client-side and exposes `messages`, `status`, and `error` as a `writable` store.

The package must not import `@deepagents-nextjs/react` (React has no role here) and must list `@sveltejs/kit` in `peerDependencies` only. Because the handler code is pure TypeScript/Web-standard and contains no `.svelte` files, `tsup` is the correct build tool — the same toolchain used for every other package in this monorepo. `svelte-package` is only needed for libraries that ship `.svelte` components; this library ships only `.ts`.

Node-runtime detection at startup is the fourth success criterion. `process.versions.node` is the most reliable check in 2025 — `typeof process` alone is no longer safe because Cloudflare Workers now expose `process` when the Node.js compat flag is enabled.

**Primary recommendation:** Build the SvelteKit handler as a thin re-use of the existing transform/accumulator core via a shared internal extraction, or by reimplementing the ~30-line proxy loop using only Web-standard APIs (no Next.js import). Use `writable` from `svelte/store` for the client store. Apply the same package.json template (CJS+ESM dual output, publint + attw validate script) as the other packages.

### Pattern 1: SvelteKit Handler — Re-use Web-Standard Core

**What:** Accept `RequestEvent` (has `.request: Request`), read body as `ArrayBuffer`, proxy via `fetch`, pipe through the transform/accumulator pipeline, return a `new Response(stream, headers)`.

**Key insight:** SvelteKit's `RequestEvent.request` is a standard Web `Request` object. The Next.js handler in `packages/server` does `request.arrayBuffer()` and builds forwarded headers — these are also standard Web APIs. The _only_ Next.js-specific part of `packages/server/handler.ts` is `import { NextRequest, NextResponse }`. The new SvelteKit handler can replicate the same logic without any Next.js import.

**When to use:** Every `+server.ts` POST route in a SvelteKit app that proxies to a DeepAgents backend.

```typescript
// Source: pattern derived from packages/server/src/handler.ts + svelte.dev/docs/kit/routing
import type { RequestEvent } from '@sveltejs/kit';
import { SseFrameAccumulator } from './accumulator';  // extracted shared module
import type { SseAdapter, SseTransform } from './types';

export interface SvelteKitHandlerOptions {
  backendUrl: string;
  adapter?: SseAdapter;
  transforms?: SseTransform[];
  getToken?: (event: RequestEvent) => Promise<string | null | undefined> | string | null | undefined;
}

export function createDeepAgentsHandler(options: SvelteKitHandlerOptions) {
  return async function POST(event: RequestEvent): Promise<Response> {
    const body = await event.request.arrayBuffer();
    // ... same proxy logic as packages/server handler, but returns new Response(stream, headers)
  };
}
```

**Critical:** The handler returns a standard `Response`, not `NextResponse`. SvelteKit routes return `Response` directly.

### Pattern 2: Svelte Reactive Store

**What:** A factory function that starts fetching the SSE endpoint and pipes frames into a `writable` store. Exposes `messages`, `status`, and `error`.

**When to use:** Client-side Svelte components that need to display chat messages from a DeepAgents backend.

```typescript
// Source: svelte.dev/docs/svelte/svelte-store
import { writable, derived } from 'svelte/store';
import type { Readable } from 'svelte/store';

export interface DeepAgentsState {
  messages: Message[];
  status: 'idle' | 'loading' | 'streaming' | 'done' | 'error';
  error: Error | null;
}

export function createDeepAgentsStore(
  endpoint: string,
  options?: { sessionId?: string }
): Readable<DeepAgentsState> & { send: (message: string) => void } {
  const store = writable<DeepAgentsState>({
    messages: [],
    status: 'idle',
    error: null,
  });
  // ... SSE fetch + ReadableStream parse loop that calls store.update()
  return { subscribe: store.subscribe, send };
}
```

**SSR safety note:** The store factory must only be called in a browser context (`onMount` or inside a `browser` guard). The factory itself must not execute at SSR time. Document this in JSDoc. The store itself (the writable object) is safe — it is the `fetch` call that must not run on the server.

### Pattern 3: Node Runtime Guard

**What:** A startup check that throws a clear error if the package is loaded in a non-Node runtime.

**Why `process.versions.node` not `typeof process`:** Since Cloudflare Workers added Node.js compat flags, `typeof process !== 'undefined'` returns `true` in Workers too. `process.versions?.node` is only defined in Node.js.

```typescript
// Source: cloudflare.com/workers/runtime-apis/nodejs/process + community.cloudflare.com/t/how-to-detect-the-cloudflare-worker-runtime
function assertNodeRuntime(): void {
  if (typeof process === 'undefined' || !process.versions?.node) {
    throw new Error(
      '@deepagents-nextjs/sveltekit requires Node.js runtime. ' +
      'Cloudflare Workers and other edge runtimes are not supported in v1.2. ' +
      'Use @sveltejs/adapter-node for your SvelteKit deployment.'
    );
  }
}
```

Call `assertNodeRuntime()` at the top of `createDeepAgentsHandler` (not at module load time, to avoid crashing non-Node apps that import but never call the function). This aligns with the existing 503 pattern in the Next.js adapter: fail at call time, not at import time.

### Pattern 4: SseFrameAccumulator Sharing

**What:** The SseFrameAccumulator logic in `packages/server/src/accumulator.ts` is pure business logic with no framework imports. Rather than duplicating it, explore extracting it to a shared internal package or simply copy the implementation.

**Decision for research:** Because this is a new package (not a modification to server), and the accumulator has no external imports, **copy the accumulator + transform types into `packages/sveltekit/src/`**. This avoids a cross-package dependency that would complicate the build and publishing order. The planner should create a task to copy `accumulator.ts` and the type definitions.

**Alternative:** Extract to `@deepagents-nextjs/core` (internal package). This is the right long-term move but is out of scope for v1.2-04. Flag as a future refactor opportunity.

### Anti-Patterns to Avoid

- **Importing from `@deepagents-nextjs/react`:** The success criteria explicitly forbid this. The SvelteKit package has no React dependency.
- **Importing from `@deepagents-nextjs/server`:** That package lists `next` as a peerDependency. Importing it would pull Next.js into a SvelteKit project.
- **Using `$app/environment` or `$app/stores`:** SvelteKit virtual modules are not resolvable by tsup. Only `svelte/store` (a real npm entry point) is safe to import.
- **Module-level `assertNodeRuntime()` call:** Would crash on import in non-Node environments even if the handler is never called. Call inside the handler function instead.
- **Using `ReadableStream` without a type guard:** Node 18 native `fetch` + `ReadableStream` are available but may need `"lib": ["ES2020", "DOM", "DOM.Iterable"]` in tsconfig — same pattern as `packages/server/tsconfig.json` (see v1.0-02 decision in STATE.md).

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| SSE frame buffering/parse | Custom byte-boundary accumulator | Copy `SseFrameAccumulator` from packages/server | Already tested; chunk-split edge cases covered |
| Svelte store reactivity | Manual subscription array | `writable` from `svelte/store` | Handles subscribe, set, update, auto-unsubscribe in components |
| CJS+ESM dual build | Custom rollup/webpack config | `tsup` with existing `outExtension` pattern | Already proven across 3 packages; zero setup |
| Package export validation | Manual export map check | `publint` + `attw` in validate script | Catches `.d.mts` vs `.d.ts` mismatch; `exports` precedence errors |

**Key insight:** The entire SSE proxy pattern already exists in `packages/server`. The SvelteKit adapter is a thin layer that swaps `NextRequest`/`NextResponse` for SvelteKit's `RequestEvent`/`Response`. Do not redesign the core; reuse the accumulator and transform types.

## Common Pitfalls

### Pitfall 1: Importing Next.js APIs into the SvelteKit Package
**What goes wrong:** `import { NextResponse } from 'next/server'` in `packages/sveltekit` causes SvelteKit consumers to download and install `next` as a peer dependency.
**Why it happens:** Temptation to re-use `packages/server/handler.ts` directly.
**How to avoid:** The new package must re-implement the proxy handler using only Web-standard `Response`, `Headers`, `ReadableStream`. Never import from `@deepagents-nextjs/server`.
**Warning signs:** `peerDependencies` in `packages/sveltekit/package.json` includes `next`.

### Pitfall 2: SvelteKit Virtual Modules in tsup Build
**What goes wrong:** `import { browser } from '$app/environment'` causes tsup to fail with "Could not resolve '$app/environment'".
**Why it happens:** SvelteKit's `$app/*` virtual modules are only resolved by Vite with the SvelteKit plugin; tsup has no awareness of them.
**How to avoid:** Never import `$app/*` in library source. For runtime environment checks, use `typeof window !== 'undefined'` or the `process.versions.node` check. For SSR-safety documentation, use JSDoc comments rather than `$app/environment`.
**Warning signs:** Build errors mentioning unresolved module paths starting with `$`.

### Pitfall 3: Svelte Store Executing at SSR Time
**What goes wrong:** The SSE fetch inside the store factory fires on the server during SSR, causing duplicate requests and hydration mismatches.
**Why it happens:** Svelte stores initialized at module level or outside `onMount` run during SSR in SvelteKit.
**How to avoid:** Document clearly that `createDeepAgentsStore()` must be called inside `onMount` or guarded by `if (browser)`. The store factory should not auto-start SSE fetching on construction — consider a `connect()` method pattern or lazy init on first subscriber (using `writable`'s `start` parameter).
**Warning signs:** SSR logs showing fetch requests to the backend URL during page render.

### Pitfall 4: `typeof process` Runtime Check Failing in Workers
**What goes wrong:** The Node guard passes in Cloudflare Workers when `nodejs_compat` flag is set, so the package runs in an unsupported environment without the intended error.
**Why it happens:** Since 2024, `process` is defined in Workers when Node.js compat is enabled. Since 2025-04-01, `process.env` is also populated.
**How to avoid:** Use `process.versions?.node` (only defined in Node.js) rather than `typeof process !== 'undefined'`.
**Warning signs:** No error thrown when testing in a Worker-like environment.

### Pitfall 5: Missing `"lib": ["DOM", "DOM.Iterable"]` in tsconfig
**What goes wrong:** TypeScript errors on `Headers`, `ReadableStream`, `TextEncoder`, `fetch` — all Web API globals.
**Why it happens:** `tsconfig.base.json` only has `"lib": ["ES2020"]`; Web APIs require DOM lib.
**How to avoid:** Add `"lib": ["ES2020", "DOM", "DOM.Iterable"]` to `packages/sveltekit/tsconfig.json` — same fix as v1.0-02 decision for `packages/server`.
**Warning signs:** TypeScript `TS2304: Cannot find name 'Headers'` etc.

### Pitfall 6: `peerDependencies` Including `@deepagents-nextjs/react`
**What goes wrong:** CI publint or attw failures; SvelteKit consumers are forced to install React.
**Why it happens:** Accidental import somewhere in the package.
**How to avoid:** Never import from `@deepagents-nextjs/react`. Add a CI check that the built dist does not reference React.
**Warning signs:** `peerDependencies` or `dependencies` in `package.json` mentions `react` or `@deepagents-nextjs/react`.

```typescript
// Source: svelte.dev/docs/svelte/svelte-store (confirmed 2026-05-01)
import { writable } from 'svelte/store';
import type { StartStopNotifier } from 'svelte/store';

// The start function only runs when the first subscriber attaches.
// In SvelteKit SSR, stores with no browser subscriber don't start.
const start: StartStopNotifier<DeepAgentsState> = (set) => {
  // This runs only in the browser (when a component subscribes)
  const controller = new AbortController();
  startSseStream(endpoint, set, controller.signal);
  return () => controller.abort(); // cleanup when last subscriber detaches
};

export const state = writable<DeepAgentsState>(initialState, start);
```

## State of the Art

| Old Approach | Current Approach | When Changed | Impact |
|--------------|------------------|--------------|--------|
| `typeof process !== 'undefined'` for Node detection | `process.versions?.node != null` | 2024 (CF Workers added process) | Must update any naive runtime checks |
| `svelte-package` for all Svelte libraries | `tsup` for pure-TS libs; `svelte-package` only when `.svelte` files ship | 2023+ (ecosystem matured) | We use tsup — correct for this package |
| Svelte 4 stores as primary state | Svelte 5 runes (`$state`) for component-local state; stores still valid for shared/async state | Svelte 5.0 (2024) | `writable` from `svelte/store` remains the correct choice for a library store that multiple components share |

**Note on Svelte 5 runes:** The phase success criteria say "Svelte reactive store". This is the `svelte/store` contract (`writable`, `readable`, `derived`). Runes (`$state`, `$derived`) are compiler features that do not work outside `.svelte` / `.svelte.ts` files and cannot be exported from a plain TypeScript library. The store approach is correct.

## Open Questions

1. **SseFrameAccumulator sharing — copy vs. extract**
   - What we know: Accumulator is pure TS, no imports, ~50 lines
   - What's unclear: Whether to copy into `packages/sveltekit/src/` or extract to a new `@deepagents-nextjs/core` internal package
   - Recommendation: Copy for v1.2-04; leave core extraction as a future refactor (out of scope for this phase)

2. **`getToken` signature for SvelteKit**
   - What we know: In `packages/server`, `getToken` receives `NextRequest`. In SvelteKit, the equivalent is `RequestEvent` (which includes `.cookies`, `.locals`, etc.)
   - What's unclear: Whether to pass full `RequestEvent` or just `event.request: Request` to `getToken`
   - Recommendation: Pass the full `RequestEvent` — it gives consumers access to SvelteKit cookies and locals for auth, which `Request` alone does not expose.

3. **Svelte store: lazy init via StartStopNotifier vs. explicit connect()**
   - What we know: `writable(initialValue, start)` is the idiomatic pattern for lazy-init stores in Svelte; `start` runs when first subscriber attaches
   - What's unclear: Whether the planner prefers a `connect()/disconnect()` imperative API or the pure reactive `StartStopNotifier` pattern
   - Recommendation: Use `StartStopNotifier` — it is more idiomatic for Svelte and handles cleanup via the returned stop function automatically
