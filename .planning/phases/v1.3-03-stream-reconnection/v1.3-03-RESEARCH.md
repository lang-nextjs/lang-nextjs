## Summary

Phase v1.3-03 implements stream reconnection for users on unstable networks. The AI SDK v6 (`ai` package) exposes a `resume` boolean on `useChat` and a `createResumableStreamContext` server-side utility that together enable reconnection after page reload or tab remount. The `resumable-stream` npm package provides the pub/sub infrastructure; its `/generic` export allows a custom `Publisher`/`Subscriber` backed by a plain JavaScript `Map` — making Redis optional for a reference implementation.

**CRITICAL GATE (confirmed 2026-05-02):** AI SDK bug #6502 (abort signal breaks resumable streams, opened May 2025, still open) and bug #11865 (stream resumption only works on page reload, not tab switch, opened Jan 2026, still open) are BOTH confirmed open. Per the STR-01 conditional gate, this phase MUST ship behind `ENABLE_STREAM_RECONNECT=true` (default off) with a prominent README warning, or be deferred to v1.4.

The architecture splits cleanly: the **server package** (`@deepagents-nextjs/server`) adds a GET handler factory and in-memory stream registry; the **react package** (`@deepagents-nextjs/react`) adds a `retry()` function to `useDeepAgentsChatReturn` and wires the `resume: true` option through `DefaultChatTransport`. Both changes are additive and backward-compatible. No new npm packages need to be added as production dependencies — `resumable-stream` provides the pub/sub contracts but the in-memory reference implementation can satisfy its `Publisher`/`Subscriber` interfaces without installing the package.

**Primary recommendation:** Ship behind `ENABLE_STREAM_RECONNECT=true` feature flag (default off). The flag gates both server-side stream persistence and client-side `resume: true`. The in-memory registry is a `Map<string, StreamRecord>` singleton in the server handler module — no Redis, no DB. `resumeId` deduplication uses the registry: a second POST with the same `resumeId` before the first stream is done returns a 409 or reuses the same stream reference.

### Pattern 1: Feature Flag Gate — `ENABLE_STREAM_RECONNECT`

**What:** An environment variable check that disables stream reconnection by default. Both server and client respect the flag.
**When to use:** Any time stream reconnection code is reached; checked at handler-instantiation time (server) and hook-render time (client).

```typescript
// Source: STR-01 conditional gate decision in STATE.md + REQUIREMENTS.md

// Server: packages/server/src/reconnect.ts
export function isStreamReconnectEnabled(): boolean {
  return process.env.ENABLE_STREAM_RECONNECT === 'true';
}

// Client: packages/react/src/hook.ts
// Read from window.__DEEP_AGENTS_FLAGS or passed as a prop option — see Pattern 4.
```

**Server enforcement:** `createDeepAgentsResumeHandler` returns a 503 with a descriptive error if `ENABLE_STREAM_RECONNECT !== 'true'`.

**Client enforcement:** When `resume` is not enabled (flag off), `useDeepAgentsChat` behaves exactly as today — no `resume: true`, no `retry()` side effects.

### Pattern 2: In-Memory Stream Registry

**What:** A module-level `Map` that tracks active streams by `resumeId`. Lives in `packages/server/src/stream-registry.ts`.
**When to use:** POST handler writes a new entry; GET handler reads and resumes; `onFinish` callback deletes the entry.

```typescript
// Source: AI SDK official docs pattern + resumable-stream/generic interface analysis

interface StreamRecord {
  streamId: string;          // opaque ID passed to createResumableStream
  createdAt: number;         // Date.now() — for TTL cleanup
  done: boolean;             // set true in onFinish
}

// Singleton — survives the lifetime of the Next.js server process
const registry = new Map<string, StreamRecord>();

const TTL_MS = 5 * 60 * 1000; // 5 minutes

export function registerStream(resumeId: string, streamId: string): void {
  registry.set(resumeId, { streamId, createdAt: Date.now(), done: false });
}

export function lookupStream(resumeId: string): StreamRecord | undefined {
  const record = registry.get(resumeId);
  if (!record) return undefined;
  // Evict expired entries on lookup (lazy TTL)
  if (Date.now() - record.createdAt > TTL_MS) {
    registry.delete(resumeId);
    return undefined;
  }
  return record;
}

export function markStreamDone(resumeId: string): void {
  const record = registry.get(resumeId);
  if (record) record.done = true;
}

export function deleteStream(resumeId: string): void {
  registry.delete(resumeId);
}
```

### Pattern 3: Server — POST Handler `resumeId` Deduplication

**What:** The existing POST handler receives a `resumeId` in the request body. If a live stream for that `resumeId` already exists, the server returns 409 (idempotent — deliver once). If none exists or the previous one is done, start a new stream.

```typescript
// Source: STR-01 success criterion 3 — "same resumeId submitted twice concurrently,
// server delivers the stream exactly once"

// In createDeepAgentsHandler POST body parsing (packages/server/src/handler.ts):
const { sessionId, resumeId } = await request.json();

if (resumeId && isStreamReconnectEnabled()) {
  const existing = lookupStream(resumeId);
  if (existing && !existing.done) {
    // Duplicate concurrent submission — return 409
    return new NextResponse('stream already in progress for this resumeId', { status: 409 });
  }
  registerStream(resumeId, generateId());
}
```

### Pattern 4: Server — GET Handler (`createDeepAgentsResumeHandler`)

**What:** A separate exported factory that creates a Next.js App Router GET handler. Reads `resumeId` from the URL, looks it up in the registry, and either resumes the stream or returns 204.

```typescript
// Source: AI SDK official docs pattern — GET handler for /api/chat/[id]/stream

// packages/server/src/reconnect.ts
import { createResumableStreamContext } from 'resumable-stream';
// OR: use the in-memory adapter that mirrors resumable-stream/generic interface

export function createDeepAgentsResumeHandler() {
  return async function GET(
    _: NextRequest,
    { params }: { params: Promise<{ resumeId: string }> }
  ): Promise<NextResponse> {
    if (!isStreamReconnectEnabled()) {
      return new NextResponse('stream reconnection disabled (set ENABLE_STREAM_RECONNECT=true)', { status: 503 });
    }

    const { resumeId } = await params;
    const record = lookupStream(resumeId);

    if (!record || record.done) {
      return new NextResponse(null, { status: 204 });
    }

    // Resume from in-memory context using stored streamId
    const streamContext = getStreamContext(); // module singleton
    const stream = await streamContext.resumeExistingStream(record.streamId);

    return new NextResponse(stream, {
      headers: {
        'Content-Type': 'text/event-stream',
        'Cache-Control': 'no-cache, no-transform',
        'X-Accel-Buffering': 'no',
      },
    });
  };
}
```

### Pattern 5: Client — `retry()` Function in `useDeepAgentsChat`

**What:** `retry()` re-triggers a GET reconnection attempt. It sets a `reconnecting` state, fires the GET to the resume endpoint, and streams the response into the existing messages. In the feature-flag-off path, `retry` is a no-op.

```typescript
// Source: STR-01 success criterion 2 + AI SDK useChat resume: true pattern

// Extend UseDeepAgentsChatOptions:
interface UseDeepAgentsChatOptions<TData> {
  // ... existing fields ...
  /**
   * resumeId for stream reconnection. Required when ENABLE_STREAM_RECONNECT=true.
   * Should be a stable ID per-conversation, e.g. derived from sessionId.
   */
  resumeId?: string;
  /**
   * Endpoint for the GET resume handler. Required when resumeId is set.
   * Example: '/api/chat/stream/resume'
   * The handler must accept GET /api/chat/stream/resume?resumeId=<id>
   * or use a dynamic segment like /api/chat/[resumeId]/stream
   */
  resumeEndpoint?: string;
  /** Whether stream reconnection is enabled (mirrors ENABLE_STREAM_RECONNECT). Default: false */
  enableReconnect?: boolean;
}

// Extend UseDeepAgentsChatReturn:
interface UseDeepAgentsChatReturn<TData> {
  // ... existing fields ...
  /**
   * Manually trigger reconnection. No-op when enableReconnect is false.
   * Sets status to 'submitted' while reconnecting.
   */
  retry: () => void;
}
```

The `resume` option on `useChat` is passed through `DefaultChatTransport` via `prepareReconnectToStreamRequest`:

```typescript
// Source: ai-sdk.dev/docs/ai-sdk-ui/chatbot-resume-streams

const transport = useMemo(
  () =>
    new DefaultChatTransport({
      api: endpoint,
      headers: async () => { /* existing token logic */ },
      body: () => ({ sessionId, resumeId, ...extraBody }),
      ...(enableReconnect && resumeId && resumeEndpoint
        ? {
            prepareReconnectToStreamRequest: () => ({
              api: `${resumeEndpoint}?resumeId=${resumeId}`,
            }),
          }
        : {}),
    }),
  [endpoint, sessionId, enableReconnect, resumeId, resumeEndpoint]
);

const { messages: aiMessages, sendMessage: aiSendMessage, status, error, reload } = useChat({
  transport,
  resume: enableReconnect && !!resumeId,
});

// retry() calls reload() to re-trigger the reconnection
const retry = useCallback(() => {
  if (enableReconnect) reload();
}, [enableReconnect, reload]);
```

### Anti-Patterns to Avoid

- **Using `resume: true` without the feature flag off path:** The abort/resume incompatibility (bug #6502) means enabling `resume: true` always will break tab-close behavior for all users. Gate it behind `enableReconnect` prop.
- **Storing stream data in a serverless-reset Map:** Document clearly that the in-memory registry is a reference implementation only — it does not survive serverless cold starts, horizontal scaling, or Vercel Function invocation boundaries. Consumers who need production reliability must use Redis.
- **Mutating `UseDeepAgentsChatReturn` type without preserving `Record<never,never>` default:** The `TData` generic has a `Record<never,never>` default (locked decision from v1.2-03). Adding new fields must not break zero-generic callers.
- **Parsing the request body twice in handler.ts:** The existing handler does `request.arrayBuffer()` for proxying. If `resumeId` is needed, either parse JSON first and re-encode, or read `resumeId` from a query param / header to avoid double consumption.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| SSE reconnection protocol | Custom EventSource wrapper | AI SDK `resume: true` + `useChat` | Edge cases in SSE reconnection (Last-Event-ID, retry timing) are handled by the SDK |
| Pub/sub for in-process stream sharing | Custom EventEmitter broker | `resumable-stream/generic` interface pattern | The interface is already defined; mirror it with a Map for consistency with the upstream library |
| Unique stream IDs | `crypto.randomUUID()` | `generateId` from `ai` package | `generateId` is already imported in the codebase; consistent ID format |

**Key insight:** The AI SDK's `resume` option on `useChat` handles all the reconnection retry timing, back-off, and duplicate-frame suppression on the client side. Don't build a custom reconnection loop.

## Common Pitfalls

### Pitfall 1: Body Already Consumed Before `resumeId` Extraction

**What goes wrong:** `handler.ts` calls `request.arrayBuffer()` to read the body for proxying. If you also try to `request.json()` to extract `resumeId`, you get "body already consumed" error.
**Why it happens:** `NextRequest.body` is a single-read stream.
**How to avoid:** Extract `resumeId` from a request header (`X-Resume-Id`) or query parameter instead of the body. This avoids double-parsing and doesn't require re-encoding the body.
**Warning signs:** `TypeError: body already used` in server logs.

### Pitfall 2: In-Memory Registry Leaks on Long-Running Servers

**What goes wrong:** The `Map` grows unboundedly if streams are never marked done (e.g., an error mid-stream skips the `onFinish` callback).
**Why it happens:** `onFinish` only fires on clean completion; mid-stream errors do not trigger it.
**How to avoid:** Implement lazy TTL eviction on lookup (as shown in Pattern 2). Also call `deleteStream` in the stream error handler.
**Warning signs:** Memory growth over many hours; `registry.size` increasing monotonically.

### Pitfall 3: `resume: true` Breaks Abort (Bug #6502)

**What goes wrong:** Once `resume: true` is set, calling `stop()` from `useChat` no longer aborts the generation. The backend process continues running until completion or timeout.
**Why it happens:** AI SDK design conflict — abort signal and resumable streams share the same disconnect mechanism.
**How to avoid:** Do NOT expose a `stop()` function when `enableReconnect: true`. Document this limitation in the README warning. This is a known open bug.
**Warning signs:** User clicks stop button, spinner continues.

### Pitfall 4: `resume: true` Only Works on Mount, Not Tab Switch (Bug #11865)

**What goes wrong:** When a user switches tabs during streaming and returns, the stream is not resumed — only page reload/remount triggers reconnection.
**Why it happens:** AI SDK's `resume: true` only fires on component mount, not on `visibilitychange` events.
**How to avoid:** The `retry()` function can be called manually via a `visibilitychange` listener in consumer code. Document this workaround in the README.
**Warning signs:** User switches tabs, returns to find a frozen/stuck stream with no auto-recovery.

### Pitfall 5: Duplicate Body Encoding for Backend Proxy

**What goes wrong:** The server handler currently passes the raw body buffer to the backend. Adding `resumeId` to the body for the in-memory lookup requires reading the JSON body, which interferes with the raw buffer pass-through.
**Why it happens:** Handler was designed as a transparent SSE proxy with minimal body inspection.
**How to avoid:** Pass `resumeId` as a request header (`X-Resume-Id: <id>`) from the client. The client sets this header in `DefaultChatTransport.headers`. The server reads it from `request.headers` before the body is consumed. This is a clean extension of the existing header-forwarding architecture.

### Pitfall 6: `createResumableStreamContext` Requires `after`

**What goes wrong:** `createResumableStreamContext({ waitUntil: after })` uses Next.js `after()` to keep work alive past the response. If `after` is not imported from `next/server`, the stream context silently fails to persist.
**Why it happens:** `after` is a Next.js-specific API; it's not available in edge or Deno runtimes.
**How to avoid:** Import `after` from `next/server` in the server handler. Document that the in-memory implementation only works in Node.js runtime (not edge). The `packages/edge` handlers do not support stream reconnection.

## Open Questions

1. **Where does the client read `ENABLE_STREAM_RECONNECT`?**
   - What we know: The server reads `process.env.ENABLE_STREAM_RECONNECT`. The client (React hook) cannot read `process.env` at runtime in a browser.
   - What's unclear: Should the client use a `enableReconnect` prop (consumer-set), or read from a Next.js public env var (`NEXT_PUBLIC_ENABLE_STREAM_RECONNECT`)?
   - Recommendation: Use the `enableReconnect?: boolean` prop on `useDeepAgentsChatOptions`. This keeps the library framework-agnostic (doesn't assume Next.js env var conventions). Consumer is responsible for wiring the flag.

2. **Does `request.arrayBuffer()` conflict with `resumeId` extraction?**
   - What we know: `handler.ts` calls `request.arrayBuffer()` first; the body stream is then consumed.
   - What's unclear: Should `resumeId` come from the body (parse JSON + re-encode) or from a header/query param?
   - Recommendation: Use `X-Resume-Id` request header. Client sends it in `DefaultChatTransport.headers`. Server reads it before body consumption. Zero conflict with existing body-proxying logic.

3. **Should `createDeepAgentsResumeHandler` be exported from the server package index or as a sub-path?**
   - What we know: All current server exports are from the single `.` entry in `exports`.
   - What's unclear: Whether a sub-path export would be cleaner given this is an optional feature.
   - Recommendation: Add to the single `.` export entry. Sub-path exports require tsup changes and extra `exports` fields. The existing pattern exports everything from `.` — keep it consistent.

4. **What happens to the in-memory registry on Next.js hot reload in development?**
   - What we know: Next.js dev server hot-reloads modules; module-level singletons can reset.
   - What's unclear: Whether the registry needs a stable global (`global.__deepagents_registry`) to survive HMR.
   - Recommendation: Use `(globalThis as any).__deepagents_stream_registry ??= new Map()` pattern for the singleton. This is the standard Next.js pattern for dev-safe module singletons (Prisma client pattern).
